# Контракт метрик

Единственное место, где написано, что означает каждая денежная (и штучная)
величина в панели, откуда она берётся и что в неё не входит. Если цифра на
двух страницах не совпадает — сначала загляните сюда: возможно, это две
разные, законно различающиеся величины. Если расхождение не объясняется этим
документом — это баг, и он должен быть либо здесь же в разделе «Известные
расхождения», либо заведён как новая задача.

Числа-примеры в этом документе (если не оговорено иное) — кабинет 1, июль
2026. Числа, связанные с каноном прибыли (§§1-5, 8, 10-12), перепроверены
запросом `scripts/check-profit-canon.mjs` к боевой БД под ролью `saas_ro`
2026-08-20 (фикс-волна ревью плана унификации). Числа, не связанные с
каноном прибыли (себестоимость §7, налог §9, счётчики заказов/штук §§13-14),
сохраняют дату проверки 2026-08-10 — их формулы этой задачей не менялись.

Ссылки на файлы и номера строк актуализированы под код после фикс-волны
ревью плана «унификация формул прибыли»
(`docs/superpowers/plans/2026-08-20-profit-unification.md`, задачи 1-6) —
документ переписан заново под задеплоенный канон, а не подправлен точечно.
Код меняется, номера строк смещаются дальше: если строка не совпадает с
описанием — ищите формулу через `grep` по имени поля/колонки/функции в
указанном файле, а не считайте раздел неверным. Неверным раздел является,
только если сама формула (не номер строки) разошлась с кодом.

## Правило источников (читать первым)

**Обновлено 2026-08-20 (фикс-волна ревью плана унификации).** До
2026-08-20 этот раздел описывал панель как намеренно разъезжающуюся: «Сводка
по товарам/РНП/Детсводка/Главная/План-факт» на одном источнике денег,
`/pnl` — на другом. Это было верно ДО плана
`docs/superpowers/plans/2026-08-20-profit-unification.md`. После задач 1-6
плана это утверждение для денежных ИТОГОВ ПЕРИОДА (revenue, commission,
logistics, acquiring, loyalty, cogs, ads, tax, profit) больше НЕ описывает
код: все семь потребителей читают ОДНУ функцию на площадку.

### Канон прибыли (с 2026-08-20)

- **WB** — `wbProfitProduct`/`wbProfitCabinet`, `lib/wbMetrics.js:437-554`.
- **Ozon** — `ozProfitProduct`/`ozProfitCabinet`, `lib/ozonMetrics.js:247-357`.
- **Семь потребителей** (план, «Структура файлов»): `pnl`, `overview`,
  `detail` (итоги периода, НЕ дневная матрица — см. исключение 1 ниже),
  `products-summary`, `rnp-summary`, `plan/fact` (факт-колонки);
  `orders` не вызывает канон напрямую, но задача 5 сверила его подстановку
  себестоимости с каноном построчно (0 расхождений на момент проверки,
  `app/api/cabinets/[id]/orders/route.js:236-249`).
- `*Product(db, taxMode, {from, to}, id=null)` — товарная прибыль (одного
  SKU при `id`, кабинета целиком при `id=null`). Реклама (`ads`) при
  переданном `id` — **всегда 0** (площадки не дают per-SKU расход рекламы
  честно, размазывать нельзя, см. §8).
- `*Cabinet(db, taxMode, period)` — товарная прибыль (без `id`) ПЛЮС
  кабинетные расходы (`cabinetCosts[]`, знаковая сумма, русские labels,
  контракт №27 — не размазываются по SKU). Используется ТОЛЬКО двумя
  кабинетными страницами — `pnl`, `overview` (решение владельца 2026-08-20,
  см. докстроку `ozProfitCabinet`, `lib/ozonMetrics.js:320-330`).

### Источник канона — не тот же, что у «сырых» операционных запросов

И WB, и Ozon канон читает НЕ `wb_finance_report`/`ozon_order_costs`
напрямую построчно по дате проводки, а денормализованные таблицы
`tenant.wb_order_costs`/`tenant.ozon_order_costs`, которые собирает воркер
(`worker/collectors/wb_order_costs.py`, `worker/collectors/ozon_order_costs.py`)
ОДИН РАЗ по каждому заказу (`srid`/`product_id`+партия). Для WB это меняет
не только таблицу, но и **привязку по дате**: воркер агрегирует ВСЕ строки
finance_report одного `srid` за всю его историю (не только за период сбора)
и кладёт результат под датой ПРОДАЖИ (`sale_dt`) —
`worker/collectors/wb_order_costs.py:22-35` объясняет это прямо: WB часто
шлёт логистические доначисления («Возмещение издержек по перевозке») днями
позже продажи, и период-фильтрованная агрегация ранее теряла такие srid
целиком (инцидент 2026-07-29, 912 srid). Из-за этого канон — это
**учёт по дате продажи** («когда продали», order-based), а прямой SQL по
`wb_finance_report WHERE rr_dt BETWEEN ...` — **учёт по дате проводки**
(«когда WB провёл строку», event-based). Для строк, где логистика/поправка
проведена в ДРУГОМ календарном месяце, чем сама продажа, эти два способа
считать один и тот же месяц дают РАЗНЫЕ числа — не потому что где-то баг, а
потому что это два разных определения «за июль». Проверено на данных (см.
§§1.1, 3.1): за июль 2026 кабинет 1 логистика по канону (order-based)
57 208,38 ₽ против 77 926,36 ₽ по прямому SQL (event-based, `rr_dt` в
июле) — расхождение 26,6%, полностью объясняется описанным механизмом
(479 строк order_costs против 723 строк в `wb_finance_report`, проверено
`saas_ro` 2026-08-20). Выручка расходится меньше (0,5%, §1.1), т.к.
основная сумма продажи почти всегда проводится в тот же день, что и сама
продажа — доначисления откладываются в основном по логистике.

### Исключения — живут вне канона

1. **Дневные ряды `detail` (матрица SKU×день) и график `overview`
   (таймсерия по дням).** Используют `wbFinanceByDay`
   (`lib/wbMetrics.js:240-292`) — по-операционный агрегат НАПРЯМУЮ на
   `wb_finance_report` (`retail_price_withdisc_rub`/`delivery_rub`/
   `commission_percent`, дата = `rr_dt`, событийный учёт, НЕ учёт по дате
   продажи). Код сам фиксирует это как сознательно оставленный технический
   хвост: «per-day вариант... остаётся живым, его использует
   Детсводка/Обзор» (`lib/wbMetrics.js:230-231`). Кандидат на будущую
   унификацию (батч/дневной канон — вне периметра плана 2026-08-20).
2. **Виджет «Убыточные товары» (`lossMakers`) на `overview`.** Инлайн-SQL,
   `app/api/cabinets/[id]/overview/route.js:144-193` — своя формула по
   `finance_report` (не вызывает `wbProfitProduct`). Вне периметра этого
   плана (следующая задача, по решению владельца).
3. **Юнит-экономика (`/unit/all`, `/unit/inputs`, `lib/unit.js`, §11.4).**
   Модельный расчёт «что было бы», не факт — глобально исключена планом
   («юнит-эк. не трогать»).
4. **Счёт заказов/штук** (`orderRub`, §§1.4/1.6, «Заказано» §13). Не
   прибыль — вне периметра плана унификации прибыли, расхождения там
   остаются как были (см. «Известные расхождения» №6, 9).

Раньше (до 2026-08-20) этот раздел объяснял разницу между `retail_price_
withdisc_rub` (операционные страницы) и `retail_amount`/`ppvz_for_pay`
(`/pnl`) как легитимный, намеренный выбор владельца. Это исторически верно
для кода ДО унификации, но сейчас неточно как описание текущего `/pnl`:
`/pnl` больше не считает `retail_amount`/`sales`/`returns`/`netSales`
отдельно (см. §1.3) — он, как и все остальные, читает канон.

## 1. Выручка

### 1.1 Выручка канона (WB, `revenue` = `cost_value_pay`, «к перечислению»)

**Что это.** Единственная выручка, которую видят все семь потребителей
канона за один период (кабинетный уровень — `pnl`/`overview`, товарный —
`products-summary`/`rnp-summary`/`detail`-итоги/`plan-fact`). Концептуально
это то же самое, что было ЭТАЛОНОМ выручки для прибыли ещё до унификации
(урок D15, 2026-07-31): сумма, которую WB реально планирует перечислить
продавцу — комиссия/эквайринг/лояльность уже вычтены площадкой внутри
этого числа.

**Источник.** `tenant.wb_order_costs`, колонка `cost_value_pay` — сборщик
кладёт туда `ppvz_for_pay` строк «Продажа» (`worker/collectors/wb_order_costs.py:57`),
для строк-возвратов (`is_return=1`) `cost_value_pay` явно обнуляется
(`:77`) — возврат не вычитается построчно из выручки, он даёт отдельный
убыток через `profit = −logistics` (§11.1). Канонический код —
`wbRawProfitAggregate`/`wbProfitProduct`, `lib/wbMetrics.js:401-462`.
Таблица `wb_order_costs` агрегирована по `srid` и датирована `sale_dt` —
это учёт «по дате продажи», НЕ «по дате проводки строки в отчёте» (см.
врез в «Правило источников» выше про расхождение с прямым SQL).

**Формула.** `revenue = SUM(cost_value_pay)` за период (ВСЕ строки, без
фильтра `is_return` — возврат уже занулён построчно сборщиком).

**Где показывается.** Все семь потребителей канона: `/pnl` (`wb.revenue`,
он же `wb.forPay`, см. §11.2), `overview` (`k.revenue`), `products-summary`
(поле `salesRub`), `rnp-summary` (`salesRub`), `detail` (`totals.revenue`,
итог периода — НЕ дневная строка), `plan/fact` (`revenue_fact`).

**Что НЕ входит.** Не является ценой, которую видит покупатель. Не включает
логистику (вычитается отдельно из `profit`, §3.1), себестоимость, рекламу,
налог.

**Проверено на данных (июль 2026, кабинет 1, `check-profit-canon.mjs`,
`saas_ro`, 2026-08-20).** `revenue = 796 215,76 ₽`.

**Расхождение с прямым SQL по `wb_finance_report`.** Прямой запрос
`SUM(ppvz_for_pay | Продажа) − ABS(SUM(ppvz_for_pay | Возврат))` за тот же
период (`rr_dt` в июле) даёт 800 471,21 ₽ (проверено 2026-08-10) —
отличается от канона на 4 255,45 ₽ (0,5%). Объясняется учётом по дате
продажи vs дате проводки (см. «Правило источников») — доначисления/поправки
по `srid`, проведённые WB в июне или августе для июльских продаж (и
наоборот), канон относит к месяцу продажи, прямой SQL — к месяцу проводки.

### 1.2 Выручка (WB, дневные ряды — `detail`/`overview`, НЕ канон)

**Что это.** Сумма продаж «по цене со скидкой продавца, без СПП»
(`retail_price_withdisc_rub`) построчно по дате проводки (`rr_dt`) — живёт
ТОЛЬКО в дневной матрице `detail` и графике `overview` (исключение 1 из
«Правило источников»). До 2026-08-20 это была формула ВСЕХ операционных
страниц за период; сейчас периодные итоги этих же страниц (§1.1) считаются
иначе — с этой формулой совпадать не обязаны.

**Источник.** `tenant.wb_finance_report`, колонка `retail_price_withdisc_rub`,
`supplier_oper_name='Продажа'`, `nm_id IS NOT NULL AND nm_id != 0`. Код —
`wbFinanceByDay`, `lib/wbMetrics.js:240-292`.

**Формула.** `salesRub = SUM(retail_price_withdisc_rub)` по дате `rr_dt`.

**Где показывается.** `detail` (дневная матрица SKU×день, `days[].revenue`),
`overview` (график по дням, `overview/route.js:266,289`). НЕ показывается
на `products-summary`/`rnp-summary`/`plan/fact`/`/pnl` — там периодный итог
теперь §1.1.

**Что НЕ входит.** Не совпадает с каноном (§1.1) — другая дата-привязка
(проводка, не продажа) и другая исходная колонка.

### 1.3 Выручка (WB, `/pnl`) — раздел устарел, канон с 2026-08-20

**Что было (до 2026-08-20).** `/pnl` считал отдельную «официальную сумму
отчёта о реализации» из `wb_finance_report.retail_amount`
(`netSales`/`sales`/`returns`) — отдельно от операционных страниц.

**Что сейчас.** `/pnl` НЕ вычисляет `retail_amount`/`netSales`/`sales`/
`returns` вовсе — эти поля исчезли из ответа роута. `/pnl` вызывает
`wbProfitCabinet` (§1.1/§11.2) и отдаёт `wb.revenue` — тот же канон, что
видят `overview`/`products-summary`/`rnp-summary`/`detail`/`plan-fact`.
`app/api/cabinets/[id]/pnl/route.js:9-10,18-40,61`. Поле `forPay` в ответе
`/pnl` (`mpBlock`, `pnl/route.js:44`) — не самостоятельный расчёт, а
`c.revenue` (то же значение, что и `revenue`) под старым именем, оставленным
для обратной совместимости фронтенда.

**Историческая справка.** Раньше `retail_amount` за июль 2026 кабинет 1 (по
прямому SQL) давал 823 280,82 ₽ — если кому-то нужна именно эта «официальная
сумма отчёта о реализации» отдельно от `ppvz_for_pay`-эталона, её больше
негде увидеть на панели: `/pnl` её не показывает. Открытый вопрос владельцу
(новый, см. раздел ниже): нужна ли эта величина панели вообще, если да — она
не восстановлена унификацией и её придётся вернуть отдельно.

### 1.4 Сумма заказов, ₽ (WB, `orderRub`) — ДВЕ конфликтующие формулы

**Что это.** Не выручка вообще, а сумма ЗАКАЗОВ (оформленных корзин) за
период. Показывает «сколько на сумму заказали», а не «сколько продано». Как и
«Заказано, шт» (раздел 13), эта величина считается по-разному на разных
страницах — с фильтром отменённых и без него.

**Формула А — с фильтром отмен (`overview`, `overview/route.js:68-71`).**
`orderRub = SUM(price_with_disc) FROM wb_orders WHERE is_cancel = 0`.
Отменённые заказы НЕ входят в сумму.

**Формула Б — без фильтра отмен (`products-summary`, `products-summary/route.js:277-286`).**
`orderRub = SUM(price_with_disc) FROM wb_orders GROUP BY nm_id`, без условия
на `is_cancel`. Отменённые заказы ВХОДЯТ в сумму — это осознанный выбор,
закреплённый комментарием в коде («Заказы из orders включают отмены → дают
честную сумму заказов»), но он делает число несовместимым с тем, что
показывает `overview` за тот же период.

**Источник (обеих).** `tenant.wb_orders`, колонка `price_with_disc`,
`order_dt` в диапазоне.

**Где показывается.** `overview` (формула А), `products-summary` (формула Б,
влияет также на «средний чек» `avgCheck = orderRub / ordered`,
`products-summary/route.js:111,236`).

**Что НЕ входит.** Ни одна из формул не выручка — часть заказов не
выкупается или отменяется. `orderRub >= revenue (1.1)`, как правило, для
обеих формул. Не путать с §1.1 — `orderRub` вне периметра плана унификации
прибыли (это счёт заказов, не денег к перечислению), формулы не менялись.

**Проверено на данных (июль 2026, кабинет 1).**

| Формула | Число |
|---|---|
| А — `is_cancel=0` (`overview`) | **1 539 861,02 ₽** |
| Б — без фильтра (`products-summary`) | **1 947 866,72 ₽** |

Разница 408 005,70 ₽ (26,5% от формулы А) — не округление и не окно данных, а
буквально другой набор строк. См. «Известные расхождения», п. 9.

### 1.5 Выручка (Ozon, канон, все семь потребителей)

**Что это.** Стоимость отправлений за период — единая формула на ВСЕХ
семи потребителях канона (у Ozon раздвоения источника между `/pnl` и
операционными страницами никогда не было, план унификации только заменил
разрозненные вызовы одной функцией).

**Источник.** `tenant.ozon_order_costs`, колонка `cost_value_retail`, дата
`COALESCE(sale_dt, return_dt)`. Канонический код —
`ozRawProfitAggregate`/`ozProfitProduct`, `lib/ozonMetrics.js:208-266`.

**Формула.** `revenue = SUM(cost_value_retail)` за период — **БЕЗ фильтра
`is_return`** (изменилось задачей 1 плана унификации, см. ниже).

**Где показывается.** `/pnl` (`ozon.revenue`), `overview`, `products-summary`,
`rnp-summary`, `detail`, `plan/fact` — везде один вызов.

**Что НЕ входит и что изменилось.** До 2026-08-20 формула фильтровала
`is_return=0` (возвраты исключались целиком, валовая сумма отгруженного).
Канон **не фильтрует** — суммирует все строки `order_costs`, включая
возвраты; чистый эффект зависит от того, как сборщик
(`worker/collectors/ozon_order_costs.py`) записывает `cost_value_retail`
для строк-возвратов. Это задокументированное, а не побочное поведение —
`returnLogistics` (справочное поле канона, §4) прямым текстом указывает
«уже внутри logistics/commission выше» по тому же принципу.

**Проверено на данных (июль 2026, кабинет 1, канон, `saas_ro`, 2026-08-20).**
`revenue = 508 259,00 ₽` (все строки). Историческое число «478 333 ₽»
(2026-08-10, `is_return=0` отдельно) относится к формуле ДО этой правки —
не сравнивайте их напрямую, это два разных определения.

### 1.6 Сумма заказов, ₽ (Ozon, `orderRub`) — ДВЕ конфликтующие формулы

**Что это.** Симметрично 1.4 — сумма оформленных заказов (не только
доставленных). Та же болезнь, что у WB: с фильтром отмен и без него.

**Формула А — с фильтром отмен (`overview`, `overview/route.js:100-101`).**
`orderRub = SUM(price) FROM ozon_orders WHERE is_cancel = 0`.

**Формула Б — без фильтра отмен (`products-summary`, `products-summary/route.js:490-503`).**
`orderRub = SUM(price * qty) FROM ozon_orders GROUP BY product_id`, `SUM`
считается по ВСЕМ строкам периода — фильтр `is_cancel=0` в этом запросе
применён только к отдельным колонкам `ordered`/`cancelled` (счётчикам штук),
не к `orderRub`.

**Источник (обеих).** `tenant.ozon_orders`, `order_dt` в диапазоне.
`overview` берёт `price` (цена за единицу); `products-summary` — `price * qty`.
На данных кабинета 1 это не даёт разницы (в периоде `qty = 1` на всех
строках), но формулы не идентичны и могут разойтись на кабинете, где заказ
идёт партией.

**Ограничение.** Таблица `orders` у Ozon хранит только последние ~2 недели
(живые отправления в обработке) — за полный месяц `orderRub` будет НИЖЕ
реальности независимо от формулы. Это ограничение источника, не баг:
`revenue` (1.5) — из `order_costs`, полный и достоверный. `orderRub` вне
периметра плана унификации прибыли, формулы не менялись.

**Где показывается.** `overview` (формула А), `products-summary` (формула Б),
`rnp-summary` (`orderedFact` — штуки, не ₽, фильтр отмен применён корректно).

## 2. Комиссия

### 2.1 Комиссия — WB, канон (все семь потребителей, включая `/pnl`)

**Что это по коду сейчас — изменилось задачей 5 плана унификации.** До
2026-08-20 операционные страницы считали комиссию вручную по проценту
(`commission_percent × retail_price_withdisc_rub / 100`, решение владельца
2026-07-09), а `/pnl` считал её как остаток (см. историческую справку
ниже). Канон делает ни то, ни другое — читает ГОТОВУЮ колонку от WB.

**Источник.** `tenant.wb_order_costs`, колонка `commission` — сборщик кладёт
туда `ABS(ppvz_sales_commission)` строк «Продажа»/«Возврат»
(`worker/collectors/wb_order_costs.py:59`) — это именно `ppvz_sales_commission`,
готовая колонка WB, которую версия документа ДО 2026-08-20 явно
противопоставляла ручному расчёту («это НЕ то же самое… расчёт делается
вручную по проценту»). Канонический код —
`wbRawProfitAggregate`/`wbProfitProduct`, `lib/wbMetrics.js:401-462`.

**Формула.** `commission = SUM(commission)` за период (все строки, та же
логика без-фильтра-`is_return`, что у выручки, §1.1).

**Где показывается.** Все семь потребителей канона — `/pnl`, `overview`,
`products-summary`, `rnp-summary`, `detail` (итоги периода), `plan/fact`.

**Важно — поле справочное, НЕ вычитается из `profit`.** commission/
acquiring/loyalty УЖЕ учтены площадкой внутри `revenue` (`cost_value_pay`,
«к перечислению») — канон их не вычитает из `profit` повторно (урок D15,
см. §11.1). Показ этого поля — информационный (напр., для расчёта
`commissionPct` на витрине).

**Формула-исключение (жива только в дневном ряде, НЕ канон).**
`wbFinanceByDay` (`lib/wbMetrics.js:240-292`, дневная матрица `detail` и
график `overview`) по-прежнему считает `commission_percent ×
retail_price_withdisc_rub / 100` построчно на `wb_finance_report` — старая
формула, описанная в этом разделе до 2026-08-20 как формула ВСЕХ
операционных страниц. Это подтверждает исключение 1 из «Правило
источников» — технический хвост, не новое расхождение.

**Проверено на данных (июль 2026, кабинет 1, канон, `saas_ro`, 2026-08-20).**
`commission = 89 757,85 ₽`.

**Историческая справка — `/pnl` до 2026-08-20 (Известные расхождения №1,
закрыто).** Раньше `/pnl` считал комиссию как остаток
`Math.max(0, netSales − forPayNet − costRub)` (`pnl/route.js:99` в старой
версии кода) и на июльских данных обнулялся (см. закрытый пункт №1 в
«Известные расхождения» ниже). Этот код больше не существует — `/pnl`
теперь получает `commission` из того же канона, что и остальные страницы.

### 2.2 Комиссия — Ozon, канон (все семь потребителей)

**Источник.** `tenant.ozon_order_costs`, колонка `commission`, **БЕЗ
фильтра `is_return`** (изменилось задачей 1 плана унификации, тот же
принцип, что и выручка Ozon, §1.5). Код —
`ozRawProfitAggregate`/`ozProfitProduct`, `lib/ozonMetrics.js:208-266`.

`is_return=0`) — старая формула, см. врез §1.5 про фильтр `is_return`.

route.js:177-203`, — этого блока в файле больше нет). Канон строит
`order_costs` из ВСЕХ `nm_id`, когда-либо встречавшихся в таблице

уже полна и аддитивна сама по себе… никакого top-up не требуется») —
top-up больше не нужен, проверено сторожем (`check-profit-canon.mjs`,
проверка «слагаемые аддитивны»).

(`lib/wbMetrics.js:240-292`) по-прежнему считает `delivery_rub` напрямую по
дате `rr_dt` — прежний источник, используется только дневной матрицей
`detail` и графиком `overview`.

**Проверено на данных (июль 2026, кабинет 1, канон, `saas_ro`,

дате проводки (см. «Правило источников»; 479 строк в `wb_order_costs`
против 723 строк «Логистика» в `wb_finance_report` за тот же календарный
июль, проверено `saas_ro` 2026-08-20). Старая версия этого раздела называла

## 4. Убыток по возвратам (Ozon) — унифицирован задачей 1, был в «Известных расхождениях» до 2026-08-20

**Что это.** Логистика и комиссия по возвращённым отправлениям. Себестоимость
возвращённого товара НЕ списывается повторно (товар физически вернулся на
склад) — решение владельца 2026-07-23, но логистика и комиссия за факт
возврата — реальный расход, который должен уменьшать прибыль.

**Что изменилось.** До 2026-08-20 эта формула жила только инлайн в
`products-summary` и отсутствовала на `/pnl`/`rnp-summary`/`detail`/
`overview`/`plan-fact` (см. историческую справку ниже — это был пункт №3 в
«Известных расхождениях»). Канон (§1.5, §2.2, §3.2) больше НЕ фильтрует
`is_return` при подсчёте `revenue`/`commission`/`logistics` — убыток
возврата уже НЕВОЗМОЖНО не учесть, он арифметически внутри общей суммы
каждого слагаемого на ЛЮБОЙ странице, читающей канон. `returnLogistics` в
ответе канона — теперь ЧИСТО справочное поле (уже включённая в
`logistics`/`commission` разбивка «сколько из этой суммы — возвраты»), не
отдельное вычитаемое.

**Источник.** `tenant.ozon_order_costs`, `is_return=1`, колонки `logistics`
и `commission` — выбираются той же агрегацией, что и остальные слагаемые.
Код — `ozRawProfitAggregate`, `lib/ozonMetrics.js:208-238` (поля
`retLogistics`/`retCommission`, объединяются в `returnLogistics` на выходе
`ozProfitProduct`, `lib/ozonMetrics.js:247-266`).

**Формула.** `returnLogistics = SUM(logistics | is_return=1) + SUM(commission | is_return=1)` —
справочная сумма, УЖЕ содержащаяся внутри `logistics`/`commission` (§§2.2,
3.2), profit её не вычитает второй раз.

**Где показывается.** Все семь потребителей канона: `/pnl`, `overview`,
`products-summary`, `rnp-summary`, `detail` (итоги периода), `plan/fact` —
везде как справочное поле, и везде убыток возврата уже внутри итоговой
прибыли (в отличие от версии контракта до 2026-08-20, где это было верно
ТОЛЬКО для `products-summary`).

**Проверено на данных (июль 2026, кабинет 1, канон, `saas_ro`,
2026-08-20).** `returnLogistics = 16 981,54 ₽` (в составе `logistics =
51 453,88 ₽` и `commission = 235 977,80 ₽`, §§2.2/3.2 — сумма отличается от
исторического «29 442,50 ₽», 2026-08-10, тем же классом причин, что и
остальные Ozon-слагаемые: канон больше не фильтрует `is_return` при выборе
базовых сумм, из которых берётся эта разбивка).

**Где показывается КАК ОТДЕЛЬНАЯ ВИТРИННАЯ КОЛОНКА.** `/pnl` (`cabinetCosts`,

## 7. Себестоимость

**Источник (единый, с 2026-07-14).** `tenant.cost_overrides` — колонки
`nm_id`/`product_id`, `platform`, `cost`, `effective_from`. Актуальная
себестоимость на дату = последняя запись с `effective_from <= дата`.

**Что изменилось задачами 1-5 плана унификации.** До 2026-08-20 `/pnl` и
`overview` пересчитывали себестоимость историчски (LATERAL по каждой
продаже) прямо в роуте, а `products-summary`/`rnp-summary` брали «на
сегодня» — два разных числа за один период (это было открытым вопросом
владельцу). С 2026-08-20 `/pnl` и `overview` НЕ делают собственный LATERAL
вовсе (grep `cost_overrides` по `pnl/route.js` — 0 совпадений) — cogs
приходит из канона (`f.cogs`/`c.cogs`, §11.1), то есть из
`tenant.wb_order_costs.cost`/`tenant.ozon_order_costs.cost`, УЖЕ посчитанных
сборщиком. Это делает cogs ЕДИНЫМ для всех семи потребителей канона —
но методика самого сборщика различается по площадке (см. ниже), поэтому
открытый вопрос владельцу закрылся ЧАСТИЧНО (устранена межстраничная
разница внутри WB и внутри Ozon, но не между WB и Ozon).

**WB — сборщик считает историчски (по дате продажи).**
`worker/collectors/wb_order_costs.py:79-87`:
```sql
LEFT JOIN LATERAL (
  SELECT cost FROM tenant.cost_overrides
  WHERE nm_id = o.nm_id AND platform='wb'
    AND effective_from <= COALESCE(substr(o.sale_dt,1,10)::date, substr(o.order_dt,1,10)::date, current_date)
  ORDER BY effective_from DESC LIMIT 1
) co ON true
```
Себестоимость КАЖДОГО заказа фиксируется один раз при сборе, на дату
продажи ЭТОГО заказа — не пересчитывается задним числом, если
`cost_overrides` поменялся позже.

**Ozon — сборщик считает «на момент своего последнего запуска», НЕ по дате
продажи.** `worker/collectors/ozon_order_costs.py:648-652`:
`effective_from <= current_date` (без привязки к `sale_dt`/`order_dt`
заказа) — та же формула, что раньше называлась «на сегодня» для
операционных страниц, но теперь это ЕДИНСТВЕННАЯ формула себестоимости
Ozon (нет больше отдельной «исторической» ветки где бы то ни было в
профит-канале).

**Витринное поле `unitCost` (справочное, НЕ участвует в `profit`).**
`products-summary`/`rnp-summary` дополнительно показывают колонку
`unitCost` — ЖИВОЙ запрос `cost_overrides WHERE effective_from <=
current_date` прямо в роуте (`products-summary/route.js:344-355` WB,
`:566-577` Ozon), для отображения «текущая закупочная цена за штуку», не
для расчёта прибыли — `profit` строки берётся из канона (`f.cogs`), эта
колонка сосуществует с ним, но формулы у них разные.

**`unit/all` (`lib/unit.js`).** Отдельная, глобально исключённая из плана
унификации ветка (§11.4) — использует `cost_overrides` (`current_date`) для
WB и Ozon независимо от канона. Не путать с профит-каноном.

**Что НЕ входит.** По намерению — себестоимость возвращённого товара НЕ
должна списываться повторно (товар физически вернулся на склад). У Ozon
это явно оговорено сборщиком (решение владельца 2026-07-23). У WB
сборщик комментирует ту же цель прямым текстом («profit возврата =
−logistics, себест. не списываем», `worker/collectors/wb_order_costs.py:110`),
но `cost` в строке возврата технически присутствует в `order_costs`
(join `cost_overrides` не условен на `is_return`) — согласуется ли это с
комментарием построчно, эта фикс-волна НЕ проверяла (нужен отдельный
SQL-аудит `wb_order_costs` на строках `is_return=1`, вне периметра задачи
F1).

## 8. Реклама

**WB, кабинетный итог.** `tenant.wb_daily_metrics`, колонка `ad_spend`.
Функция `wbAdTotal`, `lib/wbMetrics.js:293-313`:
`SUM(ad_spend) WHERE ad_spend IS NOT NULL`. Вызывается ВНУТРИ канона
(`wbProfitProduct`/`wbProfitCabinet`, `lib/wbMetrics.js:437-462`) при
`nmId=null` — то есть при расчёте кабинетной прибыли, а не отдельно на
каждой странице, как раньше. Детсводка (`detail`) для дневной матрицы
использует более детальный источник `daily_ad` (3 модели:
единая/ручная/клики) и суммирует их для итога — эта часть не входит в

## 9. Налог (УСН + НДС)

**Источник модели.** `lib/tax.js`, режим (`tax_mode`) хранится per-shop:
`{ type: 'usn_income'|'usn_income_expenses', rate, vat }`.

**Формула.** Две ПОЛНОСТЬЮ разные ветки в зависимости от режима — `expenses`
участвует только в одной из них (`calcUsnTax`, `lib/tax.js:66-85`):

- НДС (общий для обоих режимов) выделяется «изнутри» цены с НДС:
  `vat = revenue × vat/(100+vat)`. `revenueNet = revenue − vat`.
- Режим `usn_income` («Доходы»): `usn = revenueNet × rate%`. `expenses` в
  этой ветке НЕ используется вообще, даже если передан вызывающим кодом.
- Режим `usn_income_expenses` («Доходы минус расходы»): `usn = max(0, revenueNet − expenses) × rate%`,
  но не менее `revenueNet × 1%` (минимальный налог).
- `calcTotalTax(taxMode, revenue, expenses)` возвращает `{ usn, vat, total, revenueNet }`
  — `total = usn + vat`, именно это число вычитается из выручки во всех формулах прибыли.

**Единообразие.** Используется одинаково во всех страницах, где считается
налог: `/pnl`, `overview`, `products-summary`, `rnp-summary`, `detail`,
`plan/fact`, `unit/all` (`/unit` удалён задачей 5 как мёртвый роут, см.
§11.3). Расхождений в самой налоговой формуле не найдено.

**База налога — унифицирована задачей 5 (закрывает разночтение, описанное
здесь до 2026-08-20).** Раньше база различалась по странице (WB
операционные — `forPay`, `/pnl` — `netSales`/`retail_amount`). Сейчас ВСЕ
семь потребителей канона считают налог от ОДНОЙ и той же `revenue` (WB —
`cost_value_pay`, §1.1; Ozon — `cost_value_retail`, §1.5) внутри
`wbProfitProduct`/`ozProfitProduct` (`calcTotalTax(taxMode, agg.revenue,
expenses)`, `lib/wbMetrics.js:437-462`, `lib/ozonMetrics.js:247-266`) — одна
и та же строчка вызова на обеих площадках, вместо разбросанных вызовов на
каждой странице со своей `revenue`. `unit/all` — исключение (§0), считает
налог по своей модельной базе, вне канона.

## 11. Прибыль

### 11.1 Прибыль канона (`profit`) — ОДНА формула на площадку, семь потребителей

**Переписан целиком задачами 1/2/5 плана унификации.** До 2026-08-20 у
операционных страниц и `/pnl` были разные формулы прибыли (§§11.1/11.2
старой версии этого документа). Сейчас есть ровно ДВЕ формулы (WB, Ozon), у
каждой два режима (товарный/кабинетный, §0) — и их считает не «страница»,
а `wbProfitProduct`/`wbProfitCabinet` (`lib/wbMetrics.js:437-554`),
`ozProfitProduct`/`ozProfitCabinet` (`lib/ozonMetrics.js:247-357`).

**WB.** `profit = revenue (1.1, cost_value_pay) − cogs (7) − logistics (3.1) − ads (8) − tax (9)`.
Физически считается сборщиком построчно (`wb_order_costs.profit =
cost_value_pay − cost − logistics`, `worker/collectors/wb_order_costs.py:111`)
и суммируется каноном (`wbRawProfitAggregate`, `lib/wbMetrics.js:401-434`,
поле `rawProfit`), затем `wbProfitProduct` вычитает `ads`/`tax` сверху
(`lib/wbMetrics.js:437-462`). Commission/acquiring/loyalty НЕ вычитаются
повторно — они уже внутри `revenue` (площадка вычла их сама при расчёте «к
перечислению»), это неизменно с урока D15 (2026-07-31).

**Ozon.** `profit = revenue (1.5) − cogs (7) − commission (2.2) − logistics (3.2) − acquiring (5) − loyalty − ads (8) − tax (9)`.
`returnLogistics` (§4) уже внутри `commission`/`logistics` выше — НЕ
вычитается отдельной строкой (это изменилось: до 2026-08-20 в
`products-summary` он вычитался ДОПОЛНИТЕЛЬНО, теперь просто справочно
раскрывает состав, т.к. канон включает возвраты в базовые суммы
безусловно, §1.5).

**`calcOperatingProfit` — удалена (эта фикс-волна).** Версия документа до
2026-08-20 указывала на неё как на «формально задокументированную, но
никем не вызываемую» функцию (`lib/wbMetrics.js:418-433` в старой
нумерации) — 0 реальных вызовов подтверждены grep по `app/**`. Функция и
её ре-экспорт из `lib/ozonMetrics.js` удалены этой фикс-волной; роль,
которую она была должна исполнять, реально исполняют `wbProfitProduct`/
`wbProfitCabinet` выше, вызываемые всеми семью потребителями.

**Проверено на данных (июль 2026, кабинет 1, канон, `saas_ro`,
2026-08-20).** WB: `revenue 796 215,76 − cogs 414 810,00 − logistics
57 208,38 − ads 111 449,37 − tax 45 498,05 = profit 167 249,96 ₽` (товарная,
`*Product`); кабинетная (`*Cabinet`, + `cabinetCosts`, §10) —
`177 190,26 ₽`. Ozon: товарная `profit = −130 999,59 ₽` (убыточен по
каналу за этот месяц — реклама 63 947,03 ₽ и себестоимость 254 115,00 ₽
перекрывают выручку 508 259,00 ₽ за вычетом комиссии/логистики/эквайринга);
кабинетная — `−179 413,96 ₽` (кабинетные статьи Ozon в июле в основном
расходные, §10).

### 11.2 Прибыль `/pnl` (`netProfit`/`profit`) — раздел устарел, канон с 2026-08-20

**Что было (до 2026-08-20).** `/pnl` считал `netProfit`/`grossProfit`
самостоятельным каскадом: своя выручка (`netSales`, §1.3), своя комиссия
(остаточный метод, обнулявшийся на реальных данных — «Известные
расхождения» №1), без рекламы (№2), без убытка по возвратам Ozon (№3).

**Что сейчас.** `/pnl` вызывает `wbProfitCabinet`/`ozProfitCabinet` (та же
функция, что и `overview`) и оборачивает результат в `mpBlock`
(`app/api/cabinets/[id]/pnl/route.js:18-40`). Поля ответа: `revenue`,
`cogs`, `commission`, `logistics`, `acquiring`, `loyalty`,
`returnLogistics`, `ads`, `tax`, `cabinetCosts[]`, `cabinetCostsTotal`,
`unknownCostTypes`, `profit` (= канон, включает кабинетные статьи),
`grossProfit` (справочный подытог ДО рекламы/налога/кабинетных статей:
`revenue − cogs − commission − logistics − acquiring − loyalty`,
`pnl/route.js:43`), `forPay` (= `revenue` для WB, 0 для Ozon — оставлено
под старым именем для совместимости фронтенда). Полей `netSales`/`sales`/
`returns` в ответе больше нет (§1.3).

**Отличие от 11.1.** Единственное содержательное отличие теперь —
`/pnl`/`overview` вызывают `*Cabinet` (с `cabinetCosts`), а
`products-summary`/`rnp-summary`/`detail`/`plan-fact` — `*Product` (без
`cabinetCosts`, решение владельца, §0/§10). Формулы revenue/cogs/
commission/logistics/acquiring/ads/tax — идентичны на уровне товарной
части (проверено сторожем, «productId-фильтр аддитивен»).

### 11.3 Поюнитная юнит-экономика (`/api/cabinets/[id]/unit`) — роут удалён

**Что было.** До 2026-08-20 роут показывал `AVG(order_costs.profit)` —
готовую колонку из сборщика БЕЗ вычета налога, рядом считая `tax`, но не

**Что сейчас.** Роут `app/api/cabinets/[id]/unit/route.js` УДАЛЁН задачей 5

— если роут появится снова, ловушка «tax считается, но не вычитается» не
должна повториться.

### 11.4 Прибыль в модельной юнит-экономике (`unit/all`, `lib/unit.js`)

**Что это.** НЕ факт из БД, а модельный расчёт «сколько заработали бы на этой
цене» — входы частично автоматические (средние из истории), частично ручные
(`tenant.unit_inputs`), включая ставку рекламы ДРР = константа 10% по
умолчанию (не фактический расход).

**Формула WB.** `profit = priceCabinet − vat − usn − acquiring − commission − ads − logistics − cost`,
где `vat`/`usn`/`acquiring` считаются от `priceBuy` (цены с СПП), а
`commission`/`ads` — от `priceCabinet` (без СПП). `lib/unit.js:162`.

**Формула Ozon.** `profit = revNet − commission − logisticsFbo − ads − usn − cost`. `lib/unit.js:280`.

**Отличие от 11.1/11.3.** Это не измерение факта, а модель «типового» юнита:
логистика WB считается по формуле тарифа `(50+20·(L−1))/выкуп × 1.6`, а не
берётся из отчёта; реклама — фиксированные 10% выручки, а не факт из
`daily_metrics`. Использовать для сверки с фактической прибылью нельзя по
конструкции.

## 13. Заказано, шт (WB)

```sql
FROM orders WHERE order_dt BETWEEN ? AND ? GROUP BY nm_id
```
`COUNT(*)` без фильтра `is_cancel` — отменённые заказы ВХОДЯТ в «заказано»
(поле `ordered` в ответе). Дополнительно код берёт
`ordered = Math.max(o.ordered, sold + cancelled)`, что не отменяет проблему:
базовое число `o.ordered` уже включает отмены.

**Проверено на данных (июль 2026, кабинет 1, календарный месяц).**

| Формула | Число |
|---|---|
| Канон (`is_cancel=0`) | 511 |
| `products-summary` (без фильтра) | 638 |

Расхождение 24,8% на календарном июле (значение зависит от периода и доли
отмен в нём — аудит 2026-08-10 приводил 8,6% на своём умолчательном
30-дневном окне; оба числа подтверждают факт расхождения, конкретный процент
плывёт вместе с периодом). См. «Известные расхождения», п. 6.

## 14. Продано, шт

**Канон (`wbSold`, `lib/wbMetrics.js:147-166`).** `tenant.wb_sales`,
`is_realization=1 AND price_with_disc > 0` — используется в `overview`,
`plan/fact`, как основной источник в `products-summary` (`fresh`, если по
товару есть данные в `sales`), в `rnp-summary` (`soldAll`).

**Fallback в `products-summary`.** Если по `nm` нет строки в `sales` за
период — берётся `sold` из `order_costs` (`is_return=0`, дата продажи в
периоде), это ДРУГОЙ источник с потенциально другими числами (нет прямой
проверки, что два источника всегда совпадают — комментарий в коде говорит
«оба фильтра дают совпадающие числа на бою, проверено в smoke Этапа 4», но
это проверка на одном срезе, не гарантия на будущее).

**`unit/route.js` — роут удалён (задача 5 плана унификации, §11.3).** До
2026-08-20 это был третий независимый источник (`COUNT(*) FILTER (WHERE
oc.is_return=0)` из `order_costs` напрямую, без обращения к `sales`).
Больше не существует.

**Ozon.** Единый источник везде — `order_costs`, дата
`COALESCE(sale_dt, return_dt)` (`sales` у Ozon содержит только
отмены/возвраты и не годится как источник продаж — грабля #134,
задокументирована в `products-summary/route.js:435-443`). Штучный счётчик
`sold` НЕ входит в профит-канон (§0) — не пересекается с
`is_return`-правилом §1.5, которое касается только денежных слагаемых
`revenue`/`cogs`/`commission`/`logistics`/`acquiring`/`loyalty`.

## Известные расхождения с реализацией

Величины, для которых этот контракт описывает правильное (или хотя бы
единообразное) поведение, а код по состоянию на коммит, зафиксированный в
отчёте к этой задаче, считает иначе. Каждая строка — кандидат в отдельную
задачу исправления.

**Закрыто планом «унификация формул прибыли» (2026-08-20) — пункты 1-5, 7
(частично), 8 старой версии этого документа.** Оставлены как историческая
справка (что было, чем закрыто), не удалены — чтобы не потерять контекст,
почему архитектура именно такая.

1. ~~Комиссия WB в `/pnl` обнуляется на реальных данных.~~ **ЗАКРЫТО
   задачей 5.** Было: `pnl/route.js:99`, остаточный метод `Math.max(0,
   netSales − forPayNet − costRub)`, на июльских данных 2026 давал 0 ₽ при
   191+ реальных продажах. Сейчас: `/pnl` читает `commission` из канона
   (`ppvz_sales_commission`, §2.1) — 89 757,85 ₽ за июль 2026, кабинет 1.

2. ~~Реклама не вычитается в `/pnl`.~~ **ЗАКРЫТО задачей 4.** `/pnl` теперь
   вычитает `ads` из `profit` через `*ProfitCabinet` (§8, §11.2) на обеих
   площадках.

3. ~~Убыток по возвратам Ozon учтён только в `products-summary`.~~
   **ЗАКРЫТО задачей 1.** Канон больше не фильтрует `is_return` при выборе
   базовых сумм (§1.5) — убыток возврата арифметически внутри `logistics`/
   `commission` на ВСЕХ семи потребителях, `returnLogistics` — справочное
   поле разбивки (§4).

4. ~~`rnp-summary` (Ozon): расчёт возвратов не портирован.~~ **ЗАКРЫТО**,
   частный случай п. 3.

5. ~~`unit/route.js` показывает валовую прибыль без вычета налога.~~
   **ЗАКРЫТО удалением роута** (задача 5, коммит `e014738`, §11.3).

6. **«Заказано» (WB) считается двумя разными фильтрами по отменённым
   заказам — НЕ ЗАКРЫТО, вне периметра плана унификации прибыли (это
   счёт штук, не денег).** Канон (`lib/wbMetrics.js:90-102`, `overview`,
   `rnp-summary`) — `COUNT(*) WHERE is_cancel=0`.
   `products-summary/route.js:277-286` считает `COUNT(*)` без фильтра,
   отменённые заказы попадают в «заказано». Проверено на данных
   (2026-08-10, формула не менялась): 511 (канон) vs 638
   (`products-summary`) за календарный июль 2026, кабинет 1 — расхождение
   24,8% на этом периоде.

7. **Средняя маржа считалась тремя способами — ЧАСТИЧНО ЗАКРЫТО задачей 5.**
   Раньше `/pnl`, `overview`, `products-summary`/`rnp-summary` считали
   маржу взвешенно, но по ТРЁМ разным базам выручки. Теперь база одна
   (канон, §1.1/§1.5, §12) — эти три способа СХОДЯТСЯ на одном периоде
   (кроме `cabinetCosts` в числителе `/pnl`/`overview`, что не расхождение
   базы, а осознанное разное покрытие). `unit/all/route.js:46-47,63-64`
   остаётся математически некорректным для агрегата (простое среднее
   процентов без веса по обороту) — вне периметра плана (§0, исключение 3),
   НЕ ЗАКРЫТО.

8. ~~`calcOperatingProfit` заявлена как единая функция, но нигде не
   вызывается.~~ **ЗАКРЫТО этой фикс-волной** (удалена как мёртвый код,
   0 реальных вызовов подтверждены grep по `app/**`/`lib/**`/`scripts/**`,
   см. §11.1). Роль, для которой её задумывали, исполняют
   `wbProfitProduct`/`wbProfitCabinet`, вызываемые всеми семью
   потребителями.

9. **«Сумма заказов» (`orderRub`, WB и Ozon) считается двумя разными
   фильтрами по отменённым заказам — НЕ ЗАКРЫТО, вне периметра плана
   унификации прибыли.** Тот же класс дефекта, что и п. 6, для другой
   величины (§§1.4, 1.6). `overview` фильтрует `is_cancel=0`
   (`overview/route.js:62-63` WB, `:100-101` Ozon). `products-summary`
   считает `orderRub` без фильтра по отменённым
   (`products-summary/route.js:277-286` WB, `:490-503` Ozon) — осознанный
   выбор («честная сумма заказов»), не упомянутый на UI. Проверено на
   данных 2026-08-10 (формула не менялась): WB — 1 539 861,02 ₽ (с
   фильтром) vs 1 947 866,72 ₽ (без фильтра), разница 408 005,70 ₽ (26,5%);
   Ozon — 851 917 ₽ vs 944 023 ₽, разница 92 106 ₽ (10,8%). От `orderRub` в
   `products-summary` дополнительно зависит «средний чек»
   (`avgCheck = orderRub / ordered`, `products-summary/route.js:111,236`).

**Новые находки этой фикс-волны (2026-08-20) — не были в исходном аудите,
всплыли при сверке контракта с задеплоенным каноном.**

10. **Канон WB считает по дате продажи (`sale_dt`), а не по дате проводки
    строки в отчёте (`rr_dt`) — расхождение с прямым SQL по
    `wb_finance_report`, разное для разных слагаемых.** Не баг канона (см.
    подробное объяснение механизма в «Правило источников» и §§1.1/3.1) —
    но НИКТО формально не сверял, что сумма по `sale_dt` (order-based) за
    календарный месяц близка к сумме по `rr_dt` (event-based) за тот же
    месяц, если не считать эту фикс-волну. Проверено на июле 2026, кабинет
    1, `saas_ro`, 2026-08-20: revenue расходится на 0,5% (796 215,76 vs
    800 471,21 ₽), НО logistics — на 26,6% (57 208,38 vs 77 926,36 ₽; 479
    строк `wb_order_costs` против 723 строк «Логистика» в
    `wb_finance_report` за тот же календарный месяц). Величина расхождения
    logistics достаточно большая, чтобы стоило явно спросить владельца,
    устраивает ли его учёт «по дате продажи» как определение «расходы за
    июль» (см. «Открытые вопросы владельцу», новый пункт) — сейчас панель
    показывает его молча, без объяснения на UI.

11. **Канон Ozon больше не фильтрует `is_return` при выборе базовых сумм
    (revenue/commission/logistics/acquiring/loyalty) — задокументированное
    изменение формулы, не побочный эффект, но заметный числовой сдвиг.**
    См. §1.5 — было `is_return=0` (валовая, без возвратов), стало без
    фильтра (нетто-эффект возвратов встроен). Revenue: 478 333 ₽
    (2026-08-10, старая формула) → 508 259,00 ₽ (2026-08-20, канон);
    commission: 221 912,58 ₽ → 235 977,80 ₽. Если кому-то нужна именно
    валовая «сумма отгруженного без возвратов» отдельно — такого поля на
    панели больше нет ни на одной странице.

## Открытые вопросы владельцу

Здесь — не ошибки, а места, где код делает содержательный выбор, который
контракт фиксирует «как есть», потому что альтернатива не очевидно лучше и
решение не наше.

1. **Себестоимость «на дату продажи» (WB) vs «на момент последнего сбора»
   (Ozon) — ЧАСТИЧНО ЗАКРЫТО задачами 4-5, но переоткрылось в новой форме.**
   До 2026-08-20 разница была межстраничной ВНУТРИ WB (`/pnl`/`overview`
   считали исторически, `products-summary`/`rnp-summary` — «на сегодня», см.
   §7). Задача 5 убрала эту межстраничную разницу — теперь ВСЕ семь
   потребителей канона обеих площадок берут `cogs` из одного места
   (`order_costs.cost`). Но методика самого сборщика различается ПО
   ПЛОЩАДКЕ: WB считает исторически (по `sale_dt` заказа,
   `worker/collectors/wb_order_costs.py:79-87`), Ozon — «на момент своего
   последнего запуска» (`effective_from <= current_date` в момент сбора,
   `worker/collectors/ozon_order_costs.py:648-652`), НЕ по дате продажи.
   Витринная колонка `unitCost` на `products-summary`/`rnp-summary`
   (справочная, не влияет на `profit`) — отдельная третья формула
   (`current_date` на момент запроса к API панели, §7). Что из этого
   правильно для Ozon (историческая себестоимость или «на момент сбора») —
   вопрос политики учёта, не техники.

2. ~~`plan/fact` использует плановую себестоимость (`cost_plan`) как
   аппроксимацию фактической.~~ **ЗАКРЫТО задачей 5.** `plan/fact` теперь
   берёт факт-`cogs` из канона (`f.cogs`, §7, §11.1) —
   `plan/fact/route.js:206-213`, комментарий прямо фиксирует цель «факт-COGS»
   вместо прежней аппроксимации `cost_plan × qtyFact`. Плановые колонки
   (`cost_plan` для ПЛАНА, не факта) не тронуты — это не то же самое поле.

3. **Хранение и реклама Ozon по SKU не разносятся вообще** (как и хранение
   WB) — показываются только кабинетным итогом. Для WB это осознанное
   решение (контракт №27, размазывание исказит маржу товара). Для Ozon
   рекламы по SKU физически нет в источнике (Performance API отдаёт только
   «кабинет × день»). Разное происхождение одного и того же ограничения —
   стоит ли объяснять это пользователю по-разному на UI, решает владелец.

4. **`unit/all` использует фиксированную ставку рекламы 10% вместо
   фактического расхода** (`lib/unit.js:104,256` — «решение #14»). Это
   модельный инструмент, а не измерение факта (раздел 11.4) — вопрос в том,
   насколько это очевидно продавцу на экране, который выглядит как «расчёт
   по вашим товарам».

5. **Новый вопрос этой фикс-волны: учёт «по дате продажи» (WB-канон) vs
   «по дате проводки строки» (прямой `wb_finance_report`) даёт разные суммы
   за один календарный месяц** — см. «Известные расхождения», пункт 10.
   Расхождение достаточно большое для логистики (26,6% на июле 2026, кабинет
   1), чтобы владельцу стоило явно подтвердить: учёт по дате продажи
   (нынешнее поведение канона) — то, что он хочет видеть как «расходы за
   месяц», а не побочный эффект технического решения 2026-07-29 (сборщик
   перестал терять `srid` с продажей вне периода, но заодно поменял
   date-семантику агрегатов для ВСЕХ потребителей канона, не только для
   исходно затронутых заказов).
