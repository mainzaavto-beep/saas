(`.superpowers/sdd/2026-08-11-ozon-accrual-migration/`). Цель — понять,
сходится ли новый источник (`POST /v1/finance/accrual/by-day`, методы

## 1. Как сняты данные

Разовый скрипт `.superpowers/sdd/2026-08-11-ozon-accrual-migration/fetch_accrual.py`
(во временном каталоге, в репозиторий не входит):

- Креды кабинета 1 читаются так же, как их читает оркестратор:
  `worker.orchestrator._read_one_cabinet(1)` → `_env_for_shop(shop)` для
  shop с `mp_code == "ozon"` (`shop_id=2`). `_env_for_shop` возвращает
  кортеж `(env, mp)`; `OZON_CLIENT_ID`/`OZON_API_KEY` берутся из `env`.
- `os.environ["NO_PROXY"] = "*"` выставлен в начале скрипта и
  дополнительно `proxies={"http": None, "https": None}` передан в каждый
  `requests.post` — иначе запрос виснет за прокси.
- Два запроса, оба только на чтение:
  1. `POST https://api-seller.ozon.ru/v1/finance/accrual/by-day`,
     тело `{"date": "2026-08-05"}` → HTTP 200, 79 записей в `accruals`,
     `last_id` пуст (первая и единственная страница).
  2. `POST https://api-seller.ozon.ru/v1/finance/accrual/types`, тело `{}`
     → HTTP 200, 119 типов операций в справочнике.
- Между запросами пауза `time.sleep(1.2)` (ограничение — не быстрее 1
  запроса в секунду, проба показала `code 8` на третьем запросе подряд).

Оба ответа сохранены как есть в файлы фикстур, указанные выше.

## 4. Объяснение разницы до рубля

**Наивный расчёт из брифа не сходится не потому, что в источниках разные
деньги, а потому что он суммирует не ту колонку.**

Наивная формула: `68 851,00 − 25 213,19 − 7 492,73 = 36 145,08`.
`7 492,73` — это `sum(services_amount)`, а в `services_amount` **пять из
одиннадцати** типов операций (`Оплата за клик`, `Продвижение с оплатой за
заказ`, `Ускоренный сбор отзывов`, `Страхование товара от массовых
повреждений`, `Услуга размещения товаров на складе`) хранят `NULL`, а не
0. Строки в таблице **есть** (это не пропавшая категория), но их сумма
не попадает в `sum(services_amount)`, потому что `NULL` игнорируется
`sum()`. Их реальная сумма лежит в `payout_amount`:
`−2 452,36 − 1 490,98 − 305,00 − 252,96 − 0,28 = −4 501,58 ₽`.

Проверка: `36 145,08 − 4 501,58 = 31 643,50` — ровно `total_amount`
нового источника. Совпадает до копейки.

Более прямой путь к тому же результату — не переизобретать сумму из трёх
колонок, а использовать четвёртую, уже готовую: **`sum(payout_amount)` по
всем 79 строкам старой таблицы = 31 643,50 ₽, что дословно равно
`sum(total_amount)` по всем 79 записям нового ответа.** Совпадение не
только по итогу, но и **по каждой из 11 групп `operation_type_name`
отдельно** (см. таблицу §3 и разбор по `type_id` в §2 — построчная сверка
ниже).

Ответы на прямые вопросы брифа:

- **Какие величины нового источника соответствуют каким величинам
  старого?**
  - `accruals_for_sale` (старое, Σ = 68 851,00) ≡ `posting.commission.
    seller_price` ≡ `posting.commission.sale_amount` (новое, Σ = 68 851,00,
    дублирующие поля одного значения). Тождество для каждой из 29 записей:
    `seller_price = sale_price + bonus + coinvestment` (проверено
    программно, 0 расхождений).
  - `commission_amount` (старое, хранится положительным, Σ = 25 213,19) ≡
    `posting.commission.sale_commission` ≡ `posting.commission.commission`
    (новое, хранится со знаком, Σ = −25 213,19). Величина та же, знак —
    соглашение хранения (старое вычитает явно, новое уже занесло знак).
  - `services_amount` (старое, NULL для 5 из 11 типов) ≡ сумма
    `accrued.amount` по `type_id` из `item_fees` / `posting.delivery.
    services` (новое) для операций с известной разбивкой по товару/
    отправлению.
  - `payout_amount` (старое, заполнено всегда) ≡ `total_amount` (новое,
    заполнено всегда) — это два обозначения одной и той же итоговой
    величины по операции. Именно эту пару стоит сверять в задаче 5, а не
    воспроизводить `accruals_for_sale − commission_amount −
    services_amount`.
- **Входит ли комиссия в `total_amount`?** Да. Для всех 37 записей
  категории POSTING формула `total_amount = posting.products[].delivery.
  total_accrued + sale_price + sale_commission + coinvestment + bonus`
  сходится без единого расхождения (скрипт `verify_formula.py`,
  37 проверено / 0 несовпадений). Комиссия (`sale_commission`) уже
  вычтена внутри `total_amount`, отдельно вычитать её ещё раз (как в
  наивной формуле брифа) — двойной учёт был бы ошибкой, если бы не то,
  что наивная формула и без того не использует `total_amount` напрямую.
- **Попадают ли в новый источник категории, которых нет в старом (и
  наоборот)?** Нет ни в одну, ни в другую сторону — на этот день. Все 79
  записей нового `accrual/by-day` находят ровно одну группу
  `operation_type_name` в старой таблице (11 групп, построчно сверено по
  сумме и количеству записей — см. §2/§3, каждая строка совпала). Обратное
  тоже верно: лишних `operation_type_name` в старой таблице, не нашедших
  соответствия в новых `type_id`/категориях, нет. `NON_ITEM`-операции
  (реклама, продвижение, отзывы, страхование, размещение) в старой
  таблице **присутствуют** как строки — миф о том, что старый источник их
  «не видит», не подтвердился; он их не суммирует в одну конкретную
  колонку (`services_amount`), но хранит и учитывает их в `payout_amount`.
  Роли `возврат` (`Получение возврата, отмены, невыкупа от покупателя`) и
  `доход от доставки` (`Перечисление за доставку от покупателя`) из
  `worker/collectors/ozon_order_costs.py` в данных за 2026-08-05 кабинет 1
  не встретились ни в одном источнике — не фабрикую для них соответствие
  кодов, см. §5.
- **Совпадают ли границы суток?** Да — `operation_dt` старой таблицы для
  всех строк этого дня буквально `2026-08-05 00:00:00` (суточный ярлык, не
  реальное время операции), что соответствует суточной гранулярности
  параметра `date` нового метода. Итоговые суммы сошлись до копейки, что
  дополнительно подтверждает отсутствие сдвига по часовому поясу для
  этого дня.

**Побочная находка, важная для дальнейших задач плана:** сегодняшний
расчёт прибыли по заказу (`worker/collectors/ozon_order_costs.py`)
разбирает только 3 из 11 встретившихся `operation_type_name`
(`Доставка покупателю`, `Доставка и обработка возврата...`, `Оплата
эквайринга` — плюс ещё 2 в коде, `Получение возврата...` и `Перечисление
за доставку...`, не встретившиеся в этот день). Остальные 5 типов на
4 501,58 ₽ (`NON_ITEM`: реклама/продвижение/отзывы/страхование/
размещение) и 3 типа на 3 751,00 ₽ (`ITEM`: `Сбор первых отзывов`,
упаковка, материалы для упаковки) сегодня **не входят ни в один бакет
прибыли** — падают через `if/elif`-цепочку без действия. Это не предмет
задачи 1 (документ только объясняет расхождение источников, не чинит
расчёт прибыли), но релевантно для задач 3/5 и для дальнейшего аудита
прибыли (см. память `saas-audit-2026-08.md`: «прибыль в 6 местах»).

### 7.2 Разбор единственного расхождения (логистика возврата / продажа)

Роли `продажа` и `логистика возврата` не сошлись каждая по отдельности —
на **одну и ту же сумму 835,00 ₽** с противоположным знаком (продажа
занижена, логистика возврата настолько же завышена по модулю). Сумма
обеих ролей вместе, и тем более итог по всем ролям — не меняется:
расхождение это не потеря денег, а спор о том, в какую роль их положить.

**Механизм.** Роль строки логистики (`type_id` 32/29/98) в новом
источнике определяется присутствием в том же `accrual_id` блока
`commission` с положительной суммой (эвристика §5: «есть продающий блок
→логистика этого постинга — тоже продажа»). Но у отправлений с **нулевой
стоимостью товара** (`accruals_for_sale = commission_amount = 0` в старой
таблице — сам товар в отправлении ничего не стоит, платится только
доставка) новый источник блок `commission` вовсе не создаёт: там нечего
показывать (0 = 0 = 0). Эвристика не может отличить такое отправление от
настоящего возврата (там блока `commission` тоже нет) — и логистика
нулевого отправления по ошибке попадает в «логистика возврата».

**Проверено на конкретных постингах.** На июле 2026 кабинет 1 это ровно 4
постинга (все — «Доставка покупателю» в старой таблице, все с нулевым
товаром):

| posting_id | дата | payout_amount (старое) |
|---|---|---:|
| 0164952163-0080-2 | 2026-07-28 | −279,00 |
| 0164952163-0080-5 | 2026-07-28 | −279,00 |
| 0165040053-0033-1 | 2026-07-10 | −130,00 |
| 43725192-0180-1 | 2026-07-16 | −147,00 |

Сумма их логистики в новом источнике (`type_id` 32/98 каждого постинга) —
ровно **−835,00 ₽**, что в точности равно наблюдаемой разнице.

**Независимая проверка на втором кабинете.** Тот же прогон на кабинете
1008 (июль 2026) даёт **тот же паттерн** — расхождение только в
«продажа»/«логистика возврата», на этот раз 99,00 ₽, и тот же механизм:
ровно один постинг с нулевым товаром (`62089307-0168-1`, 2026-07-19,
`payout_amount = −99,00`, `accruals_for_sale = commission_amount = 0`).
Все остальные роли, включая возврат и доход от доставки (§5, обновление
задачи 5), совпали точно. Совпадение механизма на независимом наборе
данных — веский аргумент, что это системная особенность эвристики, а не
случайность одного месяца.

**Вывод**: расхождение объяснено полностью, до постинга и до рубля — это
известное ограничение эвристики «блок `commission` → продажа» на редких
отправлениях с нулевой стоимостью товара, а не потеря или задвоение
денег. Чинить эвристику (учитывать нулевые отправления отдельно) —
отдельная, необязательная доработка: она не влияет ни на итог, ни на
доверие к остальным пяти ролям, поэтому в рамках задачи 5 оставлена как
задокументированная особенность, а не исправлена вслепую.

### 7.4 Проверки

- **Идемпотентность.** Скрипт прогнан дважды подряд на одних параметрах —
  вывод побайтово идентичен (сверено `md5sum`). Ожидаемо: скрипт только

- **Покрытие периода.** Прогон на январе 2026 (кабинет 1, вне покрытия
  старого источника) печатает явное предупреждение о недостоверности и

  ненулевым кодом (расхождения формально есть), чтобы не создать
  ложно-зелёный статус: спрятать недостоверность за успешным exit code
  было бы хуже, чем громко показать её.
- **Второй кабинет.** Кабинет 1008, июль 2026 — тот же результат
  (см. §7.2): единственное расхождение того же типа и того же
  происхождения, всё остальное сходится точно.
- **Провал активности кабинета 1, январь–апрель 2026, неверифицируем
  внутри БД.** Старый источник (`tenant.ozon_finance_report`) начинается

  сверки, только новый источник (`tenant.ozon_accruals`, покрывает год
  назад от заморозки). Совпадение или расхождение чисел за этот период
  этим скриптом не проверить в обе стороны — единственная внешняя
  проверка (не через нашу БД) — выгрузка отчёта из личного кабинета
  Ozon за те же месяцы.

разобраны, не регресс.** После подмены и фикса I4 Check 1 (инвариант
периода) дал **5 красных строк на 4 неделях** (кабинет 1 — все 4 недели,

недель»: `tenant.ozon_order_costs` хранит ОДНУ строку на юнит, привязанную
к ОДНОЙ дате (дате первой операции), а начисления того же юнита физически
могут прийти в ДРУГИЕ календарные недели (корректировки, сторно,
доначисления логистики через дни/недели после продажи). Проверка 1
сторожа вычитала только «исходящую» утечку (`other_period` — деньги ЭТОЙ
недели, чья строка датирована ДРУГОЙ), но не симметричную «входящую»
(деньги ДРУГИХ недель, упакованные в строку, датированную ЭТОЙ) — для
каждой из 5 красных строк независимый расчёт «входящей утечки» СОВПАДАЛ
с остатком сторожа до копейки.

Это был **ДЕФЕКТ ОЖИДАНИЯ ПЛАНА, не регресс и не новый баг**: задача 4
предыдущего прохода предполагала, что полный пересчёт истории юнита
уберёт эту утечку — не подтвердилось, утечка — структурное свойство
модели «одна агрегирующая строка = одна дата», а не следствие неполноты
окна сборки (согласованность компонент внутри каждой строки сегодня
`= 0,00 ₽` везде — это задача 5/6 действительно починила). Независимое
доказательство: кабинет 1008, неделя 2026-08-10..16, остаток **43,49 ₽**
— ДОСЛОВНО то же число, что было зафиксировано ДО задач 5-6, — полный
пересчёт его не сдвинул ни на копейку, что и ожидаемо: пересчёт не
меняет, на какую календарную дату начисление физически легло в Ozon.

**Симметричная поправка — сторож зелёный, упаковочные потоки видимы
отдельными строками.** По решению владельца реализован вариант 2 (не
вариант 1 «просто принять как есть»): Check 1 теперь вычитает ОБА
направления утечки — «исходящую» (`other_period`/`no_row`/`null_date`,
как раньше) И «входящую» (НОВАЯ CTE `inbound_units`/`inbound` в
`check-ozon-profit-invariant.mjs` — зеркальный запрос: сумма `accrued`
начислений юнитов, чья `order_costs`-строка датирована ПРОВЕРЯЕМОЙ
неделей, но сами начисления датированы ВНЕ её). Обе суммы печатаются в
выводе **ВСЕГДА** (не только при красной строке — защита от самообмана,
рост любой категории виден глазами, требование контроллера). Порог
допуска 1 ₽ (`INVARIANT_TOL_RUB`) НЕ менялся. Check 2 (доля
«неразнесено») сознательно НЕ трогали — он проверяет только исходящую
сумму, это независимая проверка со своим порогом/калибровкой, задача
контроллера её не касалась.

**Результат — все 4 недели, оба кабинета, все три проверки зелёные,
`ALL PASS`, exit 0.** Входящие суммы в выводе совпали с независимо
пересчитанными числами разбора выше **точно, до копейки**: 2026-07-20..26
кабинет 1 −490,06 ₽; 2026-07-27..08-02 кабинет 1 −9 819,68 ₽; 2026-08-03..09
кабинет 1 −10 015,03 ₽; 2026-08-10..16 кабинет 1 −13 643,24 ₽ и кабинет
1008 +43,49 ₽ — все пять остатков после вычета ОБЕИХ утечек: 0,00 ₽ (или
−0,00 ₽, тот же ноль с плавающей точкой). Обещание спеки компонента 6
«Check 1-2 зелёные по всем 4 неделям» — **выполнено**, но не как
предполагалось изначально (полным пересчётом истории юнита), а
дополнительной симметричной поправкой сторожа, потребовавшейся именно
потому, что полный пересчёт истории юнита СОЗДАЛ упаковочный эффект
(агрегация в одну строку), а не устранил его.

**Скользящее окно и идемпотентность**: следующий штатный слот

сторожа без новых записей между вызовами; полноценная проверка (тик

после этой правки.

## 11. Уточнение датировки: порог зрелости и склейка сиблингов (2026-08-18, round 3/4)

Продолжение §10: владелец нашёл реальный дефект правила «датируем min(date)
для юнита без commission-блока» (§10, компонент 2) — **преждевременная
датировка СВЕЖИХ юнитов**. 350 строк августа кабинета 1 показывали
«продажу» с нулевой выручкой и `profit = −логистика−cost`, хотя товар
физически ещё в пути/только доставлен, Ozon его не финализировал (статусы
`delivering/delivered/cancelled`) — панель показывала фантомный убыток
там, где раньше строка была просто невидима.

**Лаг-факты (владелец ждал число) — перепроверены контролёром:**

| Метрика | Значение |
|---|---:|
| Юнитов кабинета 1 с продажей (commission-блок есть) | 8 529 |
| Лаг «первая операция юнита → приход commission-блока», p50 | 0 дней |
| Лаг, p90 | 0 дней |
| Лаг, p99 | 0 дней |
| Лаг, max | 1 день |

**Вывод из фактов**: когда commission-блок вообще приходит, он приходит
**день-в-день** с первой строкой юнита практически всегда. Значит, порог
«подождать несколько дней, вдруг commission ещё придёт» — неверная модель
проблемы. Настоящая причина 350 строк оказалась ДРУГОЙ: **232 из 350 (по
перепроверке контролёра) на самом деле УЖЕ имеют продажу в начислениях —
просто под СОСЕДНЕЙ формой сырого `unit_number`** (логистика под базовой
формой `0115022887-0449`, commission под суффиксной `0115022887-0449-5` —
ОДНО реальное отправление, Ozon репортит его по частям под двумя разными
строками в `tenant.ozon_accruals`). Прежняя группировка «по unit_number
буквально» делила такое отправление на два юнита: с деньгами, но без
commission (фантомный убыток) — и с commission, но без части денег.

**Решение (заменило первоначальную идею «порог 7-21 день»):**

1. **Склейка сиблингов при группировке** (`worker/collectors/
   ozon_order_costs.py::merge_unit_siblings`/`_family_key`, чистые функции
   без БД, покрыты тестами) — ДО `resolve_meta`/`build_order_costs`: строки
   базовой и суффиксной формы одного «семейства» (`_family_key` — 2-частная
   форма «префикс-заказ», у 3-частной срезается суффикс товара) сливаются в
   ОДНУ группу, когда РОВНО ОДИН член семьи несёт commission-блок —
   симметрично (canonical — любой член семьи с commission, не важно, base
   он или suffix). 2+ члена семьи с commission (настоящее мультитоварное
   отправление) — НЕОДНОЗНАЧНО, не склеивается, юниты обрабатываются
   раздельно как раньше (счётчик + лог). ⚠️ Найдена и исправлена ловушка
   при разработке: слепое «срезать последний дефис всегда» (как в уже
   существующем `order_meta_by_base`, чьи входы гарантированно 3-частные)
   ошибочно схлопнуло бы РАЗНЫЕ отправления с общим числовым префиксом
   (живой пример: `0229108520-0830` и `0229108520-0831` — два разных
   заказа) — `_family_key` срезает только когда дефисов ≥2.
2. **Порог зрелости уменьшен до 3 дней** (`MATURITY_THRESHOLD_DAYS`,
   p99 лага (0) + буфер на выходные/технические сдвиги) — применяется
   ТОЛЬКО к юнитам, у которых И нет commission-блока, И нет однозначного
   брата для склейки (истинно нерезолвленные, ~118 из 350 по оценке
   контролёра). Младше порога — строка вообще НЕ ПИШЕТСЯ (не просто
   недатирована — раньше в задаче 3/§10 недатированные строки всё же
   попадали в БД без даты; теперь для по-настоящему свежих юнитов строки
   нет вовсе, их деньги видны сторожу через категорию `no_row`, посчитаны
   в собственном логе сборщика отдельной строкой). Старше порога — как и
   раньше, датируется `min(date)` («настоящий сервисный/отменённый факт»).
3. **/orders, pending-ветка** (`app/api/cabinets/[id]/orders/route.js`,
   `collectOzon`): `profit = 0` вместо `-cost*qty` для заказов без строки
   `order_costs` — прямое продуктовое решение владельца («ни убыток, ни
   прибыль, нули»). Товар в пути/только доставлен теперь ВИДЕН в панели со
   статусом (`Доставляется`/`Отменён`/…) и нулевыми финансами, а не
   пропадает молча и не показывает фантомные числа.

**Эффект — намного шире, чем ожидалось.** Склейка сиблингов оказалась НЕ
локальной находкой августа, а массовым явлением по ВСЕЙ истории: из 14 902
сырых `unit_number` кабинета 1 **10 318 (69%) состоят в парах base/suffix**
одного реального отправления (обычный способ, которым Ozon разбивает
ITEM-эквайринг vs POSTING-commission по разным строкам API); после склейки
боевая `tenant.ozon_order_costs` кабинета 1 сократилась до **9 915 строк**
(было 14 902 — консолидация, не потеря денег, см. проверку ниже), кабинета

### 13.2 Механизм (два независимых случая, оба подтверждены без остатка)

`build_order_costs` строит `cost_value_retail = seller_price`,
`commission = −sale_commission` из commission-блока (`POSTING`,
`type_id IS NULL`) отправления — и НЕЯВНО предполагает, что вклад этого
блока в `SUM(accrued)` равен ровно `seller_price + sale_commission`
(= `cost_value_retail − commission`). Но фактический `accrued` строки
commission-блока — это (проверено на живых строках, точное тождество)

```
accrued = sale_price + sale_commission + coinvestment + bonus
```

Формула `comps` совпадает со `SUM(accrued)` ТОЛЬКО когда держится тождество

```
seller_price = sale_price + coinvestment + bonus
```

Это тождество и раньше упоминалось в этом документе (§2, footnote¹:
«проверено программно, 0 расхождений») — но верифицировано оно было на
ОДНОДНЕВНОЙ выборке (29 записей, 2026-08-05, кабинет 1). На всей истории
(14 147 «сырых» `unit_number` с commission-блоком, оба кабинета — точный
запрос по `tenant.ozon_accruals`) оно **не держится ровно у 45 из этих 60
строк** (0,318% = 45/14 147) — это и есть источник расхождения случая А
ниже (доли — по количеству `unit_number`, не по количеству строк
`order_costs`, т.к. один `posting_number` может нести 2+ commission-строк
на мультитоварных отправлениях, см. пример 3 ниже). Спот-проверка (8
случайных commission-строк, не входящих в 60) — тождество держится с
нулевым разрывом на каждой (см. §13.3). Разбивка 60 строк подтверждена
классификатором `is_return` (объясняет все 60 без остатка, см. проверку
ниже):

**Случай А — НЕ возврат, `is_return=0` (45 из 60).** Тождество ломается в
самих числах Ozon (не в нашем коде): `signed_diff = seller_price −
sale_price − coinvestment − bonus` (сумма по всем commission-строкам
отправления, если их несколько — мультитоварное отправление). Природа
разрыва в доступных полях не идентифицируется однозначно (`type_id`
commission-блока у ВСЕХ этих строк — обычный `NULL`, неотличим по коду
операции от нормальной продажи); по характеру чисел (стабильный
`seller_price`, ощутимые `bonus`/`coinvestment`) похоже на промо-схему с не
полностью отражённым в этих 4 полях софинансированием скидки — не
фабрикуем точное название механики без доказательства.

**Случай Б — возврат с ненулевым commission-блоком, `is_return=1`
(15 из 60).** `build_order_costs` СОЗНАТЕЛЬНО обнуляет `cost_value_retail`
для ЛЮБОГО возврата (`0.0 if is_return else seller_price` — продуктовое
решение: колонка «стоимость заказа» не должна показывать цену товара на
возврате). Но у возвратов, чей commission-блок несёт полноценные
(ненулевые) `seller_price`/`sale_price`/... (развёрнутая продажа, не голая
логистика возврата), это обнуление вычёркивает `seller_price` из `comps`
целиком, хотя `accrued` этой же строки его по-прежнему несёт (через
тождество случая А, которое у ВСЕХ 15 этих строк ДЕРЖИТСЯ — возвратный
commission-блок внутренне согласован). Итог: `signed_diff = −seller_price`
(сумма по commission-строкам). Это на 100% наше собственное,
ПРЕДНАМЕРЕННОЕ решение (продуктовая семантика отображения), а не аномалия
Ozon.

**Проверка без остатка.** Обе формулы (случай А и Б) сведены в один SQL,
применены ко всем 60 строкам — `unexplained_rows = 0` (допуск 0,02 ₽ на
двойное округление): расхождение объяснено ДО КОПЕЙКИ на каждой из 60
строк, не только в среднем.

### 13.4 `profit` не затронут ни разу

`profit = round(SUM(accrued) − cost, 2)` строится ПРЯМО из суммы всех строк
начислений отправления — не через `comps`. На всех 60 строках `profit +
COALESCE(cost,0)` совпадает с независимо пересчитанным `SUM(accrued)` (не
считая двойного округления ≤0,02 ₽, пример 4) — `profit` верен на каждой из
60 строк без исключения, тем же способом, каким он верен на остальных
≈17 800. Расхождение задевает ТОЛЬКО пять денежных КОМПОНЕНТ
(`cost_value_retail`/`commission`/`logistics`/`acquiring`/`loyalty`) —
удобную для отображения раскладку, а не итог.

**Кому это видно.** `profit`-колонку читают не все потребители — несколько
роутов панели складывают компоненты САМИ, а не читают готовый `profit`:
`app/api/cabinets/[id]/overview/route.js` (`k.revenue − k.commission −
k.acquiring − k.logistics − k.loyalty − ...`), `products-summary/route.js`,
`rnp-summary/route.js`, `plan/fact/route.js`, `unit/route.js`. На ЭТИХ 60
отправлениях их собственный пересчёт разойдётся с истинной прибылью ровно
на печатаемую сумму (до 8 073 ₽ на одну строку в кабинете 1008); на
АГРЕГАТАХ (сумма за месяц/период) эффект размывается — 70 909,40 ₽ по
модулю (35 545,40 ₽ знаковых) на фоне ≈22,2 млн ₽ накопленной прибыли
кабинета 1008 за всю историю (≈0,32%), не материально для сводных цифр, но
материально для КОНКРЕТНОГО отправления, если открыть его карточку/
детализацию.
Унификация формул (переход этих роутов на `oc.profit`) — вне периметра
этого плана (см. «Что НЕ входит» спеки компонента 4).

### 13.6 Ложная тревога первичной сверки (исправлено ре-ревью 2026-08-19)

Первичный черновик этого раздела заявлял «доп. находку»: у 50 из 60 строк
независимый пересчёт `SUM(accrued)` по `tenant.ozon_accruals` якобы
расходится с уже записанным `profit` на Σ 1 911,23 ₽ (пример:
`04358022-0232-2`, «пропавшая» строка эквайринга `type_id=1`). **Это была
ложная тревога методологии, не находка в данных** — сверка шла ПРОСТЫМ
`GROUP BY unit_number`, без учёта склейки сиблингов (`merge_unit_siblings`/
`_family_key`, §11): та самая строка эквайринга оказалась НА МЕСТЕ, просто
записана под БАЗОВОЙ формой семьи (`04358022-0232`, без суффикса `-2`,
дата 2025-09-03), на 7 дней раньше суффиксной формы с commission-блоком
(`04358022-0232-2`, дата 2025-09-10) — та же семья, ровно тот случай, для
которого `merge_unit_siblings` и существует (§11). Наивный `unit_number =
src_unit_number` эту вторую строку семьи не видит.

**Family-aware пересверка** (переиспользован боевой код, НЕ переизобретён
в SQL — ревью справедливо указало, что SQL-агрегация по `unit_number`
задваивает/теряет неоднозначные семьи): скрипт напрямую импортирует
`worker/collectors/ozon_order_costs.py::merge_unit_siblings`/`_family_key`,
строит `by_unit` из ТЕКУЩЕГО `tenant.ozon_accruals` (весь кабинет, как в
проде), прогоняет `merge_unit_siblings`, для каждой из 60 строк находит
итоговую (склеенную либо самостоятельную) группу по `src_unit_number` и
сравнивает Σ`accrued` группы с сохранённым `profit + COALESCE(cost,0)`.

**Результат: 0 расхождений из 60** (было заявлено 50 при наивной
SQL-агрегации). Вся видимость «пропажи» строк — исключительно артефакт
метода сверки, не свойство данных: `tenant.ozon_order_costs` полностью
согласован с ТЕКУЩИМ состоянием `tenant.ozon_accruals` на всех 60 строках,
никакой утечки или устаревания нет. Эскалация контролёру не требуется —
раздел удалён из числа находок; урок для будущих сверок этого документа —
любое сопоставление `order_costs` ↔ `ozon_accruals` ОБЯЗАНО идти через
`_family_key`/`merge_unit_siblings` (или их прямой импорт), а не через
голый `unit_number`, иначе неоднозначные/склеенные семьи дают ложные
«пропажи». Вердикт §13.5 не меняется — он и раньше опирался только на
самосогласованность УЖЕ ЗАПИСАННЫХ значений (§13.2-13.3), не на сверку с
исходной таблицей.
