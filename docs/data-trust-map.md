# Карта доверия к данным

Отвечает на два вопроса будущей сессии: что не нужно перепроверять — и, что
важнее, **что нельзя считать проверенным**, даже если оно годами выглядит
правильно. Заполняется честно: если участка нет в таблице, по умолчанию он
не выверен, а не «наверное, всё в порядке».

## Что означает статус «выверен»

**Выверен = есть эталон (числа из официального отчёта маркетплейса,
`reference/*/expected.json`) И сверка `scripts/check-reference.mjs` по нему
зелёная (код выхода 0).** Ничего меньшего этим статусом не считается:

- «внутренне непротиворечиво» (две наши таблицы совпали друг с другом) —
  это не выверено, это самосогласованность. Обе таблицы могут одинаково
  ошибаться.
- «выглядит правдоподобно» / «продавец не жаловался» — не выверено.
- «формула проверена на одном заказе вручную» — не выверено как метрика
  периода, хотя это полезный аргумент в пользу правильности формулы.
- «сходится с другой нашей же страницей» — не выверено, а иногда и вовсе
  ошибка методологии (см. правило по финансам в `AGENTS.md`: расхождение
  цифр — наш баг, пока не доказано обратное; но и *совпадение* без внешнего
  эталона ничего не доказывает).

Сегодня (2026-08-10) `reference/2026-07-cabinet-1/expected.json` заполнен
`null`-ами — владелец ещё не перенёс числа из официальных отчётов. Пока это
так, `scripts/check-reference.mjs reference/2026-07-cabinet-1` для любого
участка отдаёт код **2** («эталон не заполнен») — не 0 и не провал, а
отсутствие ответа. Формально **ни один участок сегодня не имеет статуса
«выверен» по строгому определению выше** — строка «Расходы кабинета WB»
ниже помечена «выверен» по более раннему, ручному сопоставлению с отчётом
(до появления `reference/`), и это оговорено отдельно.

## Известный пробел: слой расчёта не сверяется

`scripts/check-reference.mjs` сверяет только **слой данных** — то, что лежит
в таблицах `tenant.*`, с официальным отчётом маркетплейса. Он не сверяет
**слой расчёта** — то, что страница показывает продавцу поверх этих данных
(формулы прибыли, налога, маржи). Это сознательный, а не забытый пробел:
сегодня формулы прибыли живут инлайн внутри обработчиков страниц
(`app/api/cabinets/[id]/**/route.js`), а не в общих модулях
(`calcOperatingProfit` из `lib/wbMetrics.js` даже импортирована, но нигде не
вызывается — см. `docs/metrics-contract.md`, «Известные расхождения», п. 8).
Проверить слой расчёта сегодня можно было бы только подняв HTTP-запросы с
сессией владельца — то есть построив хрупкую обвязку вокруг кода, который
всё равно предстоит переносить в общий расчёт при унификации прибыли.

Правильный порядок: сначала унификация формул прибыли (отдельная работа),
потом сверка страниц — она станет тривиальной (один вызов общей функции на
эталонных входных данных). До этого момента строка «Прибыль» в таблице выше
остаётся «не выверена», и `scripts/check-reference.mjs` эту дыру не
закрывает и не может закрыть по конструкции.

## Как этим пользоваться

- Строка «выверен» — можно опираться на число без дополнительной проверки,
  но помните об оговорке в строке про расходы кабинета WB (формальной сверки
  через `reference/` ещё не было).
- Строка «выверен частично» — исправление внесено и внутренне
  непротиворечиво, но внешнего эталона нет; расхождение с официальным
  отчётом маркетплейса всё ещё возможно и не будет поймано автоматически,
  пока `reference/*/expected.json` не заполнен.
- Строка «не выверена» — не аргумент в споре с продавцом и не основание для
  вывода фичи из беты. Для строк с пометкой «дефект» — число нельзя
  использовать вообще, не только «не проверено».
- Общее правило: `AGENTS.md`, раздел «Правила работы с кодом» → «Красная
  сверка с эталоном — запрет на деплой».
