## 1. Разбор документов и определение кабинета

### 1.1 Структура документа

Каждый файл — один лист «Отчет о реализации», структура одинаковая во всех 4 файлах:
- Шапка (строки 3–10): номер и дата отчёта, период `«Реализация товаров за период с DD.MM по DD.MM.2026»`,
  плательщик (ООО «Интернет Решения», ИНН 7704217370 — это Ozon), получатель (ИНН **120705330412**,
  имя то «Матвеев Денис Валерьевич, ИП», то «ИП Матвеев Денис Валерьевич» — один и тот же продавец во всех 4 файлах).
- Таблица товарных строк (с строки 16): колонки `F` = «Реализовано на сумму, руб.», `G` = «Выплаты по механикам
  лояльности партнёров, руб.» (к реализации), `H`/`I` = кол-во/цена, `J` = «Возвращено на сумму, руб.»,
  `K` = «Выплаты по механикам лояльности партнёров, руб.» (к возврату), `L`/`M` = кол-во/цена возврата.
- Строка итогов по колонкам (`sum(F)`, `sum(G)`, `sum(J)`, `sum(K)`) сразу после последней товарной строки.
- Печатные итоги: **«Итого реализовано (за вычетом возвратов), руб.»** = `sum(F) − sum(J)` и
  **«Всего выплат от партнёров, руб.»** = `sum(G) − sum(K)` — оба сверены программно, сходятся с построчной суммой
  без исключений (см. таблицу §1.3).

**Важное уточнение периметра (расходится с исходной гипотезой брифа).** Бриф предполагал, что «Отчёт о
реализации» покрывает «продажи/возвраты и комиссию». Это **не так для данного документа**: во всех 4 файлах
нет ни одной колонки, строки или упоминания комиссии, вознаграждения Ozon, логистики, услуг или рекламы —
проверено полнотекстовым сканом всех непустых ячеек всех 4 файлов на ключевые слова `комис`, `услуг`,
`вознагр`, `тариф`. Документ показывает только: (а) сумму, реально реализованную покупателю по каждой
товарной позиции (уже за вычетом любых скидок, профинансированных самим продавцом), и (б) отдельно —
компенсацию продавцу от Ozon за участие в механиках лояльности (софинансирование скидок Ozon). Комиссия,
логистика, реклама, размещение, эквайринг и т.п. в этот документ **не входят вовсе**, не только частично.
Это не баг парсинга — это и есть весь периметр документа `«Отчет о реализации товара»` для данного продавца/
режима налогообложения (см. §1.2): он предназначен для учёта выручки (`usn_income` — упрощёнка «доходы»,
где комиссия — отдельный расход, не уменьшающий признаваемую выручку), а не для полного финансового
урегулирования. Полное урегулирование (с комиссией и услугами) — другой документ Ozon («Отчёт комиссионера»),
владельцем не выгружался и в задачу не входил.

### 1.2 Определение кабинета

Идентификация по двум независимым основаниям:

**(1) Совпадение имени/ИНН получателя с кабинетом в БД.** `auth.cabinets.cabinet_id = 1` имеет

## 2. Периметр сравнения из `tenant.ozon_accruals`

Реализация в новом источнике живёт в блоке `commission` категории `POSTING` (`accrued_category = 'POSTING'`,
`type_id IS NULL`) — это структурная запись «продающего»/«возвратного» отправления
(`docs/ozon-accrual-reconciliation.md`, §2/§4/§5). Внутри неё:

- `accrued > 0` — продажа отправления, `accrued < 0` — возврат отправления (тот же блок, знак меняется;
  подтверждено в `docs/ozon-accrual-reconciliation.md` §5, обновление задачи 5).
- `seller_price = sale_price + coinvestment + bonus` — тождество без исключений (проверялось ранее на
  других выборках; здесь пересверено не потребовалось, использовано как данность).

**Гипотеза и её проверка методом исключения.** Опробованы два варианта соответствия документа полям БД:

1. `F` («Реализовано на сумму») ≡ `seller_price`, `G` («Выплаты лояльности») ≡ `coinvestment + bonus` —
   **не сошлось**: для апреля `seller_price_pos` = 12 176,00 ₽ против документа `F` = 6 848,63 ₽ (разница
   почти вдвое, `bonus` в БД оказался лишним — это компенсация Ozon за собственные промо-скидки покупателю,
   в документ вообще не попадающая).
2. `F` ≡ `sale_price`, `G` ≡ `coinvestment` (без `bonus`) — **сошлось точно на всех 4 месяцах**, см. §3.

Это и есть периметр сравнения:

```sql
-- «Реализовано» / «Возвращено» (документ F/J)
SELECT to_char(date_trunc('month', date), 'YYYY-MM') AS month,
       round( sum(sale_price) FILTER (WHERE accrued > 0)::numeric, 2) AS db_realizovano,
       round(-sum(sale_price) FILTER (WHERE accrued < 0)::numeric, 2) AS db_vozvrat
FROM tenant.ozon_accruals
WHERE cabinet_id = 1 AND accrued_category = 'POSTING' AND type_id IS NULL
  AND date BETWEEN :from AND :to
GROUP BY 1 ORDER BY 1;

-- «Выплаты по механикам лояльности партнёров» (документ G/K)
SELECT to_char(date_trunc('month', date), 'YYYY-MM') AS month,
       round( sum(coinvestment) FILTER (WHERE accrued > 0)::numeric, 2) AS db_loyalty_sale,
       round(-sum(coinvestment) FILTER (WHERE accrued < 0)::numeric, 2) AS db_loyalty_return
FROM tenant.ozon_accruals
WHERE cabinet_id = 1 AND accrued_category = 'POSTING' AND type_id IS NULL
  AND date BETWEEN :from AND :to
GROUP BY 1 ORDER BY 1;
```

Границы месяца — календарные (`date BETWEEN 'YYYY-MM-01' AND 'YYYY-MM-DD'`), по полю `date` таблицы
`tenant.ozon_accruals` (суточная метка операции начисления). Расхождений по границам месяца не обнаружено —
см. §3, точное совпадение на всех 4 месяцах, включая стыки.

**`bonus` и `sale_commission` — вне периметра документа.** `bonus` (софинансирование Ozon крупных промо-скидок
покупателю, суммы существенно больше `coinvestment`) и `sale_commission` (комиссия Ozon) в документ не входят
ни в каком виде — это подтверждает и объясняет уточнение периметра из §1.1 на уровне отдельных полей, а не
только на уровне «в документе нет такой колонки».

**Число строк документа vs БД не совпадает — это ожидаемо, не расхождение денег.** Документ группирует
несколько отправлений с одинаковыми SKU и одинаковой ценой в одну строку (видно по колонке `H`, «Кол-во» > 1
в исходных файлах); `tenant.ozon_accruals` хранит одну строку на отправление. Например, июль: 192 строки
документа против 391+18 = 409 продающих/возвратных строк в БД — при этом суммы (см. §3) совпадают до копейки.

## 5. Старый источник (`tenant.ozon_finance_report`): информационная сверка май-июль

Старый источник начинается с `2026-05-01` (апрель недоступен вовсе — известное и задокументированное
ограничение, не новая находка). У него нет колонок `sale_price`/`coinvestment` — только `accruals_for_sale`
(≡ `seller_price` нового источника, самостоятельно доказанное тождество в
`docs/ozon-accrual-reconciliation.md`) и `commission_amount`. Поэтому сравнивать его напрямую с документом
(`F`/`J`, то есть `sale_price`) нельзя — это заведомо другая величина (`seller_price` больше `sale_price` на
сумму `coinvestment + bonus`, см. §2). Использован как **кросс-проверка между собой двух наших источников**,
не как третья точка сверки с документом.

```sql
SELECT substr(operation_dt,1,7) AS month, operation_type_name, count(*),
       round(sum(accruals_for_sale)::numeric,2) accr_sale
FROM tenant.ozon_finance_report
WHERE cabinet_id=1 AND substr(operation_dt,1,10) BETWEEN '2026-05-01' AND '2026-07-31'
  AND operation_type_name IN ('Доставка покупателю','Получение возврата, отмены, невыкупа от покупателя')
GROUP BY 1,2 ORDER BY 1,2;
```

| июнь | Получение возврата... | −35 600,00 | −35 600,00 | 0,00 |

источник насчитывает 69 продающих отправлений за май против 81 в новом — 12 отправлений отсутствуют. Разбор
по датам показывает, что старый источник просто **недобирает данные на самой границе своего окна покрытия**
(оно официально начинается 2026-05-01): например, за 28–30 апреля новый источник видит 8 продающих
отправлений на 3 841,00 ₽ (даты, которые старый источник не видит вовсе — не входят в его окно), а 1–2 мая
у старого источника всего 2 записи (по 595,00 ₽ каждая) против 5 записей в новом на 1 601,00 ₽ за те же дни —
похоже на неполный первый день/двое суток сбора старого источника, а не на смещение денег. Это **не
расхождение с документом** (документ и новый источник сходятся ровно, см. §3) — это ограничение старого,
уже выводимого из эксплуатации источника, зафиксировано как открытая, не блокирующая находка.

## 6. Воспроизведение

Разбор документов:

```bash
/opt/agents/data-presenter-agent/.venv/bin/python scripts/parse-ozon-realization-reports.py
```

(скрипт открывает все 4 xlsx через `openpyxl`, ищет товарные строки по целому числу в колонке `A`,
суммирует `F/G/J/K`, сверяет с печатными «Итого реализовано»/«Всего выплат от партнёров»)

SQL-запросы к БД (`saas_ro`, `PGPASSFILE=/root/.pgpass`, хост `localhost`, база `saas`) — все приведены
внутри соответствующих разделов выше (§1.2, §2, §4, §5), выполнялись через `psql`.

Идентификация кабинета (негативный контроль, кабинет 1008):

```sql
SELECT to_char(date_trunc('month', date), 'YYYY-MM') AS month,
       round(sum(sale_price) FILTER (WHERE accrued > 0)::numeric, 2) AS sale_price_pos
FROM tenant.ozon_accruals
WHERE cabinet_id = 1008 AND accrued_category='POSTING' AND type_id IS NULL
  AND date BETWEEN '2026-04-01' AND '2026-07-31'
GROUP BY 1 ORDER BY 1;
-- 2026-04: 1 444 689,54 / 2026-05: 1 068 927,45 / 2026-06: 909 542,07 / 2026-07: 559 812,45
-- на порядок больше документа — подтверждает, что документ НЕ про кабинет 1008.
```

## 7. Итоговый статус

- **Реализовано/возвращено** (`F`/`J` документа) — сходится с `tenant.ozon_accruals` (`sale_price`) **до
  копейки на всех 4 месяцах**, включая апрель.
- **Выплаты по механикам лояльности** (`G`/`K` документа) — сходится с `tenant.ozon_accruals`
  (`coinvestment`) **до копейки на всех 4 месяцах**.
- **Комиссия, логистика, реклама, услуги** — в документ не входят вовсе (уточнение периметра, не баг).
- **Апрель** — провал активности подтверждён независимо документом Ozon, это не недобор данных сборщиком.
- **Единственная незакрытая, но объяснённая находка**: старый источник (`tenant.ozon_finance_report`,
  выводится из эксплуатации) занижает май на 1 299,00 ₽ из-за неполного покрытия первых дней своего окна —
  не влияет на сверку документ↔новый источник, которая сошлась точно.
- Необъяснённых расхождений (когда бы наш источник числа не сошёлся с документом без причины) — **не
  обнаружено**.
