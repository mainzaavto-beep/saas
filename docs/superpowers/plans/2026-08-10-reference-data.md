# Эталонные данные и контракт метрик — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Зафиксировать, что считается правильным, так, чтобы это держалось само — без опоры на память сессии.

**Architecture:** Эталон — файл в репозитории с числами из официальных отчётов маркетплейса и доказательством их происхождения. Контракт метрик — единственное место, где написано, что означает каждая величина. Сверка-сторож — скрипт, который считает наши цифры за эталонный период и сравнивает с эталоном; красная сверка запрещает деплой. Карта доверия — что выверено, а что нет.

**Tech Stack:** Node (встроенный `fetch` не нужен, сеть не используется), PostgreSQL через `pg` под ролью `saas_ro` (только чтение), существующие смоук-скрипты как образец стиля.

## Global Constraints

- Весь текст отчётов и документов — по-русски, обращение на «вы».
- Никаких новых зависимостей: только то, что уже есть в `package.json`.
- Сверка читает боевую БД **только** под ролью `saas_ro` (`psql -h localhost -U saas_ro -d saas`); админские креды (`PGPASSFILE=/root/.pgpass-admin`) ей не нужны и использоваться не должны — сторож не имеет права менять то, что проверяет.
- `next dev` в этом каталоге запускать категорически нельзя — затирает боевую сборку.
- Эталонный период: **WB — недельные отчёты о реализации, целиком попавшие в июль 2026; Ozon — календарный июль 2026**. Кабинет 1.
- Правило продукта, которое нельзя нарушать: сводка по товарам стоит на дневных данных, отчёт о прибыли (`/pnl`) — на недельных отчётах о реализации. Различие их цифр — не баг.
- Допуск сверки: расхождение значимо, если превышает **одновременно** 1 ₽ и 0,5% от эталонной величины.
- Подгонять эталон под текущий результат панели запрещено. Эталон меняется только вместе с новой выгрузкой и записью в `SOURCES.md`.

Создать `lib/reference.js`:

```js
// lib/reference.js — чтение эталона и сравнение с допуском.
//
// Эталон — числа из официальных отчётов маркетплейса. Он существует, чтобы ловить
// расхождения, поэтому модуль намеренно строгий: незаполненная величина — это
// ошибка, а не ноль. Молчаливый ноль превратил бы сверку в вечнозелёную.
import { readFileSync } from 'node:fs';

// Расхождение значимо, только если превышены ОБА порога: и рубль, и полпроцента.
// Один порог без другого делает сверку либо шумной на копейках, либо слепой на
// мелких величинах.
const TOL_RUB = 1;
const TOL_PCT = 0.5;

export function compare(expected, actual) {
  const e = Number(expected);
  const a = Number(actual);
  const diffRub = a - e;
  const diffPct = e === 0 ? (a === 0 ? 0 : 100) : (diffRub / e) * 100;
  const ok = Math.abs(diffRub) <= TOL_RUB || Math.abs(diffPct) <= TOL_PCT;
  return { ok, diffRub, diffPct };
}

export function loadReference(dir) {
  const path = `${dir.replace(/\/$/, '')}/expected.json`;
  let raw;
  try {
    raw = readFileSync(path, 'utf8');
  } catch (e) {
    throw new Error(`эталон не читается (${path}): ${e.message}`);
  }
  const ref = JSON.parse(raw);
  const missing = [];
  for (const mp of ['wb', 'ozon']) {
    const block = ref[mp];
    if (!block) continue;
    for (const [k, v] of Object.entries(block.values || {})) {
      if (v === null || v === undefined) missing.push(`${mp}.${k}`);
    }
    for (const p of block.periods || []) {
      if (!p.date_from || !p.date_to) missing.push(`${mp}.periods`);
    }
  }
  if (missing.length) {
    throw new Error(
      `эталон не заполнен: ${missing.join(', ')}.\n`
      + `Числа берутся из официальных отчётов маркетплейса — см. ${dir}/SOURCES.md.`
    );
  }
  return ref;
}
```

- [ ] **Шаг 1: Написать сверку**

`scripts/check-reference.mjs`:

- подключается к БД под `saas_ro` (хост `localhost`, база `saas`, пароль из `~/.pgpass`; **не** использовать `adminPgConfig` из `scripts/lib/pgpass.mjs` — сторожу не нужны права на запись);

- печатает **все** расхождения, а не падает на первом;
- в конце — строка `ALL PASS` либо `N РАСХОЖДЕНИЙ`.

Точные имена колонок брать из БД (`\d tenant.wb_finance_report`, `\d tenant.ozon_finance_report`), а не по памяти.

## Сознательно отложено

**Слой расчёта (страница против ожидаемого) не входит в этот план.** Спека
описывает его как вторую половину сверки, но сегодня формулы прибыли живут внутри
обработчиков страниц, а не в общих модулях: проверить их можно было бы только
поднимая HTTP-запросы с сессией владельца, то есть строя хрупкую обвязку вокруг
кода, который всё равно предстоит переносить в общий расчёт при унификации прибыли.
Правильный порядок — сначала унификация (отдельная работа), затем сверка страниц,
которая станет тривиальной. Это записать в `docs/data-trust-map.md` как известный
пробел, а не умолчать.
