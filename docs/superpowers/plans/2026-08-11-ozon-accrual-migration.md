# Переезд финансов Ozon на методы начислений — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Собирать финансы Ozon новыми методами начислений — с разбивкой по товарам и устойчивыми идентификаторами — и доказать сверкой, что новые цифры сопоставимы со старыми.

**Architecture:** Новый сборщик пишет в собственные таблицы (строки начислений + справочник типов), не трогая существующую `ozon_finance_report`. Старый сбор продолжает работать: он остаётся источником для панели и базой для сверки. Переключение расчёта прибыли в этот план не входит — оно решается владельцем по результатам сверки.

**Tech Stack:** Python-воркер (`worker/collectors/`), PostgreSQL с RLS, `requests`, существующие механизмы оркестратора (окружение магазина, журнал прогонов).

## Global Constraints

- Сбор идёт **только на чтение** внешнего API: никаких запросов, меняющих что-либо на стороне Ozon.
- Частота: **не быстрее одного запроса в секунду** — проба показала отказ `code 8` на третьем запросе подряд. Заголовков с лимитами Ozon не отдаёт, поэтому пауза задаётся явно.
- Прокси отключается: `os.environ["NO_PROXY"] = "*"` в точке входа сборщика — иначе запрос уходит через прокси окружения и виснет (проверено).
- Время записи — только с часовым поясом: `datetime.now(timezone.utc)`. В проекте только что чинили сдвиг на три часа, не воспроизводить.
- Миграции идемпотентны (`IF NOT EXISTS`), нумерация — следующая свободная в `db/migrations/`. Для каждой новой таблицы схемы `tenant` **обязательна политика RLS** по образцу соседних (`tenant.ozon_daily_ad`), иначе данные будут видны между кабинетами.
- **Незнакомый код типа операции никогда не выбрасывается молча** — попадает в роль «прочее» и логируется. В этом же воркере ошибка глоталась пустым перехватом больше года.
- Существующий сборщик `ozon_finance` и таблица `ozon_finance_report` в этом плане **не изменяются**.
- Тексты логов и документов — по-русски.
- БД читать под `saas_ro`; миграции применять `PGPASSFILE=/root/.pgpass-admin psql -h localhost -U postgres -d saas -f <файл>`.

- [ ] **Шаг 1: Написать миграцию**

`tenant.ozon_accruals` — одна строка на строку начисления:

```sql
CREATE TABLE IF NOT EXISTS tenant.ozon_accruals (
  cabinet_id      bigint NOT NULL,
  accrual_id      bigint NOT NULL,
  line_no         integer NOT NULL,      -- порядковый номер строки внутри начисления
  date            date NOT NULL,
  unit_number     text,                  -- номер отправления; NULL для расходов уровня кабинета
  accrued_category text NOT NULL,        -- ITEM | POSTING | NON_ITEM
  type_id         integer,
  sku             bigint,
  quantity        integer,
  accrued         double precision,      -- сумма строки
  seller_price    double precision,      -- далее — только для категории POSTING
  sale_price      double precision,
  sale_commission double precision,
  coinvestment    double precision,
  bonus           double precision,
  updated_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (cabinet_id, accrual_id, line_no)
);
```

Индекс под выборки по периоду и отправлению:

```sql
CREATE INDEX IF NOT EXISTS ozon_accruals_date_idx ON tenant.ozon_accruals (cabinet_id, date);
CREATE INDEX IF NOT EXISTS ozon_accruals_unit_idx ON tenant.ozon_accruals (cabinet_id, unit_number);
```

`shared.ozon_accrual_types` — справочник, общий для всех кабинетов:

```sql
CREATE TABLE IF NOT EXISTS shared.ozon_accrual_types (
  type_id     integer PRIMARY KEY,
  name        text,
  description text,
  updated_at  timestamptz NOT NULL DEFAULT now()
);
```

## Что в этот план НЕ входит

**Переключение расчёта прибыли на новый источник.** Спека ставит его шестым шагом, но
он зависит от результата сверки: если выяснится, что источники считают разное по
смыслу, правильным решением будет не «заменить», а «пересчитать прибыль по новой
модели» — с осознанным изменением исторических цифр. Это решение владельца, и
принимать его нужно, глядя на таблицу из задачи 5, а не заранее.

Туда же уходят: обновление контракта метрик и карты доверия под новую модель,
возвращение Ozon в сверку с эталоном, отключение старого сборщика. Всё это —
следующий план, после решения владельца.
