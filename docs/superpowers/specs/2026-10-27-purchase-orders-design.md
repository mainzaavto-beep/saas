# Закупки: заказ → позиции → отправки (спека, 27.10.2026)

## 0. Зачем

Сейчас строка «Закупок» (`tenant.purchases`) = одна позиция со своей предоплатой, курсом и логистикой.
В жизни один заказ у поставщика содержит много моделей/артикулов/размеров, оплачивается общими
платежами и приезжает частями (разными отправками карго). Заказ угадывается только косвенно
(одинаковые поставщик/дата/курс/логистика у строк 42–45 каб. #1), `order_no` почти пуст, а платежи
в календаре дробятся по позициям.

Решения владельца (27.10.2026):
- у заказа общие оплаты и логистика; у позиции — товар, кол-во, цена ¥;
- товар позиции — артикул WB/Ozon из каталога **или** свободный текст;
- логистика делится по весу, без веса — по штукам;
- заказ приезжает частями, одна позиция может разделиться между отправками;
- себестоимость — на **отправленные** штуки; недостача при приёмке на остальные не раскидывается,
  показывается отдельной строкой;
- себестоимость в `cost_overrides` автоматически не пишется (ставится на `/items`);
- старые партии (`tenant.purchases`) — архив «до 16.10», только чтение, не конвертируются.

## 1. Данные — миграция 075 (идемпотентна)

Все таблицы в `tenant.*`, PK `(cabinet_id, id)`, FK внутри кабинета, RLS `tenant_iso_<t>` для
`saas_app` + `panel_local_ro_cab1`, гранты — по образцу 069.

### `purchase_orders` — шапка
`order_no TEXT`, `supplier TEXT`, `supplier_contact TEXT`, `source_country TEXT`, `category TEXT`,
`note TEXT`, `order_dt DATE`, `rate_cny NUMERIC(12,4)` (плановый курс ¥→₽),
`status TEXT CHECK IN ('draft','ordered','production','shipping','closed')` default `'draft'`,
`archived_at TIMESTAMPTZ` (закрыт), `deleted_at TIMESTAMPTZ`, `created_at`, `updated_at`.

### `purchase_order_payments` — оплаты (0..N на заказ)
`order_id`, `kind TEXT CHECK IN ('prepay','balance','other')`, `currency TEXT CHECK IN ('cny','rub')`
default `'cny'`, `amount NUMERIC(14,2) > 0`, `rate NUMERIC(12,4)` (обязателен при `cny`, курс этой
оплаты), `plan_date DATE`, `note`, `deleted_at`, `created_at`.
- `prepay`/`balance` — оплата товара поставщику (всегда `cny`).
- `other` — доставка по Китаю и прочие расходы заказа (¥ или ₽).

### `purchase_order_lines` — позиции
`order_id`, `platform TEXT CHECK IN ('wb','ozon')`, `nm_id BIGINT`, `product_id BIGINT`,
`label TEXT NOT NULL` (непустой; при выборе артикула — имя карточки), `variant TEXT` (размер/цвет),
`qty INTEGER > 0`, `price_cny NUMERIC(12,4) >= 0`, `weight_kg NUMERIC(10,4)` (NULL = не указан, иначе > 0),
`photo_url TEXT`, `note`, `deleted_at`, `created_at`, `updated_at`.
CHECK на артикул — как в `purchase_receipt_lines` (wb ⇒ только nm_id, ozon ⇒ только product_id,
NULL ⇒ ни того ни другого).

### `purchase_shipments` — отправки
`order_id`, `shipment_no TEXT` (трек/номер карго), `carrier TEXT`, `ship_dt DATE`, `eta DATE`,
`arrived_dt DATE`, `status TEXT CHECK IN ('transit','arrived','accepted')` default `'transit'`,
`cargo_rub NUMERIC(14,2) >= 0` (до МСК), `ff_rub NUMERIC(14,2) >= 0` (МСК→ФФ),
`accepted_at TIMESTAMPTZ`, `accepted_by BIGINT`, `note`, `deleted_at`, `created_at`, `updated_at`.

### `purchase_shipment_lines` — что в отправке
`shipment_id`, `line_id`, `qty_shipped INTEGER > 0`, `qty_accepted INTEGER >= 0` (NULL до приёмки),
UNIQUE `(cabinet_id, shipment_id, line_id)`.
Гард (в API, под `SELECT … FOR UPDATE` позиции): Σ `qty_shipped` по живым отправкам позиции ≤
`line.qty`; уменьшить `line.qty` ниже уже отправленного — 400.

Старое: `tenant.purchases`, `purchase_receipt_lines`, платежи `source_ref='purchase:<id>:…'` не
трогаются. Новые строки в `purchases` не создаются (POST создания в старом роуте → 410 с подсказкой).

## 2. Расчёт — `lib/purchaseOrders.js` (чистые функции, без БД)

`calcOrder({ order, payments, lines, shipments, shipmentLines })` → итоги заказа и по каждой позиции.
Округление — только на выходе.

1. **Сумма заказа ¥** `T = Σ lines (qty × price_cny)`.
2. **Эфф. курс** по оплатам товара (`prepay`/`balance`):
   `P¥ = Σ amount`, `P₽ = Σ amount × rate`;
   если `P¥ ≤ T`: `rate_eff = (P₽ + (T − P¥) × order.rate_cny) / T`;
   если `P¥ > T`: `rate_eff = P₽ / P¥` + предупреждение «оплачено больше суммы заказа».
   `T = 0` → `rate_eff = order.rate_cny`. Статус оплаты в ДДС на курс не влияет.
3. **Товар ₽/шт** позиции = `price_cny × rate_eff`.
4. **Прочие расходы заказа** (`other`: `cny` × rate, `rub` как есть) → раскидываются на все позиции
   заказа по базе (п. 5) с количеством `qty` позиции; ₽/шт = доля / `qty`.
5. **База раскидки** для набора строк: `qty × weight_kg`, если вес указан у **всех** строк набора;
   иначе `qty`. Σ баз = 0 → ничего не раскидываем, предупреждение.
6. **Логистика отправки** `L = cargo_rub + ff_rub` делится между её строками по базе (п. 5, кол-во =
   `qty_shipped`). Доля строки = `L × база / Σ баз`.
7. **Логистика позиции ₽/шт** = Σ долей по живым отправкам / Σ `qty_shipped`. Не отправлено ничего →
   `null` («логистика ещё не известна»).
8. **Себестоимость ₽/шт** = товар + прочие + логистика (при `null` логистике — с пометкой «без
   логистики»). Считается на **отправленные** штуки.
9. **Недостача** позиции = Σ по принятым отправкам `(qty_shipped − qty_accepted)` при > 0;
   сумма = недостача × себестоимость/шт. Только показ, на себестоимость не влияет.
   Излишек (`qty_accepted > qty_shipped`) — показ «излишек N шт», без влияния.

Инвариант (тест и смоук): для полностью отправленного заказа
`Σ_lines (себестоимость/шт × qty) = T × rate_eff + Σ other₽ + Σ L` до копейки (до округления).

Пример (тест): камера 70 × 150 ¥, 0,3 кг + бельё 200 × 12,5 ¥, 0,1 кг → T = 13 000 ¥. Предоплата
4 000 ¥ × 11,46, план 11,90 → `rate_eff = (45 840 + 9 000 × 11,90) / 13 000 ≈ 11,7646`; товар камеры
≈ 1 764,69 ₽/шт. Отправка 1: 40 камер (12 кг) + 200 белья (20 кг), L = 16 000 ₽ → камерам 6 000 ₽,
белью 10 000 ₽. Отправка 2: 30 камер, L = 5 000 ₽. Логистика камеры = 11 000 / 70 ≈ 157,14 ₽/шт,
белья 50 ₽/шт. Доставка по Китаю 300 ¥ × 11,5 = 3 450 ₽ (вид `other`) по весу всего заказа
(21 кг : 20 кг) → камере ≈ 25,24 ₽/шт, белью ≈ 8,41 ₽/шт.

Отклонение от §3 при плане: один роут `purchase-orders/route.js`, заказ — `GET ?id=N` (без
вложенного динамического сегмента).

## 3. API — `app/api/cabinets/[id]/purchase-orders/route.js` (+ `[orderId]/route.js`)

- `GET /purchase-orders?status=&supplier=&category=&closed=1` — список с агрегатами (позиций, шт,
  сумма ¥/₽, оплачено ¥, отправлено/принято шт, статус).
- `GET /purchase-orders/[orderId]` — заказ целиком + результат `calcOrder` + статусы строк ДДС оплат.
- `POST /purchase-orders` `{action}`: `create`; `update` (шапка); `delete` (мягко, вместе с
  оплатами/отправками, плановые строки ДДС → архив); `line_add|line_update|line_delete|line_copy`;
  `pay_add|pay_update|pay_delete`; `ship_add` (по умолчанию — все неотправленные остатки),
  `ship_update|ship_delete|ship_arrived`.
- Любое действие, меняющее оплаты/отправки/шапку, в той же транзакции вызывает
  `syncOrderPayments(orderId)`.
- Роли: запись — `manager`/`owner`, чтение — все участники (как старые закупки).
- Поиск артикула для позиции — существующий источник каталога (`wb_articles`/`ozon_products`), без
  нового SQL-слоя, если подходящий эндпоинт уже есть (выяснить при плане).
- Action-блоки без id — до проверки id (грабля D10).

## 4. Экраны

**`/fin-purchases`** — список заказов: № · поставщик · дата · позиций/шт · сумма ¥ и ₽ · оплачено
(X из Y ¥, полоска) · отправлено/принято · статус; фильтры поставщик/статус/категория/«закрытые»;
«+ Заказ». Вкладка «Архив до 16.10» — прежняя таблица партий, только чтение.

**`/fin-purchases/[orderId]`** — карточка (алиас «Закупки» в `lib/cabinetNav.js`, гард
`cabinetNav.test.mjs`):
1. Шапка + итоги (сумма ¥/₽, эфф. курс, оплачено, средняя себестоимость, недостача).
2. Позиции: товар (поиск артикула с фото или текст), вариант, кол-во, цена ¥, вес, сумма ¥,
   себестоимость ₽/шт с расшифровкой (товар/прочие/логистика), отправлено/принято; «⧉ ещё размер».
3. Оплаты: вид, сумма, валюта, курс, плановая дата, статус из ДДС (только чтение);
   «осталось оплатить N ¥».
4. Отправки: трек, перевозчик, даты, `cargo_rub`/`ff_rub` (помощник «$/кг × вес × курс $» —
   формула карго из `lib/costCalc.js`), строки «позиция → шт», «✓ Прибыла».

## 5. Стыковка

- **`/deliveries`**: новые карточки = отправки `arrived` (поставщик, № заказа, трек). Приёмка —
  `qty_accepted` по строкам (предзаполнено `qty_shipped`); позиции без артикула можно привязать
  артикул (пишется в позицию заказа). «Учтено» → `accepted`, `accepted_at/by`. Снять — только owner.
  Заказ → `closed` (+`archived_at`), когда всё отправлено и все отправки приняты. Конечная точка:
  `ff_inventory`, `stock_moves`, `cost_overrides` не пишутся. Старые партии — прежний поток.
- **Календарь/ДДС**: `syncOrderPayments(orderId)` в `lib/paymentCalendarData.js` (единственное место
  записи `dds_movements`). Оплата → `source_kind='purchase'`, `source_ref='order:<id>:pay:<pid>'`,
  ₽ = amount × rate (или ₽), статья «Поставщик» (`other` — «Карго»/прочее по виду, уточнить в плане),
  дата `plan_date` (нет — `order_dt`). Отправка → `order:<id>:ship:<sid>:cargo|ff`, статья «Карго»,
  дата `arrived_dt` → `eta` → `ship_dt`. Оплаченные и `date_locked` строки не перезаписываются;
  исчезнувшие источники → плановые строки в архив. `editRules`: у новых строк — как у `purchase`.
- **«Баланс», товар в пути** (`lib/purchasesInTransit.js`): + отправки `transit` —
  Σ `qty_shipped × себестоимость/шт`; старые партии — прежняя логика.
- **Не трогаем**: `/purchase-need` (подавать ли заказанное — открытый вопрос владельца),
  `/cost-calc` (остаётся прикидкой), `cost_overrides`.
