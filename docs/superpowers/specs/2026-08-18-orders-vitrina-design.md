# Витрина заказов: размораживание статусов и добивка — дизайн

Дата: 2026-08-18. Статус: одобрено владельцем (брейншторм в сессии).

## Зачем

Финальное ревью ремонта данных оставило очередь по витрине заказов:
(1) статусы `tenant.ozon_orders` замерзают навсегда — `/v3/posting/fbo/list`
фильтрует по дате СОЗДАНИЯ отправления, а плановый прогон ходит узким окном
«−2..сегодня»: заказ старше двух дней больше никогда не переспрашивается
(497 строк с in-transit статусом при давно завершённой продаже; механизм
подтверждён ре-ревью чтением кода и `updated_at`, замёрзшим на месяц);
(2) WB-заказы «в пути» показывают минус-себестоимость — владелец распространил
правило нулей с Ozon на WB; (3) `NOT EXISTS`-хрупкость /orders при NULL
`product_id`; (4) 60 отправлений с расхождением компонент при верном profit —
не разобраны.

## Решения владельца (зафиксированы)

1. Состав: только витрина (статусы + WB-нули + guard + разбор 60) — без подмен
   истории прибыли, без унификации формул, без курсора.
2. WB «в пути» = нули (ни прибыли, ни убытка) — как Ozon.
3. Шлюз дельты не требуется: прибыль этим планом не меняется.

## Компоненты

### 1. Размораживание статусов ozon_orders

`worker/collectors/ozon_orders.py`: lookback-пол 45 дней с концом «сегодня»
(паттерн `resolve_window` из `ozon_accruals.py`; для заказов конец окна —
сегодня, а не вчера: статус сегодняшнего заказа тоже нужен). Каждый плановый
прогон переспрашивает все отправления, созданные за 45 дней, и идемпотентно
освежает `status`/`cancel_dt`/`updated_at`. 45 дней покрывает жизненный цикл
доставки с запасом; пагинация — с паузой ≥1 с между страницами (лимиты Ozon).

Разовый бэкфилл: прогон за 90 дней назад — добивает все 497 замёрзших строк
(created начиная с июля). Строки старше 90 дней не трогаются (их статусы
финальны по возрасту; проверить выборкой, что среди них нет in-transit — если
есть, расширить бэкфилл до их min(created)).

Приёмка: строк «`ozon_order_costs.sale_dt` заполнен И commission есть И
`ozon_orders.status` in-transit» → ~0 (допустимы только заказы, реально
завершившиеся сегодня-вчера); `/orders` перестаёт показывать «Доставляется»
у завершённых.

### 2. WB-нули для «в пути»

`app/api/cabinets/[id]/orders/route.js`, WB pending-ветка: `profit = 0`
вместо `-COALESCE(co.cost,0)` (зеркально Ozon-фиксу). Билд + рестарт по
протоколу. Компоненты и так нули; строка «Итого» перестаёт занижаться на
себестоимость недоставленных.

### 3. Guard от дублей NOT EXISTS

Оба NOT EXISTS в /orders (Ozon-ветка): сравнение `product_id` через
`IS NOT DISTINCT FROM` (NULL считается совпадением), чтобы будущие строки
без товара не порождали дубль заказа в ленте. Синтетическая проверка SQL-ем
на живой БД (сегодня пересечений 0 — регресс-щит на будущее).

### 4. Разбор 60 аномальных отправлений

Задача-расследование по образцу прошлых разборов: у 60 отправлений
(31 каб.1 + 29 каб.1008) компонентная формула расходится с `SUM(accrued)`
больше чем на 0,01 (profit при этом верен — считается из суммы). Деливерабл —
объяснение механизма до рубля на 3-5 примерах: баг разбора → чинить;
свойство данных Ozon (например, типы вне известных корзин у POSTING со
спец-полями) → задокументировать в `docs/ozon-accrual-reconciliation.md` и
добавить в сторож видимую строку-счётчик класса (без порога, если класс
стабилен; с порогом — если растёт). Замолчать нельзя.

## Что НЕ входит

Подмены/пересборки прибыли (order_costs не трогается вовсе, кроме как
опосредованно пунктом 4, если найдётся баг разбора — тогда отдельное решение
контролёра с оценкой влияния); унификация формул; курсор `last_id`;
403-паттерн (наблюдение); ротация мастер-ключа (ждёт владельца).

## Ограничения (наследуются)

API Ozon — только чтение, ≥1 с между запросами, NO_PROXY; `datetime.now(timezone.utc)`;
БД читать `saas_ro`, писать сборщиками; тексты по-русски; правило: расхождение
цифр = наш баг, пока не доказано обратное; правки сборщиков = мгновенный
деплой (учитывать в порядке шагов); сторож должен остаться ALL PASS 8/8 после
всех правок.
