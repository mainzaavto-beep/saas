# Канон прибыли, волна 2: batch + последние не-канонические формулы — дизайн

Дата: 2026-08-23. Статус: очередь финального ревью унификации (2026-08-20),
владелец: «поехали дальше». Пять пунктов очереди подтверждены разведкой по
живому коду (дословных формулировок в старых доках нет — основание = код).

## Зачем

1. **N+1 до крупных каталогов**: products-summary и rnp-summary зовут
   `ozProfitProduct`/`wbProfitProduct` циклом по товарам — 2 SQL на товар
   (кабинет 1008: ≈456 SQL на загрузку страницы при 220 товарах; каталог
   в 2000 позиций даст ~4000 запросов и секундные страницы).
2. **«Одна цифра везде» ещё не везде**: (а) lossMakers-виджет Обзора —
   собственная формула прибыли SKU на построчной finance_report-базе, вне
   канона, с молчаливым выбросом SKU без себестоимости; (б) дневные ряды
   detail строятся на другой базе, чем итог той же таблицы (день —
   finance_report/приближение «rev−gross≈расходы», итог — канон): сумма
   дней структурно ≠ итогу.
3. Дубли: формула profitGross скопирована трижды (products-summary,
   detail, pnl); `total.cabinetCosts` склеивает статьи WB и Ozon без
   метки площадки (различимы только эвристикой по label).

## Компоненты

### 1. Batch-канон (ядро)

В `lib/ozonMetrics.js`/`lib/wbMetrics.js`:
- `ozRawProfitAggregateBatch(db, {from, to}) -> Map<productId, agg>` —
  тот же SQL, что скалярный, но `GROUP BY product_id` (WB — по nm_id);
  скалярная версия остаётся (detail/plan-fact зовут по одному).
- `ozProfitProductBatch(db, taxMode, period) -> Map<productId, форма
  ozProfitProduct>` — композиция: aggregate-batch + `ozAdSpend(
  groupByProduct)` (уже существует) + `calcTotalTax` в цикле (чистая
  функция, без SQL). Симметрично WB.
- Инвариант: `ozProfitProductBatch(...).get(id)` ПОКОМПОНЕНТНО равен
  `ozProfitProduct(..., id)` — прямой тест в `check-profit-canon.mjs`
  (новая проверка №6: на живых данных сравнить batch с 5 случайными
  скалярными вызовами до копейки, обе площадки).
- Роуты products-summary и rnp-summary переходят на batch (циклы
  остаются для сборки строк, но канон-вызов один на площадку).
  Ожидание: число SQL на страницу перестаёт зависеть от N.

### 2. profitGross — поле канона

`ozProfitProduct`/`wbProfitProduct`/(batch) возвращают дополнительно
`profitGross` (revenue − cogs − commission − logistics − acquiring −
loyalty; для WB — его ppvz-аналог, как в текущих дублях). Три дубля
формулы в роутах заменяются полем. Числа НЕ меняются (формула та же —
проверка: profit-snapshot --verify Δ=0).

### 3. Метка площадки в cabinetCosts

`pnl/route.js`: элементы `cabinetCosts` получают поле `platform:
'wb'|'ozon'` (в mpBlock оно известно); `total.cabinetCosts` — тот же
склеенный массив, но различимый. UI пока НЕ меняем (поле аддитивно,
фронт его игнорирует) — потребитель появится по мере надобности.

### 4. lossMakers на канон

Виджет Обзора переезжает на `wbProfitProductBatch` за свой период
(30 дней): топ-5 по отрицательному canonical profit. Изменения
поведения (задокументировать в комментарии и показать владельцу при
приёмке): (а) база прибыли = канон (ppvz), не построчный forPay-расчёт;
(б) SKU без себестоимости больше НЕ выбрасываются молча — канон считает
их прибыль без COGS (завышенной), поэтому таким строкам добавляется
флаг `costMissing: true` и пометка в UI виджета («без себеса»), чтобы
не врать. Ozon-ветка виджета — если виджет WB-only, остаётся WB-only
(расширение площадок не в этой волне).

### 5. Дневные ряды detail на базе канона

Дневные ряды обеих площадок переводятся с finance_report/приближений на
`GROUP BY день` по той же базе, что канон (`wb_order_costs`/
`ozon_order_costs`): новые хелперы `ozRawProfitByDay`/`wbRawProfitByDay`
(форма aggregate, группировка по дню, для одного товара). Прибыль дня =
дневной rawProfit − дневная реклама (daily_metrics по дню — уже есть) −
налог дня (calcTotalTax на дневной базе; при usn_income линеен ⇒ Σ дней
= итогу канона точно). Новая проверка №7 в check-profit-canon: Σ
дневных profit товара за период = profit канона (допуск 0,05 ₽;
выборочно 3 товара на площадку).
ЭТО МЕНЯЕТ ЦИФРЫ дневных строк detail (историческая витрина) → шлюз
владельца с дельтой (2-3 товара: старые дневные суммы vs новые, и как
сумма дней теперь сходится с итогом).

## Что НЕ входит

Курсорная пагинация фронта; расширение lossMakers на Ozon; изменение
кабинетных формул/pnl-итогов; UI-редизайн; wbFinanceByDay остаётся для
справочных построчных колонок detail (комиссия/логистика дня из
finance_report — informational, только прибыль дня переезжает на канон).

## Приёмка

profit-snapshot --verify: все существующие числа Δ=0, КРОМЕ дневных
строк detail (ожидаемое изменение — через шлюз владельца); check-profit-
canon с новыми проверками №6-7 — ALL PASS; замер SQL-счётчика страницы
products-summary до/после (лог эмулятора или счётчик prepare) — число
запросов не зависит от N. Тексты по-русски; расхождение цифр = наш баг.
