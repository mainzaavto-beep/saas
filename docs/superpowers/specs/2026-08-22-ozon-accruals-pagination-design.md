# Курсор last_id в начислениях Ozon + детекторы глубины — дизайн

Дата: 2026-08-22. Статус: подход Б одобрен владельцем («пиши спеку»).

## Зачем

`ozon_accruals` — финансовое ядро (из начислений считается прибыль). API
`/v1/finance/accrual/by-day` отдаёт строки страницами с курсором `last_id`,
но клиент читает ТОЛЬКО первую страницу: `check_single_page`
(`worker/collectors/ozon_accruals.py:185-198`, детектор из плана переезда
начислений) лишь замечает непустой `last_id` и переводит прогон в partial.
На текущих объёмах (≤2 тыс. заказов/кабинет) день влезает в страницу; у
крупного клиента сборщик начнёт стабильно недобирать строки → прибыль
неполная. Пункт дважды выносился «до онбординга крупных» (спеки 2026-08-15
и 2026-08-20, «Что НЕ входит») — пора закрыть.

Попутно (дух «не молчим»): три оставшихся offset/страничных цикла без
известных лимитов получают дешёвые детекторы аномальной глубины.

## Разведка (2026-08-22, проверено по коду)

- Уже на курсорах, НЕ трогаем: `iter_all_products` (last_id),
  `iter_postings` (cursor; переведён 2026-07-02 после зависания — старая
  модель offset/last_id API игнорируется), `wb_finance` (rrdid),
  `wb_catalog` (updatedAt+nmID). `ozon_finance` — page/page_size (нативная
  модель v3, лимита глубины в коде не зафиксировано).
- Дыра: `ozon_client.accrual_by_day` (`ozon_client.py:403-412`) — без
  цикла по last_id; `check_single_page` — только детектор.
- Offset-циклы без детекторов: `iter_stock` (`ozon_client.py:292-304`),
  `iter_analytics` (`ozon_client.py:336-363`), `wb_prices` (потолок
  `offset <= 50000`, `wb_prices.py:73`).

## Компоненты

### 1. Пагинация accrual_by_day (ядро)

`worker/collectors/ozon_client.py`: `accrual_by_day` становится циклом по
`last_id` (форма — как в `iter_all_products`: первая страница без
`last_id`, дальше передаём из ответа; стоп — пустой `last_id` или пустые
строки). Защита от зацикливания (урок iter_postings: API может игнорировать
курсор и отдавать ту же страницу): если `last_id` повторился или страниц
больше жёсткого потолка (константа `ACCRUAL_MAX_PAGES = 200`) — исключение
с внятным текстом → прогон partial, окно НЕ записано (существующая
семантика PartialError-подобных отказов accruals).

`worker/collectors/ozon_accruals.py`: потребитель получает все страницы;
`check_single_page` УДАЛЯЕТСЯ (заменой служит сама пагинация + счётчик:
`print` числа страниц, если их > 1 — видимость многостраничных дней).
Runtime-инварианты сборщика (consistency, row_sum_mismatch и пр.) не
меняются — работают поверх полного набора строк. `##OBS rows=` считает
строки всех страниц автоматически (счётчик общий).

Синтетический тест стыков страниц (обязателен — на живых данных
многостраничности нет): без сети, фейковый `_post` (monkeypatch),
сценарии: 2 страницы склеиваются без потерь/дублей; повтор `last_id` →
исключение; пустая вторая страница со стопом. Оформить как
`scripts/test-ozon-accruals-pagination.py` (python3, assert, exit 0/1) —
запускается руками и из задач плана; в systemd-расписание не добавляется.

### 2. Детекторы глубины offset-циклов

`iter_stock`, `iter_analytics` (ozon_client.py) и цикл `wb_prices`:
константа `DEPTH_WARN_PAGES = 30` — при превышении печатать
`⚠️ <метод>: пагинация глубже N страниц (offset=…) — проверить лимиты API`
и ПРОДОЛЖАТЬ (не ронять). Одна строка на цикл, поведение не меняется.
`wb_prices`: дополнительно — если цикл упёрся в потолок 50000 И последняя
страница была полной, печатать явное предупреждение о возможном недоборе
(сейчас потолок молчалив).

### 3. Проверка «ничего не изменилось сегодня»

Изменение обязано быть no-op на текущих объёмах: после деплоя — полный
идемпотентный прогон `ozon_accruals` кабинетов 1 и 1008 за 45-дневное окно;
сверка ДО/ПОСЛЕ: `count(*)` и `SUM(amount)` по `tenant.ozon_accruals` в
окне прогона не изменились (SQL под saas_ro, явный cabinet_id). Сторожа:
`check-ozon-accruals.mjs` (оба кабинета), `check-profit-canon.mjs`,
`profit-snapshot.mjs --verify` — ALL PASS. Шлюз владельца не нужен:
изменение может сделать сбор только полнее, на сегодняшних данных Δ=0.

## Что НЕ входит

Перевод offset-циклов на курсоры (лимиты не жмут, YAGNI); `ozon_finance`
page-модель (нативная); wb_jem (отключён); ревизия `iter_postings`/
каталогов (уже курсорные); изменение инвариантов/формул.

## Ограничения (наследуются)

Правки сборщиков = мгновенный деплой (аддитивно-безопасные; пагинация
меняет только полноту чтения, запись идемпотентна DELETE+INSERT окном);
БД читать saas_ro (BYPASSRLS → явный cabinet_id); сторожа ALL PASS после
каждой задачи; тексты по-русски; расхождение цифр = наш баг. Приёмка:
синтетический тест зелёный, no-op-сверка Δ=0 на обоих кабинетах, сторожа
зелёные.
