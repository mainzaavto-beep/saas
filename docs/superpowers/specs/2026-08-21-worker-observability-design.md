# Наблюдаемость воркера — дизайн

Дата: 2026-08-21. Статус: одобрено владельцем (брейншторм в сессии; канал алертов —
баннер в панели, выбор владельца).

## Зачем

Разведка 2026-08-21 подтвердила четыре дыры (перекликается с аудитом 2026-08
«воркер молчит об ошибках»):
1. `saas-failure@%n.service` — единственный обработчик падений юнитов — НИКОМУ
   ничего не шлёт: только строка в `jobs.collector_runs` + journal; комментарий
   в `app/cabinets/[id]/layout.js:172-174` («владельцу алерт уже ушёл») — ложь.
   Сторож финансов может падать сутками незаметно.
2. `jobs.collector_runs.rows_written` — всегда NULL с рождения (031:20 «задел
   на будущее»); сборщики печатают «записано N строк» в stdout, оркестратор
   это не парсит.
3. `date_from/date_to` журнала — CLI-окно, не фактическое (lookback-полы,
   cap_to_yesterday невидимы; «узкое окно вернулось?» недоказуемо по журналу).
4. Кабинет с перманентно битым ключом (1009: нет роли у API-ключа, 14 фейлов)
   вечно долбится суточными контрольными попытками — 6 ложных `failed`-строк
   в журнале ежедневно, шум неотличим от реальных сбоев; статус в БД пишется
   ДО переклассификации в blocked.

## Компоненты

### 1. Операторский баннер (алерты владельцу SaaS)

Плашка поверх всех страниц панели, видимая ТОЛЬКО ops-allowlist
(`SAAS_OPS_USER_IDS` — механизм /health, уже есть). Источник — `jobs.collector_runs`
(последние 24-48 ч): условия красного/жёлтого:
- юнит-фейлы (`run_kind='systemd'`, `collector LIKE 'unit:%'`) свежее 24 ч —
  красный: «Сторож/юнит X падает с <время>»;
- один и тот же сборщик failed ≥2 подряд последних прогонов по кабинету
  (не считая blocked/skipped) — красный: «<collector> кабинета N падает M тиков»;
- partial ≥3 подряд — жёлтый.
Роут `GET /api/ops/alerts` (доступ как /health), лёгкий запрос (индексы есть);
плашка в общем layout. Ложный комментарий в layout.js:172-174 — исправить.
Тесты: SQL-логика условий на синтетике (вставки в jobs — тестовая схема? НЕТ:
чистая функция классификации поверх выборки + фикстурные массивы строк).

### 2. Клиентский баннер устаревших данных

В layout кабинета (рядом с баннером битых ключей): если по активному магазину
кабинета последний `ok`-прогон ЛЮБОГО из его ключевых сборщиков (перечень:
финансы/заказы площадки) старше 24 ч И магазин НЕ в паузе ключей (иначе уже
есть свой баннер) — жёлтая плашка «Данные <площадка> не обновлялись с <дата>».
Без технических деталей. Порог 24 ч — константа с env-переопределением.

### 3. Журнал: rows_written и фактическое окно

Машиночитаемые маркеры в stdout сборщиков (стандарт: строка
`##OBS rows=<N> from=<YYYY-MM-DD> to=<YYYY-MM-DD>` в конце прогона; сборщики
уже печатают человеческие аналоги — добавить маркер рядом, человеческие строки
не трогать). Оркестратор парсит маркер из stdout и передаёт в `_record_run`:
`rows_written` — существующая колонка; фактическое окно — НОВЫЕ колонки
`eff_date_from`, `eff_date_to` (миграция 043, идемпотентная; CLI-окно в
date_from/date_to остаётся как было — история сохраняет смысл «что просили»).
Маркер отсутствует (старый/сторонний сборщик) → NULL, не ошибка. Внедрить
маркер во все Ozon/WB-сборщики с датами (перечень фиксирует план); сборщики
без дат — только rows.

### 4. Перманентно битые ключи

`worker/shop_auth.py`: новое состояние `disabled` — после
`SAAS_AUTH_DISABLE_AFTER` (дефолт 7) подряд неудачных СУТОЧНЫХ контрольных
попыток в `paused` магазин отключается: никаких дальнейших попыток; выход —
только смена ключей клиентом (существующий флоу сохранения ключей делает
`mark_ok`/сброс — проверить и подключить) или ручное снятие. Клиентский баннер
битых ключей должен различать paused/disabled текстом («проверьте ключи» vs
«сбор остановлен — обновите ключи»). Email-уведомление об отключении — через
существующий notify-broken-keys механизм (одно письмо на эпизод, как сейчас).
Контрольная попытка паузы: статусы её сборщиков в `jobs.collector_runs`
пишутся как `blocked` (не `failed`) — переклассификация оркестратора должна
происходить ДО записи в БД (или UPDATE после переклассификации — решает план;
итог: в журнале failed = настоящий сбой, шума от пауз нет).

## Что НЕ входит

Email/пуш-алерты оператору (баннер — выбор владельца; Sendsay ждёт активации);
исторический бэкфилл rows_written/eff-окон (только новые прогоны); rework
/health; курсор last_id; batch-канон; last_change_dt.

## Ограничения (наследуются)

Сборщики: правки аддитивные (маркер stdout), мгновенный деплой учитывать;
миграция 043 идемпотентна; панель — деплой по протоколу; сторожа ALL PASS
после каждой задачи; БД читать saas_ro (BYPASSRLS → явный cabinet_id); тексты
по-русски; расхождение цифр = наш баг. Кабинет 1009 после внедрения п.4 —
живой критерий приёмки (6 ложных failed/день должны исчезнуть из журнала).
