# Реклама Ozon по товарам (per-SKU) — дизайн

Дата: 2026-08-21. Статус: одобрено владельцем (решения «Сделать сейчас» и
«вычитать рекламу из прибыли товара» — в сессии 2026-08-21).

Уточнение решения (2026-08-21, после проверки кода): формулировка «как в WB»
в первом вопросе была ошибочной — WB рекламу товара ПОКАЗЫВАЕТ (колонка,
ДРР), но из прибыли товара НЕ вычитает (`lib/wbMetrics.js:439`: при nmId
ads=0). Владельцу задан повторный вопрос с честной картиной; решение:
**вычитать рекламу из прибыли товара НА ОБЕИХ площадках** — канон WB тоже
меняется, цифры прибыли по товарам WB изменятся (шлюз с дельтой до/после).

## Зачем

По-товарной рекламы Ozon в панели нет и не было: `ozon_daily_metrics.ad_spend`
пуст с рождения, канон честно показывает 0 и не вычитает рекламу из прибыли
товара (в отличие от WB, где `wb_daily_metrics.ad_spend` заполнен). Владелец
2026-08-21: «нет расходов по рекламе озона» → делать сейчас.

## Доказательная база (живая проба 2026-08-21, кабинет 1)

Скрипт-проба (3 прогона, запуски владельцем) установила:

1. **Источник существует**: Performance API `POST /api/client/statistics`
   с `groupBy: DATE` строит async-отчёт; скачивание по `link` из poll-ответа
   **с Bearer-токеном** отдаёт ZIP: внутри CSV на каждую кампанию
   (`<campaign_id>_<даты>.csv`), строки **день × sku** с колонками
   «Расход, ₽, с НДС», Показы, Клики, «Продано товаров»,
   «Заказано на сумму, ₽», ДРР.
2. **Суммы сходятся**: Σ отчёта по (кампания, день) против
   `tenant.ozon_daily_campaign_ad` — Δ=0.00 на 13 из 16 закрытых точек.
3. **Три источника расхождений** (все законные, дизайн их учитывает):
   - текущий день растёт внутри дня → зрелость: текущий день не пишем
     (или перезапишем завтра);
   - ретро-ревизии закрытых дней (+2,80 ₽ и +11,10 ₽ на 2 днях против наших
     данных, собранных раньше) → ежедневный lookback-пересбор;
   - строка `Корректировка` без даты и sku (−13,90 ₽ в пробе) → Σ по SKU
     может законно отличаться от кампанийного итога.
4. **Ключ**: `sku` отчёта = `tenant.ozon_products.fbo_sku`; маппинг на
   `product_id` (ключ `ozon_daily_metrics`) есть в каталоге.
5. **Лимиты**: `/statistics/json` (sync) быстро отдаёт 429 → только async;
   известная грабля `/statistics/daily`: максимум 61 день за запрос
   (ровно 62 — уже 400). Лимит числа кампаний на один async-отчёт
   уточнить в плане (проба: 3 кампании ок; по документации ~10).

## Компоненты

### 1. Сборщик `worker/collectors/ozon_sku_ad.py`

Отдельный сборщик (не расширение `ozon_efficiency`): async-флоу медленный
(create → poll → download, лимит одновременных отчётов), нельзя тормозить
существующий тик. Использует те же perf-creds (`OZON_PERF_CLIENT_ID/SECRET`
через существующий механизм creds кабинета); без perf-creds — мягкий skip,
как в `ozon_efficiency`. OAuth: JSON-body (basic auth даёт 401 — грабля
2026-08-02). Флоу: список кампаний со spend за окно (из
`tenant.ozon_daily_campaign_ad` — уже собран v1-сборщиком) → чанки кампаний →
create/poll/download → ZIP → CSV; `campaign_id` из имени члена архива;
заголовок ищется по строкам (перед ним титульная строка); строки
`Всего`/`Итого`/`Корректировка` пропускаются; даты `дд.мм.гггг` → ISO;
числа с запятой и NBSP. Окно: ежедневно последние 14 дней
(cap до вчера — текущий день не пишем); разовый бэкфилл истории чанками
≤61 день на всю глубину, которую отдаст API. Регистрация: orchestrator И
`run_saas_collect.sh` (урок переезда начислений — забыть второе = сборщик
не в расписании). Runtime-инварианты + `##OBS`-совместимый вывод
«записано N строк».

### 2. Хранение

Сырой слой — новая таблица `tenant.ozon_daily_sku_ad`
(`cabinet_id, date, campaign_id, sku, product_id, spend, views, clicks,
ordered_units, ordered_amount, updated_at`; PK
`(cabinet_id, date, campaign_id, sku)`; `product_id` — резолв из
`ozon_products.fbo_sku` на момент записи, NULL если товар не найден —
видимый счётчик пропусков). Идемпотентность: DELETE окна по
`(cabinet_id, date BETWEEN …)` + INSERT в одной транзакции.
Миграция — следующий свободный номер, идемпотентная. Новой таблице —
GRANT для `saas_ro` (default privileges уже есть) и политика
`panel_local_ro_cab1` (локальная панель владельца).

Агрегация в панель: после записи сырого слоя тот же прогон пересчитывает
`tenant.ozon_daily_metrics.ad_spend` (и `ad_views`, `ad_clicks`,
`ad_orders` — колонки уже существуют и пусты) SQL-суммой из
`ozon_daily_sku_ad` по `(product_id, date)` за окно — по образцу того, как
`ozon_efficiency` пересчитывает кабинетный `ad_spend` из
`ozon_daily_campaign_ad`. Обновляются только дни внутри окна прогона.

### 3. Панель

Канон обеих площадок меняется симметрично: в `ozProfitProduct` (сейчас
`ads = productId == null ? кабинет : 0`, `lib/ozonMetrics.js:257`) и
`wbProfitProduct` (`lib/wbMetrics.js:439`) при товарном фильтре ads =
реальный расход ЭТОГО товара из `daily_metrics.ad_spend` (Ozon —
заполняется этим планом, WB — данные уже есть). Инвариант №5
`check-profit-canon.mjs` (аддитивность товарного фильтра) обновляется:
Σ profit(товар) − (ads(кабинет) − Σ ads(товар)) = profit(без фильтра).
Итоги Сводки (`filteredTotals`) и тултипы — под новую композицию:
прибыль товара уже включает его рекламу; при вычете остаётся только
«нераспределённая» кабинетная часть (корректировки + кампании без
товарной разбивки). Кабинетная прибыль
(P&L/Обзор) НЕ меняется: там реклама уже вычитается суммой
`ozon_daily_efficiency.ad_spend` (источник — кампанийная таблица, она
полнее: корректировки + кампании без товарной разбивки). Тултип рекламной
колонки Сводки обновить: «по товарам — из отчётов продвижения Ozon; итог
кабинета включает также корректировки и кампании без товарной разбивки».
Historic-подмена прибыли товаров = шлюз владельца с дельтой до/после
(как в прошлых планах), GATE_CHECKS в `profit-snapshot.mjs` обновить
старое→новое.

### 4. Сторож

Скрипт `scripts/check-ozon-sku-ad.mjs` (в `saas-ozon-recon` рядом с
остальными): за 4 закрытые ISO-недели Σ `ozon_daily_sku_ad` по
(кампания, день) против `ozon_daily_campaign_ad` — допуск на корректировки
(порог: |Δ| ≤ max(1% от spend дня, 50 ₽) — калибруется по факту в плане);
плюс инвариант «Σ `daily_metrics.ad_spend` по товарам ≤ кабинетного
`ozon_daily_efficiency.ad_spend` за день» (с тем же допуском на знак
корректировок). `docs/metrics-contract.md` дополнить разделом про
по-товарную рекламу Ozon и её источник.

## Что НЕ входит

WB-сборщик рекламы (уже работает; у WB меняется только формула прибыли
товара); изменение кабинетной прибыли/P&L; UI-редизайн;
наблюдаемость воркера (отдельная спека 2026-08-21, идёт следом);
per-SKU разбивка кампаний без товарной разбивки (блогеры, брендовые) —
их расход остаётся только в кабинетном итоге.

## Ограничения (наследуются)

Правки сборщиков = мгновенный деплой (расписание подхватит) — историческую
подмену прибыли гейтить ДО регистрации в расписании; панель — только
`npm run build && systemctl restart saas-web`; БД читать `saas_ro`
(BYPASSRLS → явный `cabinet_id`), запись — только миграции/сборщики;
сторожа ALL PASS после каждой задачи; тексты по-русски; расхождение цифр =
наш баг. Приёмка: сверка сторожа зелёная на кабинете 1, прибыль товаров
на Сводке изменилась ровно на их рекламный расход, кабинетные итоги
не сдвинулись.
