# Унификация формул прибыли (WB + Ozon) — дизайн

Дата: 2026-08-20. Статус: одобрено владельцем (брейншторм в сессии).

## Зачем

«Прибыль» на страницах панели считается восемью независимыми инлайн-формулами с
разным составом расходов (карта — разведка 2026-08-15, подтверждена финальным
ревью витрины: до 8 073 ₽ расхождения на одной карточке). P&L не вычитает
рекламу и лояльность; план/факт берёт плановую себестоимость; юнит-экономика —
константу 10%. Кабинетные расходы Ozon (`tenant.ozon_cabinet_costs`,
`accrual_%`-статьи: Premium −400 тыс ₽/год, RFBS-доставка −674 тыс, штрафы...)
собираются, но не потребляются панелью вовсе, а там где показываются
(`cabinet-costs`, pnl-строки WB-аналога) — светят технические ключи `accrual_93`
вместо имён. Болезнь общая для WB и Ozon.

## Решения владельца (зафиксированы)

1. **Кабинетные расходы вычитаются на кабинетных страницах** (P&L, Обзор) —
   отдельными строками с русскими именами; **товарные страницы** (Сводка/ABC,
   РНП, карточка, план/факт) показывают прибыль товара БЕЗ кабинетных
   (размазывание по товарам отвергнуто как ложная точность).
2. **Юнит-экономика не трогается** (плановый калькулятор, легитимно другая
   логика).
3. **Шлюз**: документ «страница × месяц: было/станет» (оба кабинета, обе
   площадки, объяснение каждого сдвига) → «да» владельца → подмена формул.

## Архитектура

### Канонический слой (единственный источник формул)

В `lib/ozonMetrics.js` и `lib/wbMetrics.js` — по две канонические функции
(имена финальные, сигнатуры фиксирует план):

- **`profitProduct(period[, productId])`** — прибыль товарного уровня:
  `SUM(order_costs.profit)` (уже = деньги маркетплейса − COGS; для Ozon —
  из начислений со склейкой семей, для WB — ppvz-модель) **− реклама факт**
  (Ozon: `ozon_daily_efficiency.ad_spend`; WB: существующий `wbAdTotal`-источник)
  **− налог** (существующий `calcTotalTax`-механизм, без изменений методики).
- **`profitCabinet(period)`** = `profitProduct(period)` **− кабинетные расходы**
  (Ozon: `ozon_cabinet_costs` все статьи, включая `accrual_%`; WB:
  `wb_cabinet_costs`) — с разбивкой по статьям для отображения.

Обе возвращают и итог, и слагаемые (revenue, cogs, commission, logistics,
acquiring, loyalty, returnLogistics — справочно; ads, tax, cabinetCosts[]) —
чтобы страницы показывали строки без пересчёта. Себестоимость — всегда факт
(`order_costs.cost`/`cost_overrides` на дату продажи), как в самих order_costs.

### Имена кабинетных статей

Словарь `cost_type → русское имя`: для `accrual_<id>` — из
`shared.ozon_accrual_types` (name/description; человекочитаемая форма —
таблица соответствия в коде канона, не в роутах); для прочих статей — как
уже принято у WB. Ключ `accrual_93` больше нигде не показывается сырым.

### Потребители (все переходят на канон, своих формул не остаётся)

| Место | Функция | Примечание |
|---|---|---|
| `/api/.../pnl` | profitCabinet | впервые получает рекламу, лояльность, кабинетные статьи строками |
| `/api/.../overview` | profitCabinet | вместо компонентного пересчёта |
| `/api/.../detail` | profitProduct(productId) | |
| `/api/.../products-summary` | profitProduct по товарам | returnLogistics остаётся справочной строкой (уже внутри profit) |
| `/api/.../rnp-summary` | profitProduct по товарам | |
| `/api/.../plan/fact` | profitProduct | себестоимость — ФАКТ (плановая остаётся только в плановых колонках) |
| `/api/.../orders` | строки как есть из order_costs | пересчёт cost на лету выравнивается с каноном (та же подстановка cost_overrides, что в profitProduct) |
| `/api/.../unit` (без потребителей) | — | удалить мёртвый роут |

Юнит-экономика (`unit/all`, `lib/unit.js`) — вне периметра.

### Сторож

Новая еженедельная проверка (в существующий `saas-ozon-recon` service,
отдельный скрипт или расширение): `profitCabinet(неделя)` каждой площадки =
независимой SQL-сумме слагаемых (перекрёстная проверка канона против прямых
запросов; допуск 1 ₽). Все существующие проверки остаются зелёными.

## Шлюз и приёмка

1. До подмены роутов: скрипт сравнения считает «было» (текущие формулы страниц,
   зафиксированные как эталонные снапшоты) и «станет» (канон) помесячно за
   последние 4 полных месяца × оба кабинета × обе площадки; документ с
   объяснением каждого сдвига (реклама в P&L, кабинетные статьи, факт-COGS в
   план/факте...). **«Да» владельца обязательно.**
2. После подмены: один период → одна цифра на всех страницах (автопроверка:
   агрегаты всех роутов сходятся с каноном до копейки); прибыль июля-2026
   Ozon каб.1 согласована со сверенными документами (эталоны в
   `docs/ozon-external-reconciliation-*`); сторож ALL PASS.

## Что НЕ входит

Юнит-экономика; изменение сборщиков и таблиц (только чтение существующих);
методика налога (берётся как есть); курсор `last_id`; наблюдаемость воркера;
last_change_dt/cancel_dt; честный NULL-guard /orders (мелкий хвост витрины —
можно взять бонусом, если попадает в правимый файл); ротация ключа; Sendsay.

## Ограничения (наследуются)

БД читать `saas_ro` (BYPASSRLS → явный cabinet_id); деплой панели только
`npm run build && systemctl restart saas-web`; guard-предикаты только на
nullable-поля (перф-урок: INDF ломает hash join); правки роутов = деплой после
рестарта, сборщиков — мгновенный (здесь сборщики не трогаются); тексты
по-русски; расхождение цифр = наш баг, пока не доказано обратное; сторож
ALL PASS после каждой задачи.
