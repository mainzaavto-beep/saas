# Дизайн: оплата подписки (2026-08-07)

## Контекст и цель

Панель открыта для саморегистрации, новый кабинет получает пробный период 14 дней (`auth.cabinets.trial_ends_at`, фаза 2 auth-редизайна). Блокировки по истечении нет — сейчас клиент может пользоваться панелью бесконечно. Задача: сделать доступ платным, принимать деньги через ЮKassa и закрывать панель, когда оплаченный период кончился.

**Вне охвата** (сознательно, YAGNI): тарифные планы с разными лимитами, автосписание с сохранённой карты, промокоды и скидки, партнёрские программы, возвраты через интерфейс (делаются вручную в кабинете ЮKassa), выставление счетов юрлицам по безналу с закрывающими документами. Каждое из этого — отдельная спека, если понадобится.

## Принятые решения (с владельцем, 2026-08-07)

| Вопрос | Решение |
|---|---|
| Модель тарифа | Фиксированная цена за кабинет в месяц, число магазинов внутри не влияет |
| Периоды | 1, 3 и 12 месяцев; за длинные периоды скидка |
| Провайдер | ЮKassa (карты, СБП, чеки 54-ФЗ на стороне провайдера) |
| Способ оплаты | Ручная: клиент сам нажимает «Оплатить». Автосписание — возможно позже, отдельной работой |
| По истечении срока | 3 дня отсрочки с полным доступом и баннером, затем панель закрыта кроме страницы оплаты |
| Сбор данных | Продолжается всегда, в том числе на заблокированном кабинете |
| Архитектура | Дата «оплачено до» на кабинете + журнал платежей |

## Секция 1. Модель данных и жизненный цикл доступа

**Состояние доступа считается из двух дат на `auth.cabinets`:** существующей `trial_ends_at` и новой `paid_until`. Отдельной сущности «подписка» нет — состояние выводится, а не хранится, поэтому рассинхронизация невозможна.

```
access_until = max(trial_ends_at, paid_until)   -- NULL считается «давно прошло»
```

Четыре состояния, вычисляемые одной функцией `cabinetAccess(cabinet)`:

| Состояние | Условие | Что видит клиент |
|---|---|---|
| `trial` | `access_until` в будущем, `paid_until` пуст | Баннер «Пробный период — осталось N дней», полный доступ |
| `active` | `paid_until` в будущем | Баннер за 5 дней до конца, иначе ничего; полный доступ |
| `grace` | `access_until` прошло меньше 3 дней назад | Красный баннер «Доступ закроется <дата>, оплатите», полный доступ |
| `locked` | `access_until` прошло больше 3 дней назад | Только страница оплаты |

Длина отсрочки — `SAAS_GRACE_DAYS`, дефолт 3. Цены и периоды — тоже конфигурация, не код: таблица `billing.plans` (`code`, `months`, `price_rub`, `title`, `is_active`, `sort`), которую владелец правит SQL-ом без пересборки. Стартовое наполнение — три строки (1, 3, 12 месяцев); конкретные суммы владелец задаёт при внедрении, в коде их нет.

**Журнал платежей** `billing.payments`: `payment_id` (UUID от ЮKassa, первичный ключ — он же ключ идемпотентности), `cabinet_id`, `user_id` (кто платил), `plan_code`, `months`, `amount_rub`, `status` (`pending` / `succeeded` / `canceled`), `paid_until_before` и `paid_until_after` (что стало с датой — для разбора спорных случаев), `created_at`, `updated_at`, `raw` (JSONB — ответ провайдера как есть). Журнал — источник истины для сверки с личным кабинетом ЮKassa; `paid_until` — производная от него величина, и расхождение между ними всегда наш баг (правило проекта про финансовые расхождения).

**Продление считается от максимума:** `paid_until = max(now(), access_until) + N месяцев`. Клиент, оплативший за неделю до конца, не теряет оставшиеся дни; клиент, вернувшийся через месяц после блокировки, платит с сегодняшнего дня, а не задним числом.

**Кто может платить:** только владелец кабинета (`role = 'owner'`). Менеджер и наблюдатель видят состояние и баннеры, но кнопка оплаты им недоступна — счёт платит тот, чей это проект.

## Секция 2. Оплата через ЮKassa

**Создание платежа.** `POST /api/cabinets/[id]/billing/pay {plan_code}` (только владелец, только подтверждённый email — платить с непроверенного адреса нельзя): сервер сам берёт цену из `billing.plans` по коду (клиент передаёт только код плана — сумма из браузера не принимается никогда), создаёт платёж в ЮKassa с `capture: true`, `confirmation.type: redirect`, `return_url` на `/cabinets/<id>/billing?paid=1`, описанием «Подписка SySell, <N> мес., проект <имя>» и чеком 54-ФЗ (позиция услуги, НДС по настройке владельца, email плательщика). Записывает строку в `billing.payments` со статусом `pending` и отдаёт клиенту `confirmation_url` для перехода.

**Идемпотентность в обе стороны.** В запрос к ЮKassa кладём заголовок `Idempotence-Key` (UUID нашей строки платежа) — повторный клик не создаёт второй платёж у провайдера. В обратную сторону: `payment_id` — первичный ключ, а зачисление выполняется одним `UPDATE ... WHERE status = 'pending'` внутри транзакции с продлением `paid_until`; повторный вебхук по тому же платежу не продлит период второй раз.

**Подтверждение — вебхук, а не редирект.** `POST /api/billing/webhook` (публичный путь, вне сессии) принимает уведомление `payment.succeeded`. Порядок: проверить, что источник — ЮKassa; вытащить `payment_id`; **перезапросить платёж по API ЮKassa** и поверить сумме и статусу из ответа API, а не телу вебхука; затем в одной транзакции пометить платёж `succeeded` и сдвинуть `paid_until`. Возврат на `return_url` — только для UX: страница показывает «платёж обрабатывается», сама опрашивает `GET /api/cabinets/[id]/billing` и обновляется, когда вебхук отработал. Деньги никогда не зачисляются по факту редиректа: браузерный возврат подделывается тривиально.

**Защита вебхука.** ЮKassa не подписывает уведомления, поэтому доверять телу нельзя в принципе. Три меры: (1) обязательная перепроверка платежа через API провайдера; (2) фильтр по списку IP-сетей ЮKassa (`SAAS_YOOKASSA_IPS`, обновляемый конфигом — реальный IP берём из `X-Forwarded-For`, его проставляет Caddy); (3) секретный сегмент в URL вебхука (`/api/billing/webhook/<SAAS_YOOKASSA_WEBHOOK_SECRET>`) — чтобы адрес нельзя было угадать. Любое несоответствие суммы или статуса — платёж не зачисляется, в лог пишется предупреждение, в `billing.payments.raw` сохраняется полученное тело для разбора.

**Несходящаяся сумма — стоп.** Если сумма из API провайдера не совпадает с ценой плана в нашей БД, зачисления не происходит вообще: статус ставится `succeeded`, но `paid_until` не двигается, и в лог идёт ошибка с обоими числами. Это ситуация «клиент заплатил не столько» — разбираем руками, а не гадаем.

**Что делать со сбоями.** Платёж, зависший в `pending` дольше суток, помечается `canceled` фоновым скриптом (`scripts/billing-reconcile.mjs`, systemd-таймер раз в час), который дополнительно перезапрашивает у ЮKassa все `pending`-платежи за последние 3 дня и дозачисляет те, по которым вебхук не дошёл. Это страховка от потерянных уведомлений: клиент заплатил — доступ обязан открыться, даже если уведомление не долетело.

## Секция 3. Интерфейс и блокировка

**Страница `/cabinets/[id]/billing`** — единственное место про деньги: текущее состояние («оплачено до <дата>» / «пробный период до <дата>» / «доступ закрыт»), три карточки периодов с ценой и выгодой относительно месячной, кнопка «Оплатить» (владельцу), таблица прошлых платежей (дата, период, сумма, статус). Для менеджера и наблюдателя — то же состояние, но вместо кнопки текст «Оплату производит владелец проекта».

**Баннеры** живут в существующей шапке кабинета (`app/cabinets/[id]/layout.js`, туда уже встроены баннеры триала и подтверждения почты — они объединяются в один компонент, чтобы шапка не превращалась в стопку полос): в `trial` — жёлтый с числом дней, в `active` за 5 дней до конца — жёлтый «Подписка заканчивается <дата>», в `grace` — красный «Доступ закроется <дата>».

**Блокировка.** Проверка — в `lib/withCabinet.js`, рядом с проверками роли и подтверждения почты: если состояние `locked`, любой кабинетный API отвечает 402 `{ error, code: 'subscription_required' }`. Исключения (работают всегда): сам биллинговый API, `/api/cabinets/[id]/me`, выход из аккаунта и просмотр профиля. Страницы кабинета: `layout.js` при `locked` редиректит на страницу оплаты — кроме неё самой. Список проектов и переключатель кабинетов остаются доступными: у клиента может быть один кабинет оплачен, другой нет.

**Что блокировка не трогает.** Воркер продолжает собирать данные по заблокированному кабинету — иначе после оплаты клиент увидит дыру в истории, а маркетплейсы отдают ограниченное окно назад. Это осознанная плата за качество данных; если появятся «мёртвые» кабинеты, месяцами не платящие, их отключение будет отдельным решением (кандидат: перестать собирать после 60 дней блокировки).

**Роль владельца сервиса.** Владелец (`SAAS_OPS_USER_IDS`, механизм уже есть на странице `/health`) видит на `/health` дополнительный блок: кабинеты, состояние доступа, дата окончания, сумма последнего платежа. Ручное продление — SQL-ом (`UPDATE auth.cabinets SET paid_until = ...`), интерфейса для этого не делаем: операция редкая, а кнопка «выдать доступ бесплатно» в панели — лишний риск.

## Изменения схемы БД

Миграция `034_billing.sql`:
- `auth.cabinets` + `paid_until TIMESTAMPTZ` (NULL = никогда не платили);
- `billing` — новая схема; `billing.plans` (`code TEXT PK`, `months INT`, `price_rub NUMERIC(10,2)`, `title TEXT`, `is_active BOOL`, `sort INT`). Миграция создаёт таблицу пустой — цены владелец задаёт отдельным INSERT при внедрении (готовый шаблон запроса кладём в план реализации). Панель без активных планов кнопку оплаты не показывает и пишет «тарифы не настроены», а не падает;
- `billing.payments` (описана в секции 1), индекс по `(cabinet_id, created_at DESC)`;
- `GRANT` для роли `saas_app`: SELECT на `plans`, SELECT/INSERT/UPDATE на `payments`, UPDATE `paid_until` идёт через существующие права на `auth.cabinets`.

## Тестирование

- **Смоук** `scripts/smoke-billing.mjs` против тестового магазина ЮKassa: создание платежа (сумма берётся с сервера, подмена суммы клиентом игнорируется), зачисление по вебхуку и сдвиг `paid_until`, повторный вебхук не продлевает второй раз, чужой/поддельный вебхук отклоняется, продление от максимума (оплата до истечения не съедает остаток), блокировка после `grace` (402 на кабинетном API, редирект на страницу оплаты), доступность биллингового API при блокировке, запрет оплаты для менеджера и наблюдателя.
- **Проверка сверки**: скрипт `billing-reconcile.mjs` дозачисляет платёж, по которому вебхук «потерян» (эмулируется тем, что вебхук просто не вызывается).
- **Ручная приёмка на проде**: владелец платит реальные 1–2 рубля тестовым планом и проверяет чек в почте и запись в кабинете ЮKassa.

## Риски

- **Пропущенный вебхук** — клиент заплатил, доступ не открылся. Закрыто скриптом сверки раз в час; при этом клиент видит на странице «платёж обрабатывается», а не ошибку.
- **Двойное продление** при повторных уведомлениях. Закрыто условным `UPDATE` по статусу внутри транзакции; проверяется смоуком.
- **Блокировка бьёт по своим**: неверный расчёт даты закроет панель платящему клиенту. Поэтому `cabinetAccess` — одна функция с прямыми тестами, а не три копии условия по коду; на проде перед включением блокировки гоняем сверку состояний по всем кабинетам.
- **Первый платёж в проде** может вскрыть несоответствие настроек чека (НДС, признак предмета расчёта). Поэтому приёмка — реальным платежом на маленькую сумму до анонса клиентам.

## Что потребуется от владельца до внедрения

1. Магазин в ЮKassa: `shopId` и секретный ключ (тестовые и боевые) — в `.env.local` как `SAAS_YOOKASSA_SHOP_ID` / `SAAS_YOOKASSA_SECRET_KEY`.
2. Настройка чеков: ставка НДС (или УСН без НДС), признак предмета расчёта — уточняется при заполнении данных магазина.
3. Цены на три периода.
4. URL вебхука прописывается в кабинете ЮKassa после деплоя: `https://sysell.ru/api/billing/webhook/<секрет>`.
