# Переключение расчёта прибыли Ozon на источник начислений — дизайн

Дата: 2026-08-15. Статус: одобрено владельцем (брейншторм в сессии).

## Зачем

Расчёт прибыли Ozon (`worker/collectors/ozon_order_costs.py` → `tenant.ozon_order_costs`)
питается от старого отчёта `tenant.ozon_finance_report` и учитывает 6 из 14 реально
встречающихся типов операций: на проверенном дне (2026-08-05, кабинет 1) мимо прибыли
прошло 8 252,58 ₽. Новый источник `tenant.ozon_accruals` доказан трёхуровневой сверкой
(внутренняя арифметика → старый источник → официальные документы Ozon, всё до копейки —
`docs/ozon-external-reconciliation-2026-08.md` и `-expenses-`). Переключаем расчёт на него.

## Решения владельца (зафиксированы)

1. **История пересчитывается целиком** — на всю глубину покрытия начислений
   (2025-08-14 → сегодня, кабинеты 1 и 1008). Цифры прошлых месяцев в панели изменятся
   (станут точнее). Шва «старая/новая модель» нет.
2. **Старый сборщик `ozon_finance` остаётся сторожем** — продолжает работать в расписании,
   еженедельная автосверка старый↔новый ловит расхождения. Решение об отключении — через
   2-3 месяца спокойной работы, отдельно.
3. **Периметр — только переключение источника.** Контракт таблицы `tenant.ozon_order_costs`
   (набор и смысл колонок) сохраняется, 8 инлайн-формул прибыли в роутах панели не трогаем —
   их унификация (болезнь общая с WB) — отдельный следующий проект.

## Архитектура (подход А)

### Единица расчёта — отправление

`ozon_order_costs.py` v2 группирует строки `tenant.ozon_accruals` по
(`cabinet_id`, `unit_number`) и пишет одну запись на отправление в `tenant.ozon_order_costs`
(тот же ключ и колонки, что сейчас). Строки без `unit_number` (NON_ITEM) — расходы уровня
кабинета, в order_costs не попадают (см. ниже).

**Ключевой инвариант (самопроверка модели):**

```
SUM(accrued по строкам, попавшим в order_costs)
+ SUM(accrued по строкам уровня кабинета)
= SUM(total_amount всех начислений за период)
```

Инвариант проверяется в самом сборщике на каждом прогоне (по образцу `row_sum_mismatch`
задачи 3): расхождение — счётчик, русский лог, exit-код 3 (partial). Ничего не может
выпасть из расчёта молча — любой новый/незнакомый тип либо попадает в позаказные «прочее»,
либо в кабинетные «прочее», и сумма всё равно сходится.

### Раскладка по колонкам контракта

| Колонка order_costs | Источник в ozon_accruals | Примечание |
|---|---|---|
| `cost_value_retail` (revenue) | `seller_price` commission-блока (POSTING, `type_id IS NULL`) | та же семантика, что сейчас (`accruals_for_sale` ≡ `seller_price` — тождество доказано) |
| `commission` | `sale_commission` commission-блока | |
| `logistics` | ВСЕ позаказные сервисные строки отправления, кроме комиссии и эквайринга: логистика (типы 32/29/98 по таблице «код → роль») **плюс прочие/незнакомые позаказные типы** | ключевое отличие от старой модели: недостающие сейчас позаказные типы попадают сюда, потому что роуты панели пересчитывают прибыль из компонент и вычитают `logistics` все до одного — положив «прочее» в отдельную колонку, мы бы снова его потеряли. Незнакомый тип дополнительно логируется со счётчиком |
| `acquiring` | ITEM-строки type_id=1, привязанные к отправлению | |
| `loyalty` | по фактическому составу типов; уточняется разбором на фикстурах, фиксируется явным перечнем type_id (может остаться пустым) | `/pnl` — единственный роут, не вычитающий loyalty: класть сюда можно только то, что и по смыслу лояльность |
| `cost` (COGS) | `tenant.cost_overrides` — как сейчас | без изменений |
| `profit` | `SUM(accrued всех строк отправления) − cost` | инвариантная формула |

**Согласованность компонент и инварианта.** Обязана выполняться построчная проверка:
`seller_price − commission − logistics − acquiring − loyalty = SUM(accrued строк отправления)`,
где каждая из компонент (`commission`/`logistics`/`acquiring`/`loyalty`) — это
**−1 × сумма знаковых `accrued` строк своей корзины** (не сумма `|accrued|`
по строкам!). На типовом отправлении сумма корзины отрицательна, поэтому
`−sum(корзина) == |sum(корзина)|` — отсюда более простая (но неточная в
общем случае) запись `|commission|` в более ранних черновиках этого
документа. Разница проявляется на сторно/разворотах внутри одной корзины
(например, эквайринг `−24.99` и `+24.99` в один день — верная сумма
корзины 0, а `Σ|accrued строки|` дала бы 49.98): такой случай встретился
на живых данных при реализации задачи 3 (см. `task-3-report.md`, находка
ревью) и исправлен именно как «`−sum`, а не `Σ|·|`». (следует из доказанного
тождества `total_amount = delivery + sale_price + sale_commission +
coinvestment + bonus` и `seller_price = sale_price + coinvestment + bonus`).
Сборщик проверяет её на каждом отправлении: расхождение — счётчик + лог +
exit 3. Это гарантирует, что компонентные формулы роутов и колонка `profit`
дают одну и ту же прибыль.
| `is_return` | коды 45/59 у отправления И/ИЛИ отрицательный commission-блок | **фикс эвристики ±835 ₽**: нулевые отправления (sale_price=0 без commission-блока) больше не путаются с возвратами; правило верифицируется на фикстурах и на живых месяцах сверкой ролей |

### Расходы уровня кабинета (NON_ITEM)

NON_ITEM-начисления (размещение, страхование, обработка отзывов, кабинетные услуги, …)
пишутся дневным агрегатом в `tenant.ozon_cabinet_costs` по образцу WB
(`wb_cabinet_costs`): дата, статья (тип из справочника), сумма. Потребление их роутами
панели — в следующем проекте (унификация формул); в этом плане они собираются и сверяются.

**Защита от двойного счёта рекламы.** Типы продвижения (трафареты, вывод в топ и др. —
точный перечень type_id фиксируется разбором) в `ozon_cabinet_costs` **не пишутся**:
реклама уже приходит из Performance API (`ad_spend`, нужна панели с разбивкой по
кампаниям) и вычитается роутами. Вместо записи — сторож (см. ниже) еженедельно сверяет
«NON_ITEM-продвижение ↔ ad_spend» и кричит при расхождении больше порога (порог — в ₽,
абсолютный, без процентных допусков; дефолт 100 ₽/неделя, настраивается аргументом скрипта).

### Пересчёт истории — теневая таблица

1. Новый сборщик пишет год (покрытие начислений, оба кабинета) в теневую
   `tenant.ozon_order_costs_shadow` (та же структура; RLS по образцу).
2. Скрипт сравнения формирует документ «дельта прибыли по месяцам»: старая прибыль /
   новая / разница ₽ и % + разложение дельты по причинам (новые типы операций, фикс
   эвристики возвратов, прочее). **Владелец смотрит дельту ДО подмены.**
3. Подмена — атомарно в одной транзакции: DELETE строк периода покрытия из боевой
   таблицы + INSERT из теневой; строки глубже покрытия начислений (если есть) не
   трогаются. Теневая таблица после подмены удаляется.
4. Откат: пересборка старой версией сборщика из git — вход (`ozon_finance_report`)
   продолжает собираться сторожем.

### Сторожа после переключения (еженедельный таймер)

1. Существующая сверка источников `scripts/check-ozon-accruals.mjs` (старый↔новый).
2. Инвариант `order_costs + cabinet_costs = total_amount` за неделю.
3. Продвижение NON_ITEM ↔ `ad_spend` Performance API.

Всё — с ненулевым exit-кодом при расхождении, по образцу существующих сверок; запуск —
systemd-timer по образцу `saas-billing-reconcile.timer`.

## Что НЕ входит

- Унификация 8 инлайн-формул прибыли в роутах (отдельный проект, касается и WB).
- Потребление `ozon_cabinet_costs` роутами панели (туда же).
- Курсор пагинации `last_id` (нужен до онбординга крупных клиентов — отдельная задача).
- Отключение старого сборщика (решение через 2-3 месяца спокойной работы сторожей).
- Юнит-экономика (`lib/unit.js:calcOzon`) — плановая модель, не читает order_costs,
  не затрагивается.

## Ограничения (наследуются от переезда начислений)

БД читать `saas_ro`, писать только через сборщик/миграции админом; API Ozon — только
чтение, ≥1 с между запросами (для этого плана API не нужен — все данные уже в БД);
время — `datetime.now(timezone.utc)`; незнакомый тип не выбрасывается молча; миграции
идемпотентны, тенантные таблицы — с RLS (+ политика `panel_local_ro_cab1`); логи и
документы по-русски; правило: расхождение цифр = наш баг, пока не доказано обратное.
