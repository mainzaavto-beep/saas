# Дизайн: регистрация, авторизация и инвайты (2026-08-06)

## Контекст и цель

Панель переходит от закрытой (общий секретный код `SAAS_INVITE_CODE`) к **открытой платной модели**: саморегистрация → триал → подписка. Текущий auth-контур этого не выдерживает: регистрация по инвайт-ссылке в проде не работает в принципе (два независимых обрыва), сценария «существующий пользователь + инвайт» нет, восстановления пароля и почты нет, ошибки массово проглатываются. Полный перечень — 26 находок аудита auth-флоу от 2026-08-06 (отчёт Explore-агента в сессии; ключевые включены ниже по месту).

**Решение**: достраиваем текущий стек (iron-session + bcryptjs + свои роуты), без миграции на Auth.js и внешние сервисы. Соцвход не нужен; ядро (хэши паролей, sealed-cookie сессии) здоровое; все реальные проблемы — в продуктовой логике вокруг, которую любая библиотека всё равно не даёт.

**Вне охвата**: оплата подписки (тарифы, платёжный провайдер, ограничение доступа по истечении триала) — отдельная спека следующим заходом. Здесь закладываем только `trial_ends_at` и баннер триала.

## Принятые решения (с владельцем, 2026-08-06)

| Вопрос | Решение |
|---|---|
| Охват | Весь путь клиента: регистрация, вход, инвайты, восстановление пароля, ошибки |
| Модель регистрации | Открытая саморегистрация, `SAAS_INVITE_CODE` удаляется |
| Монетизация | Триал (14 дней, конфиг `SAAS_TRIAL_DAYS`) → подписка; оплата — отдельной спекой |
| Почта | Транзакционный SMTP (nodemailer), креды владелец даст на этапе реализации |
| Подтверждение email | Мягкое: в панель пускаем сразу; без подтверждения нельзя подключать API-ключи МП и приглашать команду; email пришедшего по инвайту считается подтверждённым |
| Способы входа | Только email + пароль (соцвход не нужен; если понадобится — отдельное решение) |

## Фазы (каждая деплоится отдельно)

### Фаза 0 — хотфикс инвайтов (немедленно)

Цель: ссылка наблюдателю работает сегодня, до большой стройки.

1. `middleware.js`: `/api/invite/` добавить в публичные пути (роут сам проверяет сессию на POST). Сейчас анонимный `GET /api/invite/<token>` перехватывается middleware → 401 «unauthorized» на форме регистрации, инвайт не принимается никогда.
2. `app/api/auth/register/route.js`: валидный инвайт-токен освобождает от `SAAS_INVITE_CODE` (сервер проверяет токен по БД: существует, не принят, не истёк). Сейчас при `?invite=` поле кода скрыто, а сервер код требует → всегда 403.
3. Редирект после регистрации по инвайту — в кабинет приглашения, не `/onboarding`; ответ `POST /api/invite/<token>` проверяется, ошибки показываются.
4. `lib/auth.js` `firstCabinetOf`: искать по `auth.memberships` (как `/api/cabinets`), не по `cabinets.owner_user_id`. Сейчас приглашённый сотрудник при каждом входе попадает на «Создание проекта» с `active_cabinet_id = null`.

### Фаза 1 — страница приглашения `/invite/[token]`

**Ссылка**: `<база>/invite/<token>`, база — из `NEXT_PUBLIC_URL` (задать в `.env.local`; сейчас не задан, хардкод `https://sysell.ru` ломает любой не-прод). Старый формат `/register?invite=` редиректит на новую страницу.

**Страница** (публичная) валидирует токен через `GET /api/invite/<token>` и показывает:

- Валиден: «<Имя пригласившего> приглашает вас в кабинет «<имя>» с ролью <роль>» + действия по ситуации:
  - нет сессии: «Создать аккаунт» → `/register?invite=<token>` (форма без поля кода, плашка приглашения); «У меня уже есть аккаунт» → `/login?next=/invite/<token>`;
  - есть сессия: «Принять приглашение» → `POST` → редирект в кабинет.
- Невалиден: человеческое сообщение («уже использовано» / «истекло <дата>» / «не найдено») + совет запросить новую ссылку.

**Правила принятия** (`POST /api/invite/[token]`):

- Одна транзакция: `INSERT membership` + `UPDATE invitations SET accepted_by, accepted_at`. Сейчас две операции без транзакции.
- Если у принимающего уже есть роль **выше или равная** в кабинете — membership не трогаем, инвайт не жжём, ответ «Вы уже участник». Закрывает само-понижение владельца собственной viewer-ссылкой (сейчас `ON CONFLICT ... DO UPDATE SET role` понижает).
- `user_id` строго из сессии (уже так после фикса a7bd7dc). Токен одноразовый, 7 дней, отзыв на «Команде» — без изменений.

**Страница «Команда»**: показывать ошибки создания инвайта / смены роли / удаления участника (сейчас молча игнорируются); для viewer — явное «управление командой доступно владельцу» вместо пустого списка. `GET /api/cabinets/[id]/members`: список команды виден всем участникам, но email/телефоны — только owner/manager (сейчас viewer видит контакты всех).

### Фаза 2 — открытая регистрация и триал

- `SAAS_INVITE_CODE` удаляется из кода и `.env.local`; поле «Invite-код» — с формы.
- Форма: имя, фамилия, email, пароль ×2. `first_name`/`last_name` сохраняются (сейчас сервер их игнорирует). Email → trim + lower на сервере; миграция: уникальный индекс `lower(email)` (перед этим проверить дубли в данных). Регистрация дублей — «Такой email уже зарегистрирован — войти?» со ссылкой; сырые ошибки БД (`duplicate key ...`) в UI не попадают, гонка ловится `ON CONFLICT`/уникальным индексом, не отдельным SELECT.
- Онбординг: кабинет создаётся с `trial_ends_at = now() + SAAS_TRIAL_DAYS дней` (дефолт 14). Ответы `POST /shops` проверяются; неудача — видимая ошибка, не молчаливый редирект. Баннер в шапке: «Пробный период до <дата>». Принудительной блокировки по истечении в этой спеке нет.
- Rate-limiting `/api/auth/login` и `/api/auth/register`: лимит по IP и по email: 5 попыток/мин на аккаунт, 20/мин с одного IP (значения — константы в одном месте, менять легко), ответ 429 «попробуйте через минуту». Неудачные входы — в лог (stdout → journald). Реализация уровня приложения (один инстанс Next), без внешних зависимостей.
- Вход: `next` из query сохраняется вместе с параметрами (сейчас middleware теряет `?search`-часть); после входа — последний активный кабинет по membership.
- Сессия: продление при активности (rolling, переустановка куки не чаще раза в сутки); 7 дней неактивности — истекает. Сейчас умирает ровно через 7 дней после логина посреди работы.

### Фаза 3 — почта, подтверждение email, восстановление пароля

**Транспорт**: `lib/mailer.js` — nodemailer, SMTP-креды из `.env.local` (`SAAS_SMTP_HOST/PORT/USER/PASS/FROM`). Письма текстовые, одна ссылка. SMTP недоступен → пользователю «не удалось отправить письмо, попробуйте позже», в лог — ошибка; регистрацию сбой почты не блокирует.

**Токены**: таблица `auth.user_tokens (token_hash PK, user_id FK, kind CHECK ('verify_email','reset_password'), expires_at, used_at, created_at)`. В БД — только SHA-256-хэш токена; сам токен (`crypto.randomUUID` либо 32 случайных байта base64url) — только в письме. Одноразовые. Срок: verify — 7 дней, reset — 1 час. Повторная отправка инвалидирует прежние токены того же вида.

**Подтверждение email** (мягкое):

- После регистрации — письмо со ссылкой `/verify?token=`; переход ставит `users.email_verified_at`.
- Без подтверждения: жёлтый баннер с «Отправить ещё раз» (не чаще 1/мин); закрыты подключение/изменение API-ключей МП и создание инвайтов (проверка на API, не только UI).
- Регистрация через инвайт → `email_verified_at = now()` сразу.
- Существующие пользователи (до этой фазы) считаются подтверждёнными — миграция проставляет `email_verified_at = created_at`.

**Восстановление пароля**:

- `/forgot`: ввод email → всегда «Если такой аккаунт есть, мы отправили письмо» (без раскрытия существования аккаунта) → письмо со ссылкой `/reset?token=`.
- `/reset`: новая пара пароля → смена + `session_version + 1` (все устройства разлогинены) → на `/login` с сообщением об успехе.
- Смена пароля в `/settings` — тоже `session_version + 1` (кроме текущей сессии: её кука переиздаётся) и через общий `lib/auth.js`, не прямой bcrypt в роуте.

**Серверная инвалидация сессий**: `users.session_version INT DEFAULT 1`; копия в куке; `getSession` сверяет — несовпадение = сессии нет. Смена/сброс пароля, `status != 'active'` → инкремент. Закрывает «украденная кука живёт 7 дней несмотря ни на что». Сверка требует запроса в БД — выполняется в `getSession` на Node-руте; Edge-middleware по-прежнему проверяет только валидность куки (косметика, реальные данные защищены роутами).

### Фаза 4 — надёжность и гигиена

- Единый ответ на неверный вход: 401 «Неверный email или пароль» и для suspended/deleted (сейчас 400 с текстом статуса — энумерация аккаунтов).
- `logout` — только POST (сейчас доступен GET — CSRF-выход одной картинкой).
- `login`/`register` роуты не отдают `e.message` наружу — общий «Внутренняя ошибка, попробуйте позже», детали в лог.
- `users.last_login_at` — проставляется при входе (пригодится для поддержки и для будущего биллинга).
- Мёртвый код: недостижимая ветка редиректа в `register/page.js`, никогда не устанавливаемые `error`-стейты в двух UI команды — вычистить; два дублирующих UI команды (`TeamPage.jsx` и вкладка в `settings`) свести к одному компоненту.

## Изменения схемы БД (по миграции на фазу)

- Фаза 2: уникальный индекс `lower(email)` на `auth.users`; (`trial_ends_at` уже существует).
- Фаза 3: `auth.users` + `email_verified_at TIMESTAMPTZ`, `session_version INT NOT NULL DEFAULT 1`; новая `auth.user_tokens`; backfill `email_verified_at` существующим.
- Фаза 4: `auth.users` + `last_login_at TIMESTAMPTZ`.

Схема `auth` остаётся без RLS (как сейчас, доступ только через приложение).

## Тестирование

- **Смоук-скрипт** (node, против тестовой БД + dev-сервера): регистрация → онбординг → создание инвайта → принятие новым пользователем → принятие существующим → вход сотрудника ведёт в кабинет → повторное использование токена отклонено → истёкший токен отклонён → «владелец кликает свою ссылку» не понижает роль → forgot/reset → старая сессия мертва после сброса → rate-limit срабатывает. Гоняется перед каждым деплоем auth-правок.
- **Ручной чек-лист на проде** после каждой фазы (короткий, в плане реализации).
- Существующий занесённый инвайт (токен от 2026-08-04, кабинет 1, viewer) — живой тест фазы 0: после деплоя владелец пересылает ссылку наблюдателю.

## Риски

- Правки `middleware.js` и `lib/session.js` затрагивают вход всех текущих пользователей — деплой фаз 2–3 делать не в часы пик, смоук-скрипт обязателен.
- Уникальный индекс `lower(email)` упадёт при существующих дублях — миграция сначала проверяет данные.
- Доставляемость SMTP (спам-фильтры) — вне нашего контроля; мягкое подтверждение выбрано в том числе поэтому: недоставленное письмо не блокирует вход в панель.
