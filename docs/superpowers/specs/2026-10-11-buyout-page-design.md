# Процент выкупа: страница, размеры, единый расчёт (WB) — дизайн

Дата: 2026-10-11. Решения владельца приняты в диалоге этого же дня.

## 1. Зачем

Владелец не доверяет «% выкупа» в «Сводке по товарам» и хочет точный выкуп по каждому
товару, а для одежды — по каждому размеру. Нужна отдельная страница и единая цифра везде.

## 2. Что не так сейчас

`app/api/cabinets/[id]/products-summary/route.js:97,271` (формула не менялась с переноса из
старого дашборда 12.07.2026, `f288080`):

```
buyoutPct = sold / (sold + returns + cancelled)
```

- `sold` — продажи по `sale_dt` в окне, `returns` — по `return_dt` в окне, `cancelled` —
  отмены среди заказов с `order_dt` в окне. Три РАЗНЫЕ популяции заказов в одной дроби: на
  коротком окне и при росте/падении продаж процент «плавает» без реальной причины.
- У Ozon в `cancelled` попадают отмены до отгрузки — это не невыкуп.
- В панели три независимые формулы выкупа (сводка; юнитка WB — `unit/all` по отчёту
  реализации; юнитка Ozon — по `order_costs`), не согласованные между собой.

## 3. Решения владельца

1. Выкуп считается **когортно по дате заказа**: заказы периода → судьба каждого заказа.
2. **Отмены до отгрузки в процент не входят**, показываются отдельной колонкой.
3. **«Сводка по товарам» переходит на новый расчёт** (WB) — одна цифра везде.
4. **Юнит-экономика не трогается**: там выкуп — коэффициент сведения логистики окна к одной
   продаже (`logistics = Σлогистики / продано`, сверено с фактом 06.10.2026), а не показатель
   товара. Разница документируется в контракте метрик (§5.4).
5. **Сначала только WB.** Ozon — отдельный этап после пробы данных (§8).
6. Страница с графиком по неделям.

## 4. Данные (WB, кабинет #1, факт 10.10.2026)

- `wb_orders`: `srid` уникален (4095/4095), `tech_size` заполнен у заказов одежды (XS…XL;
  у неразмерных товаров `0`), `is_cancel` integer, `cancel_dt`.
- `wb_sales`: `sale_id` `S…` (выкуп) / `R…` (возврат), связь с заказом по `srid`.
- `wb_finance_report`: по `srid` есть логистика `bonus_type_name LIKE 'К клиенту при отмене%'`
  — признак того, что товар уехал к покупателю и не был выкуплен. Из 229 отмен когорты
  60–30 дн. назад: 214 с такой логистикой (невыкуп), 15 без (отмена до отгрузки).
- `wb_order_costs.self_buyout` (integer, 53 строки на кабинете #1) — самовыкупы.
- Когорта 60–30 дн. назад: 461 заказ → выкуп 228, отмены 229, возврат 5, в пути 4 →
  выкуп ≈ 50 % (сходится с ~49 % из расчёта логистики юнитки 06.10).
- Время до развязки: медиана 4 дня, p90 11–15 дней, p99 ≈ 20 дней.

## 5. Канон

### 5.1 Судьба заказа WB (одно ведро на `srid`, проверки в этом порядке)

| Ведро | Условие |
|---|---|
| `self` (самовыкуп) | `wb_order_costs.self_buyout = 1` по `srid` — исключается из всех вёдер ниже, считается отдельно |
| `returned` (возврат) | есть `wb_sales.sale_id LIKE 'R%'` по `srid` |
| `sold` (выкуплен) | есть `wb_sales.sale_id LIKE 'S%'` по `srid` |
| `refused` (невыкуп) | `is_cancel = 1` и есть строка `wb_finance_report` по `srid` с `bonus_type_name LIKE 'К клиенту при отмене%'` |
| `cancelled_pre` (отмена до отгрузки) | `is_cancel = 1`, логистики к клиенту нет и `cancel_dt` (или `last_change_dt`, если `cancel_dt` пуст) старше `CANCEL_SETTLE_DAYS = 7` дней на дату расчёта |
| `pending` (в пути) | всё остальное, в т.ч. отмена моложе 7 дней без логистики (отчёт реализации ещё мог не прийти) |

Одна строка `wb_orders` = 1 шт. (WB отдаёт заказ поштучно).

### 5.2 Формулы

```
resolved  = sold + refused + returned
buyoutPct = resolved > 0 ? sold / resolved : null
pendingShare = pending / (resolved + pending)
```

- `pending` и `cancelled_pre` в знаменатель не входят.
- `immature = pendingShare > IMMATURE_SHARE (0.05)` — период «не дозрел», цифра ещё
  изменится; UI показывает метку.
- `lowSample = resolved < MIN_RESOLVED (20)` — процент показывается бледным.
- Размер: группировка по `wb_orders.tech_size`; `0`/пусто — «без размера», такая строка
  у товара не раскрывается. Сумма по размерам = товар, сумма по товарам = кабинет (по
  счётчикам, не по процентам).
- Период: даты заказа по МСК, `order_dt::date` в `[from, to]`, по умолчанию 30 дней по вчера
  (класс окон «по вчера», как в Сводке).

### 5.3 Недели (график)

Последние 12 полных и текущая неделя заказа (пн–вс, МСК), независимо от периода таблицы. Для
каждой недели — те же счётчики и `buyoutPct`, `immature`, `lowSample`. Режимы: весь кабинет;
выбран товар — линия товара + по линии на размер.

### 5.4 Почему юнитка — другая величина

Юнитка WB (`unit/all`, `lib/unit.js`) берёт `b = продано / (продано + невыкупы)` по СОБЫТИЯМ
отчёта реализации за 30 дней по вчера: так `F + R(1−b)/b = Σлогистики окна / продано`, и
логистика юнитки сходится с фактом. Подстановка когортного выкупа сломала бы это равенство.
Это доказанная разница формул с решением владельца (11.10.2026), а не расхождение: на
странице выкупа и в подсказке колонки юнитки — подпись, в `docs/metrics-contract.md` — новый
раздел §18.

## 7. Ошибки и границы

- Пустые `catch` запрещены (правило по финансам) — `console.error` + 500.
- Отчёт реализации отстаёт: отмена без логистики моложе 7 дней — `pending`, не
  `cancelled_pre`; со временем переходит в правильное ведро сама.
- Возврат без строки заказа (заказ старше истории `wb_orders`) в когорту не попадает — когорта
  строится от заказов.
- Только кабинет #1 для проверок; на боевых кабинетах клиентов ничего не пишем (страница
  только читает).

## 8. Вне объёма (следующие этапы)

- **Ozon**: `ozon_sales` неполна (на кабинете #1 672 «доставленных» отправления когорты без
  строки продажи), у FBO пустая `shipment_dt` — невыкуп от отмены до отгрузки, вероятно,
  отделяется только по начислениям (логистика отправления). Сначала проба, потом свой дизайн.
  До этого Ozon на странице и в Сводке — прежняя формула с пометкой «переводится».
- Выгрузка в Excel, причины невыкупа, перевод юнитки (решено не переводить).
