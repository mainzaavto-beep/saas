# Ремонт данных прибыли Ozon — дизайн

Дата: 2026-08-17. Статус: одобрено владельцем (брейншторм в сессии).

## Зачем

После переключения прибыли на начисления (план `2026-08-15-ozon-profit-switch.md`)
остались четыре известных дефекта качества данных, зафиксированные финальным ревью и
сторожем: (1) сборщик рекламы теряет `ad_spend` в дни без заказов — Check 3 сторожа
вечно красный; (2) юниты без commission-блока не имеют дат — −1,81 млн ₽ расходов
невидимы в помесячных разрезах панели; (3) отправления с потерянными каталогом SKU
пропускаются — ~334 тыс ₽ и 6 284 отправления старых месяцев кабинета 1 отсутствуют,
известный разрыв инварианта; (4) сторож слеп к резолвленным номерам отправлений
(detail-JOIN по сырому unit_number) и видит только прошлую неделю.

## Решения владельца (зафиксированы)

1. Состав: ремонт данных целиком (все четыре дефекта + скользящее окно сторожа).
   Унификация 8 формул прибыли и курсор пагинации `last_id` — отдельными планами.
2. Помесячные цифры прошлых месяцев изменятся ещё раз (перераспределение −1,8 млн ₽
   по месяцам при неизменном годовом итоге + добавка ~334 тыс ₽ в старые месяцы
   каб.1) — одобрено с шлюзом: теневой пересчёт → документ дельты → «да» владельца →
   подмена. Без «да» подмены нет.

## Компоненты

### 1. Починка ad_spend (первым — гасит вечно красный сторож)

`worker/collectors/ozon_efficiency.py::_collect_ads`: UPDATE-only паттерн заменяется
на upsert (`INSERT ... ON CONFLICT (cabinet_id, date) DO UPDATE SET ad_spend = ...`) —
день с рекламой без заказов создаёт строку сам; прочие метрики строки остаются NULL
(заказов нет — это честные NULL, не нули). Бэкфилл: пересчёт `ad_spend` за всё
покрытие `tenant.ozon_daily_campaign_ad` (источник уже в БД, API не нужен) обоими
кабинетами; сверка после: `SUM(ad_spend)` = `SUM(spend)` по кампаниям за период,
расхождение 0. Проверить симметрично: не страдает ли WB-аналог тем же паттерном —
только проверка и фиксация факта (починка WB, если болеет, — отдельная задача вне
этого плана, чтобы не раздувать периметр).

### 2. Датировка бездатных строк order_costs

Правило: юнит без commission-блока получает дату первой операции —
`min(date)` его строк начислений: в `return_dt`, если юнит помечен возвратным
(типы 45/59 или отрицательный commission-блок), иначе в `sale_dt`.
Семантика документируется в §9 и карте доверия как «дата первой операции» (не дата
продажи в строгом смысле — компромисс ради видимости денег в помесячных разрезах;
владелец в курсе). Датированные ранее строки не меняются. Инвариант: после датировки
строк с NULL в обеих датах быть не должно вовсе — сборщик проверяет и считает.

### 3. Строки без товара (SKU-пропуски)

Сборщик перестаёт пропускать юниты, чей sku не резолвится в `product_id`:
- сначала дополнительная попытка резолва через `tenant.ozon_orders` (по
  posting_number → product);
- не резолвится — строка пишется с `product_id NULL` (схема позволяет; деньги
  важнее карточки). Счётчик «без товара» в итоговой строке.
Эффект: разрыв инварианта ~334 тыс ₽ исчезает (цель: разрыв за всю историю = 0 ₽
с допуском 1 ₽); старые месяцы каб.1 наполняются. Проверить выборочно 2-3 роута
панели (pnl, products-summary): строки с NULL product_id не роняют агрегацию
(ожидаемо попадают в «прочее»/без карточки — зафиксировать фактическое поведение,
не чинить роуты).

### 4. Колонка исходного номера (миграция 042)

`ALTER TABLE tenant.ozon_order_costs ADD COLUMN IF NOT EXISTS src_unit_number text` —
сборщик пишет исходный `unit_number` начислений; `detail`-JOIN сторожа переходит на
`oc.src_unit_number = a.unit_number` (устраняет ложный `no_row` для резолвленных
номеров). Роуты панели колонку не знают — поведение панели не меняется. RLS-политики
таблицы уже стоят, новых не нужно. Индекс по (cabinet_id, src_unit_number) — только
если сторож заметно замедлится (проверить время; не создавать превентивно).

### 5. Сторож: скользящее окно

`check-ozon-profit-invariant.mjs` проверяет последние 4 закрытые ISO-недели (вместо
одной), каждая — отдельные строки вывода и отдельный вклад в exit-код. Порог
unresolved (40%/1000 ₽) применяется к каждой неделе. Время работы — замерить;
лимит разумности ~1 мин.

### 6. Пересчёт и шлюз

Как в прошлый раз: тень (миграция 041 идемпотентна — пересоздать), полный пересчёт
единым диапазоном на кабинет обновлённым сборщиком, короткий документ дельты
(помесячно: было/стало/разница; отдельно — сколько денег обрело даты и сколько
отправлений добавилось в старые месяцы), **СТОП на «да» владельца**, атомарная
подмена по образцу `scripts/switch-ozon-profit.sql`, DROP тени. После подмены —
разовый прогон сторожа: Check 1-2 зелёные по всем 4 неделям, Check 3 зелёный
(ad_spend починен), известные исключения исчезли.

## Что НЕ входит

Унификация 8 инлайн-формул прибыли (+ потребление ozon_cabinet_costs панелью);
курсор `last_id`; починка WB ad_spend, если болеет (только диагностика); разбор
403-паттерна Ozon API на 12:00-тике (наблюдение продолжается); отключение
`ozon_finance`.

## Ограничения (наследуются)

Юнит собирается по ПОЛНОЙ истории строк; lookback-пол 45 дней; DELETE-ключи =
posting ∪ исходные unit_number (уже реализовано фикс-волной; новая колонка
`src_unit_number` этот механизм не меняет, только делает исходный ключ видимым);
незнакомое не молчит;
инвариант сумм + согласованность компонент (знаковая формула); контракт колонок
панели не меняется (новая колонка — аддитивно); `datetime.now(timezone.utc)`;
миграции идемпотентны; тексты по-русски; БД читать `saas_ro`, писать сборщиком,
миграции/подмена — админским psql по скрипту; API Ozon не нужен и запрещён;
расхождение цифр = наш баг, пока не доказано обратное.
