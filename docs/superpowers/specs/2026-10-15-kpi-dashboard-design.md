# Дашборд показателей — дизайн

Дата: 2026-10-15. Статус: утверждён владельцем (диалог 15.10.2026).
Образец — скрин «Оцифровка → Общие показатели» (сетка KPI-плиток с прошлым периодом и дельтой).

## 1. Цель

Отдельная страница «Дашборд показателей»: сетка плиток с ключевыми цифрами кабинета за период,
сравнение с прошлым периодом той же длины, цвет «хорошо/плохо», раскрытие состава по клику,
личная настройка набора и порядка плиток. Все цифры — из канона (правило «одна цифра везде»,
AGENTS.md → «Жёсткое правило по финансам»); новых формул денег не вводим.

## 2. Решения владельца

| # | Вопрос | Решение |
|---|---|---|
| 1 | Объём | Полная версия: фильтры, «+ Метрика», настройка виджетов |
| 2 | Чья настройка | Своя у каждого пользователя |
| 3 | Опер. расходы и прибыль | Прибыль — канон (как `/pnl`), без `opex`; опер. расходы — справочная плитка |
| 4 | Фильтр «Группы» | Убран (бренды, категории, артикулы остаются) |
| 5 | «+ Метрика» / `▢ N` | Каталог готовых метрик (без своих формул); `▢ N` — раскрытие состава плитки |
| 6 | Товарный фильтр и кабинетные расходы | Кабинетные плитки → «—» с подсказкой «не делится по товарам»; прибыль = Σ прибыли товаров (без кабинетных расходов, как прибыль товара в Сводке) |

## 3. Размещение и фильтры

- Пункт меню верхнего уровня «Дашборд показателей» (📈) сразу после «Главной»
  (`app/cabinets/[id]/layout.js`), адрес `/cabinets/[id]/kpi`.
- Фильтры (состояние — в URL, чтобы делиться ссылкой):
  - **период** — по умолчанию 7 полных дней по вчера (класс окон «по вчера», как вся панель);
  - **магазины** — мультивыбор `auth.shops` кабинета. Tenant-данные не несут `shop_id`, поэтому
    фильтр сводится к площадке (WB/Ozon). Ограничение: несколько юрлиц одной площадки в одном
    кабинете не различаются — подписано в подсказке фильтра;
  - **бренды, категории, артикулы** — мультивыбор с поиском; варианты из `wb_articles`/
    `ozon_products` (бренд, категория — у WB `subject`/категория карточки, у Ozon `category`),
    только активные товары (`statusMap()` из `lib/finItems.js`, fallback `active`).
- **Прошлый период**: та же длина, вплотную до текущего (`prevTo = from − 1`,
  `prevFrom = prevTo − (N − 1)`), как `products-summary`.

## 4. Источники (только канон)

**Без товарного фильтра** — `wbProfitCabinet` / `ozProfitCabinet` (`lib/wbMetrics.js`,
`lib/ozonMetrics.js`) за оба периода, по выбранным площадкам. Прибыль, налоги, комиссия,
логистика, реклама, кабинетные расходы (`cabinetCosts[]`) совпадают с `/pnl`.

**С товарным фильтром** (бренд / категория / артикулы) — `wbProfitProductBatch` /
`ozProfitProductBatch`, сумма по выбранным товарам. Плитки кабинетных расходов (хранение,
платная приёмка, прочие удержания, штрафы, компенсации, опер. расходы) — «—» с подсказкой.

**Прочие источники (все — через строки «Сводки по товарам», `buildTotals`
(`lib/productsSummaryData.js`), не отдельными запросами):** заказы ₽/шт (с отменами), % выкупа и
остатки шт/капитализация ДАШБОРД НЕ СЧИТАЕТ САМ — он суммирует те же строки `items`, что отдаёт
Сводка, а `buildTotals` сама внутри зовёт канон: заказы — `wbOrdersAllByDay`/`ozOrdersAllByDay`
(как Матрица заказов и «Заказано» на Сводке, контракт §13), % выкупа — `lib/buyout.js` +
`lib/buyoutData.js` (FBO, когорта по дате заказа, контракт §18). Одна цифра со Сводкой и честный
товарный фильтр — по построению, не отдельной сверкой.
- остатки шт и капитализация — поля `stock`/`unitCost` тех же строк. Капитализация = Σ stock ×
  unitCost (текущая себестоимость `cost_overrides`); товар с остатком без себестоимости — в
  подсказке «без себестоимости: N». ⚠️ Открытый вопрос владельцу (не чиним здесь): Сводка берёт
  остаток WB как `quantity_full` (с «в пути»), Ozon — «доступно» (`fbo_present − fbo_reserved`),
  а `/stocks` у WB — «доступно». Решение по канону остатка — отдельной задачей;
- опер. расходы — `tenant.opex` (справочно, в прибыль не входит): `domain='business'`,
  `status='active'`, `included_in_cogs=0` (уже в себестоимости), дата `substr(COALESCE(op_date,
  period||'-01'),1,10)` в окне. **Не делится по площадкам** (финальное ревью 15.10.2026, F4): если
  выбраны не ВСЕ площадки кабинета (фильтр «Магазины» ýже `cabinet.marketplaces`), плитка
  недоступна («—», подсказка «Опер. расходы не делятся по площадкам — при выборе части магазинов
  не показываются») — делить кабинетную сумму по части площадок нечем, это не «ошибка загрузки».
  См. также §6.

**Строки Сводки по умолчанию (не `includeInactive=1`)** — финальное ревью 15.10.2026, F1: и
«деньги с товарным фильтром», и остатки/капитализация, и варианты фильтров (бренды/категории/
артикулы) строятся из ТЕХ ЖЕ строк, что видит Сводка по умолчанию (активные + товары с движением
периода); дашборд не включает «мусорные» inactive-товары без активности — иначе его остатки/
капитализация и товарный фильтр расходились бы со Сводкой на любом кабинете с историей снятых
с продаж карточек.

## 5. Плитки

База процентов «% от выручки» — канон выручки `revenue` (как маржа на Сводке).

| Плитка | Основная / вторая | Хорошо, когда |
|---|---|---|
| Чистая прибыль / маржа | `profit` / profit ÷ revenue | ↑ |
| Продажи | `revenue` / продано шт | ↑ |
| Реализация | `realized` | ↑ |
| Заказы | ₽ / шт | ↑ |
| % выкупа | buyout % | ↑ |
| Логистика | `logistics` (+`returnLogistics`, Ozon `services` — в раскрытии) / % | доля ↓ |
| Реклама / ДРР | `ads` / ДРР от заказов (§15.3) | доля ↓ |
| Хранение | кабинетный расход «хранение» / % | доля ↓ |
| Платная приёмка | cabinetCosts приёмка / % | доля ↓ |
| Прочие удержания | cabinetCosts прочие / % | доля ↓ |
| ROI | profit ÷ cogs | ↑ |
| Себестоимость продаж | `cogs` / % | доля ↓ |
| Опер. расходы | `opex` / % | доля ↓ |
| Налоги | `tax` / % | доля ↓ |
| Налоговая база | база по `WB_TAX_BASE` (Ozon — его канон) | нейтрально |
| Комиссия | `commission` / % | доля ↓ |
| Ср. цена до скидок МП | revenue ÷ шт | ↑ |
| Капитализация по себес. | ₽ на конец периода | нейтрально, без сравнения |
| Остатки | шт на конец периода | нейтрально, без сравнения |
| Штрафы | cabinetCosts штрафы / % | доля ↓ |
| Компенсации | cabinetCosts компенсации / % | ↑ |
| Ср. цена продажи | realized ÷ шт | ↑ |
| Ср. логистика на 1 шт | logistics ÷ шт | ↓ |
| Ср. прибыль на 1 шт | profit ÷ шт | ↑ |

**Сопоставление статей `cabinetCosts[]` с плитками (правило F2, финальное ревью 15.10.2026)** —
ДВА уровня, не один общий «неизвестный → Прочие удержания»:
1. Явный маппинг по `cost_type` (не по подписи), таблица соответствий — `COST_TILE` в
   `lib/kpiDashboard.js`; явно замапленная статья идёт в свою плитку НЕЗАВИСИМО от знака суммы
   (напр. WB `payout_other` — всегда «Компенсации», даже если бы была отрицательной).
2. Статья, которой НЕТ в явном маппинге (в т.ч. WB `reviews`, Ozon `accrual_57`/`accrual_62` и
   прочие неперечисленные accrual-коды) — маршрутизируется по ЗНАКУ канон-суммы ЭТОЙ строки:
   доход (`amount > 0`) → «Компенсации», расход (иначе) → «Прочие удержания». `costTileOf`
   принимает `amount` третьим аргументом именно для этого шага.
   Ozon-явный список расширен: «Платная приёмка» — `accrual_12/131/134` + `accrual_13/77/133/135`;
   «Штрафы» — `accrual_93` + `accrual_89/90/91/92/94`.
`cabinetCostsInfo[]` (WB «Продвижение», уже в рекламе) в плитки не входит ни на одном уровне.

**Цвет.** Красный — плохо, зелёный — хорошо, серо-голубой — нейтрально/без сравнения.
Расходы оцениваются по **доле в выручке**, а не по рублям (иначе падение продаж красит расходы в
«успех»). |Δ| < 1 % (относительное изменение оцениваемой величины) — без цвета. Деление на ноль →
«—», без цвета.

**Раскрытие (`▢ N`, клик по плитке):** всегда WB / Ozon; логистика — к клиенту / возвратная /
сборы Ozon; удержания, штрафы, компенсации, приёмка — по статьям `cabinetCosts`; налоги — WB / Ozon (разложения УСН/НДС канон
наружу не отдаёт, свою формулу не вводим); комиссия — WB / Ozon + эквайринг. N — число строк раскрытия.

**Каталог «+ Метрика»:** ДРР от продаж (§15.3), к перечислению (`payout`), прибыль до налога
(`profitGross`), СПП ₽ (WB `spp`), эквайринг, сборы Ozon, возвратная логистика, отмены шт,
возвраты шт.

## 6. Настройка виджетов

- Миграция `068_kpi_dashboard_prefs.sql`: `tenant.kpi_dashboard_prefs (cabinet_id, user_id,
  layout JSONB, updated_at)`, PK `(cabinet_id, user_id)`, RLS по `app.cabinet_id`, гранты как у
  соседних tenant-таблиц. `layout = {order: [tileKey...], hidden: [tileKey...], extra: [tileKey...]}`;
  неизвестные ключи при чтении отбрасываются.
- UI: перетаскивание (на узком экране — стрелки ↑↓), галочка «скрыть», «Сбросить к стандарту».
- Доступ: смотреть — все роли (как `/pnl`); сохранять свой layout — любой член кабинета, в т.ч.
  наблюдатель (личный вид, не данные кабинета). `user_id` — только из сессии.
- **Опер. расходы vs фильтр «Магазины» (F4, финальное ревью 15.10.2026):** `tenant.opex` —
  кабинетная сумма, физически не делится по площадкам. Если выбраны не ВСЕ площадки кабинета
  (`platforms.length < cabMps.length`, `lib/kpiDashboardData.js`) — загрузчик не запрашивает opex
  вовсе (`cur.opex = prev.opex = null`), возвращает `platformScoped: true`; `buildTiles` получает
  это как `opexUnavailable` и помечает плитку «—» с подсказкой «Опер. расходы не делятся по
  площадкам — при выборе части магазинов не показываются» — это НЕ «ошибка загрузки» (`error`),
  та же природа недоступности, что у кабинетных плиток при товарном фильтре (§4/§5), только по
  другому измерению фильтра.

## 7. Код

- `lib/kpiDashboard.js` — чистые функции: плитки из канонических агрегатов, дельты, цвет,
  производные, раскрытия, каталог, нормализация layout. Без БД.
- `lib/kpiDashboardData.js` — загрузка; запросы строго последовательно (одна транзакция
  `withCabinet`), каждый источник под своим `SAVEPOINT` (паттерн блока складов на Главной):
  сбой источника → его плитки «ошибка загрузки» + `console.error`, остальные живы.
- `app/api/cabinets/[id]/kpi/route.js` — GET (данные + layout + варианты фильтров), POST
  `save_layout` / `reset_layout`.
- `app/cabinets/[id]/kpi/{page.js, KpiPage.jsx, ...}` — `{ cabinetId }` в пропсах, палитра
  `lib/palette.js`, хуки до ранних return (D1–D7).
