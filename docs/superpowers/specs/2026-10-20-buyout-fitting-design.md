# Процент выкупа: разрез «Одиночные / Примерки» (20.10.2026)

Страница `/buyout`, контракт метрик §18. Решения владельца — 20.10.2026.

## Проблема

Часть покупателей заказывает несколько вариантов одной модели (разные размеры и/или цвета),
меряет и оставляет один — остальные уходят в невыкуп/возврат. Другие заказывают один вариант.
Общий % выкупа смешивает два поведения: по нему нельзя судить ни о посадке размера, ни о
«честном» выкупе модели.

Данные кабинета #1 (FBO, 90 дн до 20.10): Ozon — 117 из 4 610 заказов содержат >1 товара, почти
всё «Комплект нижнего белья» (≈ половина — разные размеры одного цвета, ≈ половина — разные цвета
одного размера), изредка накидки разных размеров; WB — 60 корзин из ~1 770 с одним `nm_id` в 2–3
размерах.

## Решения владельца

- Примерка = 2+ варианта ОДНОЙ модели в одном заказе; различаем типы: размеры, цвета, смешанная.
- По умолчанию страница и Сводка показывают «Все» — канон §18 не меняется; новый разрез — фильтр.

## Определения

- **Корзина**: Ozon — номер заказа = первые две части `posting_number` (`0107344381-0022-1` →
  `0107344381-0022`); WB — `wb_orders.g_number`.
- **Модель**: Ozon — `ozon_products.model_id`; WB — `wb_articles.imt_id`. Fallback (поле пусто) —
  Ozon: название товара; WB: сам `nm_id` (без склейки цветов); такие строки помечаются ⚙.
- **Вариант**: Ozon — `product_id`; WB — пара (`nm_id`, `tech_size`).
- **Цвет / размер варианта**: Ozon — `ozon_products.color` / `size` (атрибуты каталога, см. ниже);
  WB — цвет = `nm_id` (у WB карточка nm = цвет внутри `imt_id`), размер = `tech_size`.
  Пустой цвет/размер сравнивается как одинаковое значение. Разбор `offer_id` не нужен.
- **Тип строки когорты** (`fit`), по составу её корзины в пределах модели, самовыкупы не считаются:
  - `single` — в корзине один вариант модели (несколько штук одного варианта — тоже `single`);
  - `fit_size` — 2+ варианта, размер различается, цвет один;
  - `fit_color` — 2+ варианта, цвет различается, размер один; **а также** варианты одного цвета
    И одного размера/габарита, различимые ТОЛЬКО по id (напр. узор «иероглиф»/«квадрат» одной
    расцветки и размера пледа) — это расцветки/узоры одного товара, не примерка по размеру;
  - `fit_mixed` — различаются и цвет, и размер.
- **bySize** строится только по корзинам `fit_size`, где КАЖДЫЙ вариант несёт непустой `sizeKey`
  (иначе порядок «меньший/больший» строился бы на суррогатных ярлыках `sizeLabel`); такая
  корзина всё равно учтена в общих счётчиках.
- Ограничение (пишется на странице): видна только примерка внутри одного заказа; разные заказы
  одного человека не связываются — ID покупателя маркетплейсы не отдают. Оценка — нижняя граница.
  Модель = карточка, как её склеил продавец — разные товары в одной карточке (встречалось в
  электронике) дают ложную примерку; фильтр «только FBO» (§18) может расщепить корзину FBO+FBS.

## Данные (миграция 073)

- `tenant.ozon_products`: `model_id bigint`, `color text`, `size text`. Сборщик `ozon_catalog` уже
  вызывает `/v4/product/info/attributes` (проба 20.10.2026, каб. #1): `model_info.model_id`
  (все цвета и размеры комплекта — один `model_id`, count 30); цвет — атрибут 10097 «Название
  цвета» (`коричневый`), fallback — первое значение 10096 «Цвет товара»; размер — 9533 (`M`,
  `L`), fallback 4295 (российский, `44`; несколько значений → через `/`). 4508 — «размер на
  фото», НЕ размер варианта. У накидок/пледов атрибута размера нет, но есть габариты: ширина
  8416 × длина 8415 → `size = "90*160"` (нужны ОБА атрибута, иначе `None` — не угадываем; найдено
  при финальном ревью 20.10.2026, пледы «Белый иероглиф 90*160» и т. п.). Новых запросов нет.
- `tenant.wb_articles`: `imt_id bigint` — из карточек Content API в `wb_catalog` (`imtID`; проба:
  три цвета комплекта — один `imtID`). Колонки цвета у WB не нужно.
- Сборщики пишут поля через COALESCE (пустой ответ не затирает). Регистрация сборщиков не
  меняется. `lib/buyoutData.js` добавляет к строкам когорты `basket`, `modelKey`, `variantKey`,
  `colorKey`, `sizeKey`, `sizeLabel`, `fitEstimated`.

## Расчёт (`lib/buyout.js`, чистые функции)

- `tagFitting(rows)` → строки с полем `fit` и `basketKey` (корзина × модель). Группировка по
  (площадка, корзина, модель).
- `filterByFitting(rows, kind)`, `kind ∈ all|single|fitting|size|color|mixed` (`fitting` = все три
  `fit_*`; `size`/`color`/`mixed` = `fit_size`/`fit_color`/`fit_mixed`). Отсекает строки ДО `aggregateBuyout` /
  `weeklyBuyout` — как `filterByCategory`; вёдра и формула % не меняются.
- `fittingSummary(rows, asOf)`:
  - `share` — доля корзин-примерок среди корзин модели и доля строк (штук) в примерках;
  - `basketBuyout` — по СУДИМЫМ корзинам-примеркам (нет строк `pending` И не ВСЕ строки
    `cancelledPre`): доля, в которых выкуплен (`sold`) хотя бы один вариант; самовыкупы
    исключены; варианты, отменённые до отгрузки, всё равно входят в `avgVariants` (заказанный
    набор, не судьба);
  - `avgVariants`, `avgKept` — среднее число вариантов в примерке и выкупленных из них;
  - `keptBySize` — только `fit_size`: по модели — счётчик «заказанный набор размеров → выкупленный
    размер» (напр. `S+M → M: 7`), плюс по каждому размеру доля «оставлен, когда был в паре с
    меньшим / большим» — сигнал маломерит/большемерит.
  - `estimated` — есть ли строки на fallback.

## API и UI

- `GET /api/cabinets/[id]/buyout?...&fit=all|single|fitting|size|color|mixed` (дефолт `all`,
  неизвестное → `all`; `mixed` в UI не выводится — для смоука). То же для `series=1`. Ответ дополняется `fitting` (результат `fittingSummary` по строкам после фильтра
  категорий, до фильтра `fit`) и `fit` (применённое значение). Комбинируется с `cat`.
- `/buyout`: переключатель «Все · Одиночные · Примерки · Размеры · Цвета» рядом с «Категория»;
  плитка «Примерки» (доля, выкуп по заказу) под KPI; сворачиваемый блок «Что оставляют из примерок
  по размеру» — таблица по моделям; ⚙ с подсказкой при `estimated`; строка-оговорка про
  ограничение. Сводка, юнитка, `/kpi` — без изменений.
