# Качество операторских алертов + хвосты пагинации — дизайн

Дата: 2026-08-23. Статус: очередь финальных ревью наблюдаемости (M-b/M-e) и
пагинации; владелец сказал «поехали дальше» — тема выбрана как имеющая
прямую ежедневную ценность (красный шум в новой операторской плашке).

## Зачем

Наблюдаемость (план 2026-08-22) дала операторский баннер, но два класса
шума снижают доверие к красному цвету:
1. **Юнит-алерт не объясним и слишком красный.** `saas-failure@` ловит
   ЛЮБОЙ ненулевой exit тика — включая partial по троттлингу МП (429 у
   ozon_sku_ad уже красит «юнит падает» почти ежедневно). Оператор видит
   «юнит упал», но не видит из-за какого сборщика/кабинета и насколько
   это серьёзно.
2. **Серии без границы свежести.** «failed×2 подряд» горит, пока строки
   не выйдут из 48-часового окна, даже если сборщик больше вообще не
   запускается (пример вживую: шесть красных 1009 висят после disabled
   до ~24.08).

Плюс три крошечных хвоста финального ревью пагинации — дешевле привезти
одной поездкой.

## Компоненты

### 1. Объяснимый юнит-алерт (lib/opsAlerts.js)

Для каждого unit-фейла (`run_kind='systemd'`) искать «объясняющие» строки
сборщиков: `started_at` в пределах ±30 минут от unit-строки, статус из
{failed, timeout, partial}. Правила:
- есть failed/timeout среди объясняющих → красный, текст дополняется:
  «Юнит X падает с <время> (виновники: <collector> каб.<N>, …)» — до 3
  виновников, дальше «и ещё K»;
- объясняющие ТОЛЬКО partial → алерт понижается до ЖЁЛТОГО с текстом
  «Тик X завершился с partial (<collector> каб.<N> — обычно троттлинг
  МП)»;
- объясняющих нет (юнит упал сам — OOM, таймаут systemd, панель) →
  красный, текст прежний.
`classifyRuns` остаётся чистой функцией (вся логика на переданных rows);
partial-строки для этого больше НЕ выбрасываются из входной выборки до
группировки — исключение только из СЕРИЙ (как сейчас), сопоставление с
юнитом делается по полному набору.

### 2. Граница свежести серий

Серия failed/timeout×2 (красный) и partial×3 (жёлтый) срабатывают только
если САМЫЙ СВЕЖИЙ прогон пары (cabinet, collector) моложе
`SERIES_FRESH_HOURS = 12` (константа в lib/opsAlerts.js с комментарием;
12 = два плановых тика с запасом). Старше — сборщик не запускается
(disabled/выключен/снят с расписания), серия гаснет сама, не дожидаясь
выхода из 48-часового окна.

### 3. Тест-фикстуры

`scripts/test-ops-alerts.mjs` дополняется кейсами: (и) unit-fail +
failed-строка в ±30 мин → красный с виновником в тексте; (к) unit-fail +
только partial рядом → жёлтый; (л) unit-fail без объясняющих → красный
прежним текстом; (м) failed×2, самый свежий 13 часов назад → пусто;
(н) failed×2 свежие → красный (регресс-защита). Итог «OK 13/13».

### 4. Хвосты пагинации (мелкий таск, worker)

а) Тест-кейс на потолок `ACCRUAL_MAX_PAGES` в
`scripts/test-ozon-accruals-pagination.py` (5-й кейс: 201 страница без
повтора курсора → RuntimeError «потолок»; monkeypatch константы до
малого значения, чтобы тест был быстрым). б) Литерал `time.sleep(1.0)`
межстраничной паузы → `REQUEST_PAUSE_SEC` (константа уже в модуле).
в) Докстрока `ozon_accruals.py:36-41`: буллет про пагинацию убрать
из-под заголовка «Один сторож» (косметика структуры докстроки).

## Что НЕ входит

Email/пуш-алерты; поллинг баннера (обновление по навигации — принятое
решение); изменение механики OnFailure/exit-кодов сборщиков (partial
остаётся exit 3 — семантика «окно не записано» неприкосновенна); ревизия
индексов collector_runs (отдельная очередь); Sendsay.

## Приёмка

Тест 13/13; после деплоя панели живой `/api/ops/alerts` (нодой через
classifyRuns на живой выборке): сегодняшний шум обязан преобразиться —
partial-юнит-алерты жёлтые с виновником, серии 1009 (если disabled уже
случился и прогонов нет свежих) погашены; настоящие failed — красные с
именами. Сторожа: check-profit-canon (1, 1008), profit-snapshot --verify
— ALL PASS (цифры не трогаются вообще).

## Ограничения (наследуются)

Панель — деплой по протоколу; worker-правки = мгновенный деплой
(аддитивные); тексты по-русски; classifyRuns — чистая функция без БД;
расхождение цифр = наш баг.
