# География 2.0 — эффективность складов и схем FBO/FBW/FBS

Дата: 2026-08-28. Статус: утверждена владельцем (сессия 27–28.08).

## Цель

Владелец работает по FBO/FBW и FBS на обеих площадках и хочет по вкладке «География» принимать решения:
1. **Распределение стока** — на какие склады FBO/FBW везти товар (локальность продаж, покрытие регионов).
2. **Выбор схемы** — где FBS проигрывает/выигрывает у FBO по скорости доставки.
3. **Контроль операционки FBS** — время собственной отгрузки на СЦ, просрочки.

Утверждено: все три направления в одной вкладке «География»; Ozon FBS интегрируется
**везде** (заказы, продажи, прибыль), не только в географию.

## Что вскрыла разведка (27.08, живой API кабинета 1)

| Факт | Следствие |
|---|---|
| Сборщик Ozon читает только `/v3/posting/fbo/list` | 57 FBS-отправлений с мая (48 delivered) отсутствуют в панели целиком — занижены заказы, выручка, прибыль. По правилу «расхождение = наш баг» чинится обязательно |
| Сборщик читает `analytics_data.warehouse`, API отдаёт `warehouse_name` | `ozon_orders.warehouse` пуст во всех 3225 строках — разрез «по складам» для Ozon мёртв |
| WB Marketplace API доступен нашему токену | `/api/v3/warehouses` (10 FBS-складов продавца), `/api/v3/supplies` с `createdAt/closedAt/scanDt` — источник «времени отгрузки на СЦ» |
| WB statistics-api не отдаёт дату доставки на ПВЗ | Точная скорость доставки WB невычислима; принят прокси «заказ → выкуп» по `srid` с честной пометкой в UI |
| WB FBS работает с 28.07 (174 заказа, `warehouse_type='Склад продавца'`) | Признак схемы WB уже в БД (`warehouse_type`), но нигде не используется |
| Ozon `analytics_data` (FBO) содержит `city, delivery_type (PVZ/…), warehouse_id, warehouse_name` | Есть чем наполнить и склад, и тип доставки; `region` у FBO-постингов отсутствует — только город |
| Ozon FBS-постинг содержит `shipment_date`, `delivering_date`, `city`, `region` | Честные даты для скорости доставки Ozon |

Известные болячки текущего роута географии (`app/api/cabinets/[id]/geography/route.js`):
не использует канон-функции и `lib/period.js`, штуки считает `COUNT(*)` вместо `SUM(qty)`,
продажи Ozon = дубль заказов, `period=all` сканирует всё без ограничений.

## Утверждённый подход

**Поэтапно: сначала фундамент данных, потом витрина** (вариант A).
Альтернативы (витрина сразу на неполных данных; всё одним релизом) отклонены:
риск для канона прибыли и переделки.

## 1. Сбор данных (воркер)

- **Баг склада Ozon**: читать `warehouse_name` (+ сохранить `warehouse_id`, `delivery_type`);
  бэкфилл перезбором окна с 2026-05-01.
- **Ozon FBS**: тот же сборщик заказов/продаж дополнительно ходит в `/v3/posting/fbs/list`;
  строки пишутся в `ozon_orders`/`ozon_sales` с `scheme='fbs'` (FBO-ветка ставит `scheme='fbo'`).
  Прибыль — через существующий канон начислений: `ozon_accruals` собирает операции всех схем,
  связка по `unit_number`; после интеграции сверка до копейки.
- **Даты доставки Ozon**: сохранять `shipment_date` → `shipment_dt` и дату фактической
  доставки → `delivered_dt` (FBS — из постинга; FBO — из начисления «доставка покупателю»
  по `unit_number`, данные уже собираются).
- **Поставки WB FBS**: новый сборщик `wb_supplies` (marketplace-api `/api/v3/supplies`,
  пагинация по `next`) → `tenant.wb_supplies`. Лаг «closedAt → scanDt» = время отгрузки на СЦ.
- **Справочник кластеров Ozon**: сборщик `/v1/cluster/list` → `shared.ozon_clusters`
  (кластер ↔ склады; для локальности Ozon).
- **WB скорость (прокси)**: ничего не собираем — дельта `wb_orders.order_dt → wb_sales.sale_dt`
  по `srid` считается в каноне.

Регистрация новых сборщиков: orchestrator **и** `run_saas_collect.sh` (урок переезда начислений).

## 2. Схема БД (миграции)

- `tenant.ozon_orders`: `+ scheme TEXT`, `+ warehouse_id BIGINT`, `+ delivery_type TEXT`,
  `+ shipment_dt TEXT`, `+ delivered_dt TEXT`.
- `tenant.ozon_sales`: `+ scheme TEXT` (для разрезов по схеме без JOIN к заказам).
- `tenant.wb_supplies`: `cabinet_id, supply_id (PK с cabinet_id), created_at, closed_at,
  scan_dt, done, cargo_type, updated_at`.
- `shared.ozon_clusters`: `cluster_id, cluster_name, warehouse_id, warehouse_name, updated_at`
  (без RLS, как `shared.wb_warehouses`).
- Новым tenant-таблицам — политика RLS и `panel_local_ro_cab1` (правило из памяти).
- WB: новых колонок не нужно (`warehouse_type` уже есть).

## 3. Канон (lib)

Новый модуль `lib/geoMetrics.js`; расчёт локальности из `/stocks`
(`buildWarehouseEfficiency`, LATERAL-фаззи имён складов, `byCluster`) выносится в lib
и переиспользуется обеими вкладками — «Склады» и «География» считают одинаково.

- **Локальность**: % заказов, отгруженных из кластера покупателя.
  WB: `shared.region_to_cluster` (округ покупателя → кластер) × `shared.wb_warehouses.region`.
  Ozon: склад → кластер из `shared.ozon_clusters`; сторона покупателя — если
  `/v1/cluster/list` отдаёт состав регионов кластера, используем его, иначе строим свою
  карту «город/регион → кластер» по аналогии с `region_to_cluster` (решается на этапе плана
  пробой живого API).
- **Скорость**: медиана дней. WB — заказ→выкуп (прокси, включает лежание на ПВЗ);
  Ozon — заказ→`delivered_dt` (точная). Разрезы: регион × схема × склад.
- **FBS-операционка**: медиана и распределение лага `closedAt→scanDt` (WB),
  `in_process_at→shipment_date` (Ozon); просрочки.

## 4. Вкладка «География» v2 (UI + API)

Роут переезжает на канон: `lib/period.js` (классы окон «по вчера»), `SUM(qty)` вместо
`COUNT(*)`, честные продажи Ozon (из `ozon_sales`, а не дубль заказов).

Секции сверху вниз:
1. **KPI-плашки** с дельтами к прошлому окну (паттерн Сводки): локальность %,
   медианная скорость доставки, доля FBS в заказах, медианное время отгрузки на СЦ.
2. **Регионы**: заказы/продажи по округам (WB) / городам (Ozon) — нынешние графики,
   модернизированные.
3. **Локальность**: матрица «склад отгрузки → округ покупателя», подсветка
   локальных/дальних потоков.
4. **Скорость**: регионы × схема, FBO и FBS рядом — где FBS проигрывает в днях.
5. **FBS-отгрузки**: поставки WB со стадиями создана→закрыта→принята СЦ, выбросы подсвечены.

Фильтры: площадка, период, **схема (новый)**, товар/бренд/группа (как сейчас).
Пометка у WB-скорости: «до выкупа, не до ПВЗ» (прокси).
Пустые состояния честные: пока данные Ozon не накопились — «копим с ДД.ММ», без нулей.

## 5. Проверки и сторожа

- Сторож «одна цифра везде»: суммы заказов/продаж Географии = Сводке бит-в-бит.
- Сверка Ozon FBS после интеграции: выручка/прибыль = живому API и начислениям до копейки.
- Смоук-скрипты протокола проверки панели; деплой только после шлюза.
- Сверка бэкфилла склада Ozon: 0 пустых `warehouse` у свежих постингов.

## 6. Этапы (каждый — свой план → реализация → шлюз → деплой)

1. **Данные**: баг склада Ozon + FBS Ozon везде + даты доставки + `wb_supplies` +
   `ozon_clusters`; сторожа и сверки.
2. **Канон + витрина**: `lib/geoMetrics.js`, вынос локальности в lib, секции 1–4
   (WB-локальность работает сразу, Ozon — по мере накопления).
3. **FBS-операционка**: секция 5, просрочки, при желании — алерты.

## Вне рамок (YAGNI)

- Карта России/геокодирование — не делаем, хватает таблиц и матриц.
- Интеграция WB FBS-сборки заказов (`marketplace-api /api/v3/orders`) — заказы FBS уже
  приходят через statistics-api; отдельная лента не нужна.
- Рекомендательный движок «куда везти сток» — сначала смотрим на данные глазами.
- Ozon supply-orders (поставки на FBO) — отдельная тема, не про FBS-отгрузку.
