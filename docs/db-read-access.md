# Чтение боевой базы SaaS-панели

Памятка для агентов и сессий, которым нужно посмотреть данные панели.
База PostgreSQL `saas` на `localhost:5432`. Порядок действует с 2026-08-08.

## Как читать

Под ролью `saas_ro`. Пароль уже лежит в `~/.pgpass` — вводить и подставлять
ничего не нужно, каталог запуска значения не имеет:

```bash
psql -h localhost -U saas_ro -d saas -Atc "select count(*) from auth.cabinets"
```

Роль видит все рабочие схемы:

| Схема | Что внутри |
|---|---|
| `auth` | пользователи, кабинеты, участники, магазины и состояние их ключей |
| `billing` | платежи, подписки, тарифы |
| `jobs` | `collector_runs` — журнал прогонов сборщиков (статусы, ошибки) |
| `tenant` | данные клиентов: заказы, продажи, финотчёты, остатки, реклама (WB и Ozon) |
| `shared` | общие справочники |

Примеры:

```bash
# состояние ключей маркетплейсов по всем магазинам
psql -h localhost -U saas_ro -d saas -c \
  "select shop_id, cabinet_id, mp_code, auth_state, auth_failed_at from auth.shops order by shop_id"

# что не собралось за сутки
psql -h localhost -U saas_ro -d saas -c \
  "select cabinet_id, collector, status, error from jobs.collector_runs
    where started_at > now() - interval '1 day' and status <> 'ok' order by started_at desc"
```

## Чего роль не может

INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, изменение прав и чтение
`pg_authid` — всё это база отклоняет. Это не договорённость и не правило в
инструкции: у роли просто нет таких прав, обходить нечего.

У роли есть `BYPASSRLS` — иначе клиентские таблицы `tenant.*` под построчной
защитой отдавали бы ноль строк (политики выданы роли `saas_app`). Это влияет
только на видимость: роль видит данные **всех** кабинетов. Для операторской
диагностики так и задумано; для узкой задачи лучше завести отдельную роль,
ограниченную одним кабинетом.

## Если нужна запись

Миграция, удаление тестовых записей, разовая правка боевых данных —
**остановись и попроси владельца.** Не ищи обходной путь: другой инструмент,
другой скрипт, пароль из соседнего файла. Отказ в доступе — это ответ, а не
препятствие, которое надо обойти.

Запись выполняется явной командой с админским паролем, который лежит
отдельно:

```bash
PGPASSFILE=/root/.pgpass-admin psql -h localhost -U postgres -d saas -f db/migrations/0NN_*.sql
```

Тем же способом запускаются проверочные скрипты — они заводят и удаляют
тестовые записи, поэтому им нужен доступ на запись (`scripts/lib/pgpass.mjs`,
подробности в `AGENTS.md`):

```bash
PGPASSFILE=/root/.pgpass-admin node scripts/smoke-auth-phase0.mjs http://127.0.0.1:3200
```

## Что этот порядок не затрагивает

Воркер и панель ходят в базу своими учётными данными и `~/.pgpass` не
используют: воркер берёт `POSTGRES_PASSWORD` из `/etc/saas-worker.env`,
панель — роль `saas_app` из `.env.local`. Роль `saas_ro` заводится скриптом
`db/ops/saas_ro_role.sql` (не миграция: роли живут в кластере, а не в базе).
